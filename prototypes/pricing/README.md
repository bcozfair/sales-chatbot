# Prototype — เครื่องคิดราคาแบบ configurator

**ของทดลอง ยังไม่ต่อกับระบบจริง** สร้างเพื่อพิสูจน์ว่าไฟล์ราคา Excel ของฝ่ายขาย
(`data/ราคา BH (Final 02-02-69).xlsx` · `data/ราคาTC อัพเดต (13-05-69).xlsx`)
แปลงเป็นเครื่องคิดราคาอัตโนมัติได้จริง **ก่อน** ที่จะไปแตะอะไรใน production

---

## ข้อตกลงของโฟลเดอร์นี้

1. **ไม่มีไฟล์ไหนใน `prototypes/` ถูก import จากโค้ดที่รันจริง** ตรวจได้ด้วย
   `grep -rn "prototypes/" --include=*.ts --include=*.html . | grep -v "^./prototypes/"`
   ต้องได้ 0 บรรทัด
2. **ไม่แตะฐานข้อมูล ไม่มี migration ไม่มี route ไม่มี LLM** — `engine.ts` ไม่มี import ของ
   สิ่งเหล่านี้เลยแม้แต่ตัวเดียว ตัวที่อ่านไฟล์คือ `importer.ts` ซึ่งอ่าน `.xlsx` อย่างเดียว
3. **`utils/pricing.ts` · `services/quotationService.ts` · `index.ts` ไม่ถูกแก้แม้แต่บรรทัดเดียว**
4. ถอดทั้งโฟลเดอร์ทิ้งแล้วระบบเดิมเหมือนเดิมเป๊ะ

## วิธีรัน

```bash
# 1. แปลง Excel → สมุดราคา JSON  (ต้องมีไฟล์ xlsx ใน data/)
npx tsx prototypes/pricing/importer.ts

# 2. ด่านตรวจ — เทียบกับ "ตัวอย่างการคิดราคา" ที่ฝ่ายขายเขียนไว้ในชีตเอง
npx tsx prototypes/pricing/golden.ts

# 3. ด่านตรวจแม่แบบ .xlsx — ส่งออก → ให้ exceljs อ่าน → อ่านกลับ → ราคาต้องเท่าเดิมทุกบาท
npx tsx prototypes/pricing/roundtrip.ts

# 4. แม่แบบ .xlsx
npx tsx prototypes/pricing/xlsx.ts export                 # แม่แบบกฎราคา (แก้แล้วนำกลับได้)
npx tsx prototypes/pricing/xlsx.ts odoo                   # ตารางราคาสำหรับนำเข้า Odoo (ทางเดียว)
npx tsx prototypes/pricing/xlsx.ts import "<ไฟล์>.xlsx"    # อ่านไฟล์ที่แก้แล้ว + รายงานจุดที่ผิด
npx tsx prototypes/pricing/xlsx.ts import "<ไฟล์>.xlsx" --save   # เขียนทับ book.json

# 5. ลองคิดราคาด้วยมือ
npx tsx prototypes/pricing/cli.ts --code "TSK-04(S2)6x300+3M"   # อ่านรหัสแล้วคิดราคาให้เลย
npx tsx prototypes/pricing/cli.ts --list
npx tsx prototypes/pricing/cli.ts TSK-04 --options D
npx tsx prototypes/pricing/cli.ts TSK-04 --axis D=6 --axis "thread=1/2”" --dim L1=300
npx tsx prototypes/pricing/cli.ts BH-01C --dim dia_mm=600 --dim width_mm=150 --opt conn:pl2
```

`importer.ts` รับ `--data <path>` ถ้าไฟล์ Excel ไม่ได้อยู่ที่ `data/` ของทรีนี้

## พิมพ์รหัสสินค้า → ได้ราคา (`code.ts`)

แอดมินมีรหัสอยู่ในมืออยู่แล้ว การให้ไล่กดเลือกทีละช่องคือการพิมพ์ข้อมูลเดิมซ้ำ

```bash
npx tsx prototypes/pricing/cli.ts --code "TSK-04(S2)6x300+3M"
```

**ไวยากรณ์ของรหัสไม่ได้ถูกประดิษฐ์ขึ้นในโค้ดนี้ — ชีตราคาเขียนไว้เองที่หัวตารางทุกชีต**

| ชีต | เซลล์ | รหัสมาตรฐานที่ชีตเขียนไว้ |
| --- | --- | --- |
| TS-04 | `A7` | `ราคาตั้ง Standard TS_- 04(S_) 6x100+1M` |
| TS-14 | `A10` | `ราคาตั้ง Standard TS_- 14 D x100-U` |
| TS-18 | `A13` | `ราคาตั้ง Standard TS_- 18 (F_) D1-D2 x100+50` |
| BH | `E19` | `ตัวอย่างการคิดราคา BH-01C (BH-01C-600x150-380-4950W-PL-PL2)` |

`(S_)` **คือขนาดเกลียวเป็น "หุน"** (1 หุน = 1/8 นิ้ว) — พิสูจน์ด้วยราคาจริงใน Odoo
เทียบกับตาราง (วัด 2026-09-18): `TSK-04(S2)6x100+1M` = **615** = `TS-04!D25` (เกลียว 1/4")
ตรงเป๊ะ · `TSK-04(S4)6x100+1M` = **770** = `TS-04!F25` (เกลียว 1/2") ตรงเป๊ะ

### กฎเหล็กข้อเดียวของตัวอ่านรหัส: ท่อนที่ไม่มีหลักฐาน ต้องออกมาเป็น "อ่านไม่ออก"

ห้ามเดาแล้วปล่อยผ่านเงียบ ๆ เพราะ **ราคาที่ตกของไปหนึ่งท่อน หน้าตาเหมือนราคาที่ถูกต้องทุกประการ**
ผลลัพธ์ของตัวอ่านจึงเป็น "รายการท่อน" พร้อมป้าย 4 แบบ ไม่ใช่แค่ `ProductConfig`:
อ่านได้ · **ตีความเอง** (guess) · ไม่มีผลกับราคา · **อ่านไม่ออก** — หน้าจอแสดงครบทุกท่อน
และขึ้นแถบเตือนเมื่อมีท่อนที่อ่านไม่ออก

**สองพฤติกรรมที่ตั้งใจให้ "แพงไว้ก่อน" ไม่ใช่ "ถูกไว้ก่อน":**

1. แกนของตารางราคาที่รหัสไม่ได้บอก **ไม่ถูกเติมค่าแรกให้** — หน้าจอขึ้น "— ยังไม่ได้เลือก —"
   แล้ว engine ตอบว่าไม่มีราคา เพราะค่าแรกของทุกตารางคือราคาถูกที่สุดเสมอ
2. หน้าแปลนของ TS-18 ที่อ่านไม่ออก **ถูกใส่ลงแกนทั้งที่อ่านไม่ออก** เพื่อให้กฎ
   "หน้าแปลนนอกรายการต้องขอราคาจากผลิต 2" (`TW!L34`) ทำงาน — ปล่อยว่างไว้จะกลายเป็น
   ใบที่ไม่มีหน้าแปลน ซึ่งคิดราคาต่ำกว่าจริงโดยไม่มีอะไรเตือน

### ราคาสายมาจากชีตอื่น และนั่นคือเหตุผลที่ `ratesFrom` รับ `sheet` ได้

ราคาตั้งของ TS-04 คือ `6x100+1M` (รวมสาย 1 เมตรแล้ว) แต่ **ชีต TS-04 ไม่มีคอลัมน์ราคาสาย**
ทั้งที่รหัสจริงเกือบทุกตัวสั่งสายยาวกว่านั้น · ราคาสายต่อเมตรของ TC อยู่ที่
`TS-21+22+25!A26:B29` ที่เดียว (ถัก 80 · PVC 100 · ไฟเบอร์กลาส 95 · เทปล่อน 180) และชีตนั้น
เขียนกำกับไว้เองที่ `A44` ว่า *"สายType ไหน ให้เอาราคาสายType นั้นมาบวกเพิ่มกรณีเกิน 1 เมตร"*
⇒ แมปของ TS-04 อ้างข้ามชีตไปเอาราคามา **ไม่ก๊อปตัวเลขมาไว้ในแมป** ไม่งั้นวันที่ราคาสายขยับ
จะมีรุ่นที่ลืมแก้ (เจ้าของเคาะให้ใช้ตารางนี้ 2026-09-18)

ชนิดสายที่รหัสไม่ได้บอก ใช้ `axisDefaults` ของรุ่น (`สายสแตนเลสถัก` ตาม `TS-02,02-SI!E25`
*"สาย Standard Type K = สแตนเลสถัก"*) — เป็น **ข้อมูลในสมุดราคา ไม่ใช่ค่าคงที่ในโค้ด**
และเดินทางไปกลับผ่านไฟล์ `.xlsx` ได้ (คอลัมน์ "ตัวเลือกที่ใช้เมื่อไม่ได้ระบุ" ในชีต `รุ่น`)

## แม่แบบ .xlsx — สองไฟล์ที่คนละเรื่องกัน และห้ามสลับ

| | **แม่แบบกฎราคา** | **ตารางราคาสำหรับ Odoo** |
| --- | --- | --- |
| คืออะไร | "กฎ" ทั้งเล่ม | "ผลลัพธ์" ณ วันที่กด |
| ทิศทาง | ออกไปแก้ **แล้วนำกลับเข้ามาได้** | **ทางเดียว** นำกลับเข้าระบบนี้ไม่ได้ |
| ข้างใน | 13 ชีต — รุ่น · ราคาตั้งชีตละรุ่น · กฎบวกเพิ่ม · อัตราตามแกน · ข้อห้าม · ค่าที่คำนวณเอง | 3 ชีต — คำอธิบาย · `product.template` (303 แถว) · รายการที่คลี่ไม่ได้พร้อมเหตุผล |
| ใครอ่าน | แอดมินที่ตั้งราคา | หน้า import ของ Odoo |

**ทำไมต้องเตือนเรื่องสลับไฟล์:** ถ้าใครแก้ราคาในไฟล์ Odoo แล้วนำเข้า Odoo ตรง ๆ
ราคาใน Odoo จะไม่ตรงกับสมุดราคาที่ระบบใช้คิด **โดยไม่มีอะไรฟ้องเลย** — ไฟล์ฝั่ง Odoo
จึงเขียนเตือนไว้ในชีตแรกของตัวเอง ไม่ได้ฝากไว้ในคู่มือที่ไม่มีใครเปิด

**รุ่นที่คลี่เป็นรายการสินค้าไม่ได้** คือรุ่นที่ราคาคิดจากตัวเลขต่อเนื่อง (Band Heater คิดจาก
พื้นที่ผิว) — ไม่ใช่ "ยังไม่ได้ทำ" แต่เป็น "ทำไม่ได้โดยธรรมชาติของสินค้า" เพราะสเปกมีได้ไม่จำกัด
ไฟล์จึงออกมาพร้อมชีตที่บอกเหตุผลรายแถว ไม่ได้ตัดทิ้งเงียบ ๆ

### สามอย่างที่ทำให้ไฟล์ที่แอดมินแก้แล้วยัง "อ่านกลับได้"

1. **โครงสร้างอ่านออกจากตัวชีตเอง** — ชื่อแกนอยู่ในหัวตาราง (ช่องซ้ายบนเขียน `D` ทับเส้นทแยง `thread`)
   ชื่อปริมาณอยู่ในหัวคอลัมน์ (`ช่วงของ area_in2 ตั้งแต่`) ⇒ ไฟล์ที่ถูกบันทึกใหม่ · ส่งต่อ ·
   ก๊อปข้ามเครื่อง ยังอ่านกลับได้ ไม่ต้องจำอะไรจากตอนส่งออก
2. **หาคอลัมน์จากข้อความหัวตาราง ไม่ใช่จากตำแหน่ง** — สลับคอลัมน์ · แทรกคอลัมน์ของตัวเอง ·
   แทรกแถวคำอธิบายข้างบน ทำได้หมด (ไฟล์ราคาจริงที่รับมาก็ทำแบบนั้นทุกไฟล์)
3. **ผิดแถวเดียวไม่ล้มทั้งไฟล์** — รายงานเป็นรายการว่า *ชีตไหน แถวไหน ผิดยังไง*
   แล้วไม่เปลี่ยนอะไรจนกว่าจะแก้ครบ

### เงื่อนไขเขียนเป็นข้อความ ชุดเดียวกับที่ใช้บนหน้าจอ

```
ทุกกรณี · ติ๊ก[conn:pl2] · แกน[D]=6|6A|6S · แกน[D]!=6|8 · ขนาด[L1]>100
และ(ก , ข) · หรือ(ก , ข) · ไม่(ก)
```

คั่นรายการค่าด้วย `|` **ไม่ใช่ลูกน้ำ** เพราะค่าแกนจริงมีลูกน้ำอยู่ข้างใน (`3/4" , 1/2"` ใน TS-18)
· หน้าจอกับไฟล์ใช้ตัวแปลงตัวเดียวกัน (`sheet.ts`) ⇒ ไม่มีทางที่ฝั่งหนึ่งยอมรับแล้วอีกฝั่งไม่ยอมรับ

## สิ่งที่ prototype นี้ค้นพบ (ไม่ได้ตั้งใจหา)

### 1. ⚠️ ตัวอย่างใน TS-18 ไม่ตรงกับตารางของตัวเอง — ห้ามใช้เป็นเฉลย

ชีตเขียนไว้ที่ `TS-18!L4`:

```
เช่น  TSK-18(2) 6-6x100+50 = 800+650+(5x25) = 1525
```

- `800 + 650 + 125 = 1,575` **ไม่ใช่ 1,525** — ตัวเลขในหมายเหตุบวกกันเองยังไม่ลงตัว
- ราคาตั้ง D=6 Type K/J ในตารางปัจจุบัน (`TS-18!D25`) = **880 ไม่ใช่ 800**

⇒ หมายเหตุนี้ค้างมาจากราคารอบก่อน ตารางถูกอัปเดตแต่ตัวอย่างไม่ถูกอัปเดตตาม
**ถ้าใครเอาไปเป็น golden test จะไล่แก้ engine ให้ตรงกับราคาที่เลิกใช้แล้ว**
`golden.ts` จึงพิมพ์เคสนี้ออกมาเป็น "รายงาน" ไม่ใช่ "ด่าน"

### 2. ⚠️ กับดัก regex ที่เกือบทำให้ทุกขนาดได้ราคาต่ำสุด

ตัวแยกช่วงราคาของ BH เขียนครั้งแรกว่า `/^(\d+)\s*-\s*\D/` เพื่อจับ `"101 - ขึ้นไป"`
แต่ `\s*` backtrack ให้ `\D` ไปแมตช์ช่องว่างได้ ⇒ `"0 - 5"` ถูกอ่านเป็น **ช่วงไม่มีขอบบน**
แล้วกลืนทุกขนาดไปที่ 700 บาท (ของจริงคือ 10,975) แก้เป็น `[^\d\s]`

จับได้เพราะ golden case มีเฉลยจากชีต — ถ้าไม่มีเฉลย บั๊กแบบนี้ **ไม่ error และไม่มีอะไรฟ้อง**
มันแค่คืนราคาถูกเกินจริงไปเรื่อย ๆ

### 3. adder ผูกกับ "ช่วงราคา" ไม่ใช่ผูกกับรุ่น

BH-03 คิดค่ากำลังไฟเกิน 100W ที่ 10 บาท/100W (`G3:G7`) แต่ **`G8` ของช่วง "101 ขึ้นไป" เว้นว่าง**
⇒ สินค้าที่ตกช่วงนั้นไม่คิดค่ากำลังไฟ ถ้าเขียนเป็น "รุ่น BH-03 คิด 10 บาท/100W" จะเกินจริง
1,900 บาทในเคสตัวอย่าง (2000W)

### 4. หน้าแปลน JIS 10K ราคาไม่เท่ากันข้ามชีต

`TS-18` → 1/2"+3/4" 580 · 1" 650 · 1.5" 650 · 2" 700
`TW` → 1/2"+3/4" 600 · 1" 800 · 1.5" 910 · 2" 1,100

**ห้ามทำตาราง "ราคาหน้าแปลนกลาง"** — adder ต้อง scope ที่รุ่น

## ข้อจำกัดที่รู้ตัว (ของ prototype นี้เอง)

1. **ภาษาเงื่อนไขยังไม่มีตัวดำเนินการ modulo** ⇒ กฎ "ความกว้างควรลงท้ายด้วย 0 หรือ 5"
   (`BH!H5`) ยังใส่ไม่ได้ · ทางแก้: เพิ่ม operator หรือย้ายกฎนี้ไปเป็น validation ของ UI

2. **กฎที่ต้องรู้ "ความหมายเชิงตัวเลข" ของแกน D ยังต้องไล่ระบุค่าเป็นรายตัว**
   เช่น "2 element ทำได้ตั้งแต่แกน 6 mm ขึ้นไป" ตอนนี้เขียนเป็น
   `{ axis: "D", in: ["2","2.5S","3","3A", … ] }` ซึ่งยาวและลืมง่าย
   **ตัว prototype ยืนยันข้อเสนอเดิมว่า ค่าแกนควรเก็บเป็น string ดิบ แล้วแขวน `tags`
   (เช่น `dia_mm: 6`, `grade: "finished_core"`) เป็น attribute เสริม** ไม่ใช่ parse
   ความหมายจากตัวอักษร (`3.2A` · `15.97B` · `21.3I` · `7TN` ไม่มีกติกาเดียวที่ครอบคลุม)

3. **BH: ยังไม่ชัดว่า `600x150` ในรหัสรุ่นคือ (เส้นผ่านศูนย์กลาง × ความกว้าง) หรือกลับกัน**
   สูตร `W × π × ID / 645` เป็นการคูณ ผลลัพธ์จึงเท่ากันทั้งสองทาง ราคาเลยไม่เพี้ยน
   **แต่กฎ "OD เล็กสุด 65mm" กับ "ความกว้างเล็กสุด 25mm" ผูกกับตัวที่ถูก** — ต้องถามฝ่ายผลิต

4. **`TS-18` ใช้แกน `flange` ตัวเดียวกับสองตาราง (เฟอร์รูล/JIS)** ซึ่งวันนี้ไม่ชนกัน
   เพราะป้ายกำกับคนละแบบ แต่เป็นความบังเอิญ ไม่ใช่สัญญา — ของจริงควรแยกเป็น
   `flange_type` + `flange_size`

5. **สมุดราคายังไม่มีเวอร์ชันที่ผูกกับวันที่มีผล** — `book.version` เป็นวันที่ import
   ไม่ใช่วันที่ราคาเริ่มใช้
