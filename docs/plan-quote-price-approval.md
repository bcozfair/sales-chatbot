## 1. โจทย์ที่หัวหน้าสั่ง (2026-09-15)

> การออกใบเสนอราคาผ่านเว็บ ถ้าติดเงื่อนไขการขายต่ำกว่าราคาขั้นต่ำ ต้องส่งต่อให้ผู้มีสิทธิ์อนุมัติ
> อนุมัติราคาให้ก่อน ถึงจะบันทึก draft นั้นเป็นใบเสนอราคาจริงได้ — ต้องเพิ่ม role
> "ผู้อนุมัติใบเสนอราคา" · หากไม่อนุมัติก็ย้อนกลับมาหา subadmin ให้แก้ไขหรือยกเลิกได้

**คำตอบของเจ้าของต่อคำถามที่แตกแขนง** (ถามตอบ 2026-09-15 ก่อนลงมือ):

| คำถาม | คำตอบที่เลือก |
| --- | --- |
| ใครกดออกใบจริงหลังอนุมัติ | **ผู้อนุมัติกดแล้วออกใบเลย** — ไม่มีใบค้างเพราะคนลืมกลับมากด |
| กฎข้อไหนต้องขออนุมัติ | **เฉพาะ `MIN_PRICE_VIOLATION`** — ข้ออื่น (สต็อก · MOQ · สินค้าระงับ · blacklist · เครดิตค้าง) ยังติ๊กรับทราบเองได้เหมือนเดิม |
| สิทธิ์ของ role ใหม่ | **ทำได้ทุกอย่างของ `subadmin` + อนุมัติ** |
| ใบจาก LINE | **ไม่แตะ** — ติดราคาขั้นต่ำแล้วออกใบไม่ได้เหมือนเดิม |

**ทำไม LINE ถึงไม่เข้าคิว** — เส้น LINE ตอบด้วย `replyToken` เท่านั้น (ห้าม push, `CLAUDE.md`)
⇒ ต่อให้เซลส์ยิงขออนุมัติได้ ก็ไม่มีทางส่งผลอนุมัติกลับไปหาเขาทีหลัง เซลส์ต้องมานั่งถามเอง
ซึ่งแย่กว่าข้อความ "ออกใบไม่ได้ ติดต่อแอดมิน" ที่มีอยู่แล้ววันนี้ · ทางที่ใช้อยู่จริงคือให้แอดมิน
ออกใบให้ทางหน้าเว็บ ซึ่งรอบนี้มีคิวอนุมัติรองรับแล้ว

## 2. ของเดิมที่ต้องเข้าใจก่อน — ไม่งั้นแก้ผิดจุด

### 2.1 วันนี้หน้าเว็บทะลุกฎราคาขั้นต่ำได้ด้วยการติ๊กเอง

```
preview → โมดัลติ๊กรับทราบ → POST /webquote/drafts (สร้างร่าง + เขียน rule_overrides)
        → POST /api/quotation/:id/confirm ทีละใบ   ← ทั้งหมดนี้อยู่ในปุ่มเดียว
```

ร่าง **ไม่ค้างใน DB** เลยในทางปฏิบัติ เพราะสองขั้นสุดท้ายยิงติดกันในฟังก์ชันเดียว
(`confirmAll()` ใน `QuoteRequest.tsx`) ⇒ ของใหม่คือครั้งแรกที่ร่างจากหน้าเว็บ **ต้องค้างอยู่จริง**
ระหว่างรอคน ⇒ ทุกอย่างที่เคยจริงเพราะ "ร่างอยู่ไม่เกินสองวินาที" ต้องถูกตรวจใหม่หมด (§2.3)

### 2.2 การปลดล็อกผูกกับ "ใบ" ไม่ใช่ "endpoint" — ข้อนี้ห้ามเปลี่ยน

`PUT /api/quotation/:id` และ `POST /api/quotation/:id/confirm` เป็นของที่ **LIFF ของเซลส์ใช้ร่วม
กับหน้าเว็บ** ⇒ เงื่อนไขใหม่ทุกข้อต้องอ่านจาก **คอลัมน์บนแถวของใบ** ไม่ใช่จากตัว endpoint
ไม่งั้นใบจาก LINE จะเปลี่ยนพฤติกรรมตามไปเงียบ ๆ (เหตุผลเต็มอยู่ที่ `plan-web-quote-request.md` §N.2)
⇒ คอลัมน์ใหม่ `quotations.price_approval` คือตัวปลด · ใบจาก LINE เป็น `NULL` เสมอ

### 2.3 กับดักที่เจอตอนสำรวจ — ร่างที่ค้างจะถูกลบทิ้งโดยของเดิม

`insertDraftQuotations()` ลบร่างเก่าของ `user_id` เดียวกันทุกครั้งที่สร้างร่างใหม่:

```sql
DELETE FROM quotations WHERE user_id = $1 AND status IN ('pending_company','pending_contact','draft')
```

`user_id` ของหน้าเว็บคือ `web:<admin>:<sales>` ⇒ **แอดมินคนเดิมออกใบให้เซลส์คนเดิมอีกใบหนึ่ง
ระหว่างที่ใบก่อนหน้ารออนุมัติอยู่ = ใบที่รออนุมัติหายไปทั้งใบโดยไม่มีอะไรฟ้อง**
⇒ เติมเงื่อนไข `AND price_approval IS NULL` ที่ DELETE นั้น

**กับดักข้อที่สองจากเรื่องเดียวกัน: ค่าขนส่งอัตโนมัติคิดจาก "กลุ่มใบ" ซึ่งเคยแปลว่า
"ร่างทั้งหมดของ user นี้"** — จริงมาตลอดเพราะร่างอยู่ไม่ถึงสองวินาที · พอร่างค้างข้ามวัน
แอดมินคนเดิมมีได้ทั้งชุดที่รออนุมัติและชุดที่กำลังทำ ⇒ ยอดสินค้าสองชุดถูกบวกกันเพื่อตัดสิน
ค่าขนส่ง และ **ใบที่รออนุมัติถูกแก้ยอดใต้มือคนอนุมัติขณะที่เขากำลังอ่านมันอยู่**
⇒ `applyShippingFeeToQuoteGroup()` รับ `requestId` เพิ่มเป็นขอบเขตของกลุ่ม
(`price_approval->>'request_id' IS NOT DISTINCT FROM $3`) · ไม่ส่งมา = กลุ่มของใบที่ไม่ได้อยู่
ในคำขอ ซึ่งคือทุกใบของ LINE/LIFF ⇒ พฤติกรรมเดิมทุกประการ

**ทำไมไม่ใช้ status ใหม่ (`pending_approval`)** — เพราะ `status` ถูกอ่านอยู่หลายสิบจุด
(หน้าประวัติ · LIFF · `getRecentConfirmedQuotations` · export · `cancelOldRevision`) ค่าใหม่
แปลว่าต้องไล่แก้ทุกจุดให้ตีความเหมือน `draft` และจุดที่ลืมจะพังเงียบ ๆ · เหตุผลเดียวกับที่
`plan-web-quote-request.md` §N.3 เลือก "ไม่มีสถานะใหม่" ให้คิวแก้มือใน Odoo

## 3. ข้อตัดสินใจที่ล็อกแล้ว

### 3.1 กติกากลาง — เพิ่มชั้นที่สามให้ `blockingViolations()`

วันนี้กฎมีสองชั้น: ทะลุได้ด้วยการรับทราบ (ทุกข้อ) · ทะลุไม่ได้เลย (`SYSTEM_ERROR`)
รอบนี้เพิ่มชั้นกลาง **"ทะลุได้ด้วยการอนุมัติเท่านั้น"** และอยู่ที่เดียวกับของเดิมใน
`services/quotationService.ts`:

```ts
export const APPROVAL_REQUIRED_TYPES = ['MIN_PRICE_VIOLATION'] as const;  // เพิ่มข้อใหม่ = เติมที่นี่บรรทัดเดียว
export const requiresPriceApproval = (v: Violation) => …
export function blockingViolations(violations, acknowledgedKeys, approvedKeys = null)
```

**พารามิเตอร์ที่สามมีค่าเริ่มต้น `null`** ⇒ ผู้เรียกที่ยังไม่ส่งค่าได้พฤติกรรม "ไม่มีใครอนุมัติ"
= ราคาขั้นต่ำบล็อกเสมอ ซึ่งเป็นด้านที่ปลอดภัย (fail-closed) และตรงกับพฤติกรรมเดิมของใบจาก LINE

⚠️ **ผลข้างเคียงที่ตั้งใจ:** ร่างเก่าที่ติ๊กรับทราบราคาขั้นต่ำไว้ก่อน deploy จะยืนยันไม่ผ่านอีกต่อไป
ต้องส่งขออนุมัติใหม่ — วัด 2026-09-15 ก่อน deploy ว่ามีกี่ใบ (คำสั่งอยู่ที่ §7)

### 3.2 อนุมัติแล้วยังผูกกับ "ราคาที่อนุมัติ" ไม่ใช่แค่ชื่อรุ่น

`violationKey()` เป็น `type|model` ไม่รวมตัวเลขโดยตั้งใจ (ไม่งั้นโมดัลเด้งซ้ำทุกครั้งที่พิมพ์)
⇒ ถ้าใช้คีย์นั้นเป็นตัวปลดตรง ๆ **ผู้อนุมัติที่อนุมัติ ฿100 จะกลายเป็นอนุมัติ ฿10 ให้ด้วย**
คำขอจึงเก็บ "ราคาที่อนุมัติต่อรุ่น" ไว้ใน `price_approval.items[]` และตอนออกใบเทียบใหม่:

```
ราคาปัจจุบันของรุ่นนั้น ≥ ราคาที่อนุมัติ  ⇒ ยังถือว่าอนุมัติแล้ว (ขายแพงขึ้นไม่ต้องขอใหม่)
ราคาปัจจุบัน < ราคาที่อนุมัติ             ⇒ คีย์นั้นหลุด ⇒ บล็อก ⇒ ต้องขออนุมัติรอบใหม่
```

ตรรกะอยู่ที่ `approvedViolationKeys()` ใน `quotationService.ts` ที่เดียว

### 3.3 คำขอหนึ่งคำขอ = ร่างทั้งชุด ไม่ใช่ทีละใบ

ใบจากหน้าเว็บแตกเป็น PM/THT ได้ และ **ค่าขนส่งอัตโนมัติคิดจากยอดรวมของทุกใบในกลุ่ม**
⇒ ถ้าอนุมัติทีละใบ จะมีสภาพ "ออกใบ PM ไปแล้ว ส่วน THT ยังรออยู่" ซึ่งอธิบายกับลูกค้าไม่ได้
ทุกใบในการกดหนึ่งครั้งจึงได้ `price_approval.request_id` ก้อนเดียวกัน · อนุมัติครั้งเดียวออกทั้งชุด
· ใบในชุดที่ไม่มีรายการต่ำกว่าขั้นต่ำก็ถือเป็นส่วนหนึ่งของคำขอ (`items: []`)

### 3.4 ห้ามอนุมัติใบของตัวเอง — ยกเว้น `admin`

`approver` ทำงานของ `subadmin` ได้ด้วย (ข้อ §1) ⇒ เขาออกใบต่ำกว่าขั้นต่ำเองได้ ถ้าอนุมัติเองได้
ด้วย ด่านนี้ก็ไม่ได้กันอะไรเลย ⇒ **`approver` อนุมัติใบที่ตัวเองเป็นคนขอไม่ได้ (403)**

`admin` อนุมัติได้ทุกใบรวมถึงของตัวเอง เพราะ **`admin` แก้ราคาขั้นต่ำของสินค้าเองได้อยู่แล้ว**
ผ่านเมนูตั้งค่า ⇒ ห้ามเขาอนุมัติใบตัวเองก็แค่เพิ่มขั้นตอน ไม่ได้เพิ่มการควบคุม
และกันเคส "ผู้อนุมัติมีคนเดียวแล้วคำขอค้างตลอดกาล"

### 3.5 ไม่อนุมัติ = ใบยังอยู่ ไม่ใช่ถูกลบ

`price_approval.status = 'rejected'` + เหตุผล · ใบยัง `status = 'draft'` ⇒ subadmin เห็นในคิว
ของตัวเอง แล้วเลือก **แก้ไข** (โหลดรายการกลับเข้าฟอร์ม แล้วส่งคำขอใหม่ — ใบเดิมถูกยกเลิก
*หลัง* ใบใหม่ถูกสร้างสำเร็จเท่านั้น) หรือ **ยกเลิก** (`status = 'cancelled'` ด้วยกลไกเดิม)

## 5. รูปของข้อมูล

```jsonc
// quotations.price_approval
{
  "request_id": "uuid",              // ใบทั้งชุด (PM+THT) ใช้ค่าเดียวกัน
  "status": "pending | approved | rejected",
  "requested_by_id": 3, "requested_by": "nan", "requested_by_name": "…",
  "requested_at": "2026-09-15T…",
  "note": "เหตุผลที่ขอลดราคา (ผู้ขอพิมพ์)",
  "items": [                         // เฉพาะรายการที่ต่ำกว่าขั้นต่ำ — เป็น "ราคาที่ถูกอนุมัติ"
    { "model": "…", "name": "…", "quantity": 5, "price": 95.00, "min_price": 120.00 }
  ],
  "violations": [ … ],               // สิ่งที่ server คำนวณเอง ไม่ใช่ที่หน้าจอส่งมา
  "decided_by_id": 7, "decided_by": "boss", "decided_at": "…",
  "decision_note": "ลดได้ถึงแค่นี้"   // ผู้อนุมัติพิมพ์ (บังคับเมื่อไม่อนุมัติ)

```

⇒ ใบที่ถูกยกเลิก/ออกเลขแล้วหลุดจากคิวเอง ไม่มีปุ่ม "ปิดงาน" ให้ใครลืมกด (กติกาเดียวกับ §N.3)

## 6. เส้นทางใหม่ทั้งเส้น

```
subadmin กรอกฟอร์ม → /webquote/preview → เจอ MIN_PRICE_VIOLATION
   → โมดัล: ส่วน "ต้องขออนุมัติ" (ติ๊กไม่ได้ อ่านอย่างเดียว) + ช่องเหตุผล
   → ปุ่ม "ส่งขออนุมัติราคา" → POST /webquote/drafts {request_approval:true}
        → สร้างร่างจริง + price_approval:pending  → **ไม่ยิง confirm**
   → หน้าจอ: "ส่งขออนุมัติแล้ว รอผู้อนุมัติ"

ผู้อนุมัติ (approver/admin) → แท็บ "อนุมัติราคา" → เปิดคำขอ → เห็นทุกบรรทัด + ส่วนต่างจากขั้นต่ำ
   ├─ อนุมัติ  → ตรวจกฎใหม่ (fail-closed) → เขียน approved → confirm ทุกใบในชุด → เลขใบ + PDF
   └─ ไม่อนุมัติ (ต้องใส่เหตุผล) → เขียน rejected → ใบกลับไปอยู่คิวของ subadmin
                                     ├─ แก้ไข → โหลดเข้าฟอร์ม → ส่งคำขอใหม่ (ใบเดิมถูกยกเลิกหลังใบใหม่สำเร็จ)
                                     └─ ยกเลิก → status = cancelled
```

## 7. ด่านตรวจ

`npm run diag:price-approval` — **ข้อที่ห้ามล้มเด็ดขาดคือข้อ 1** เพราะเป็นตัวพิสูจน์ว่าเส้น LINE
ไม่ถูกแตะ:

1. ใบจาก LINE ที่ติดราคาขั้นต่ำ → `PUT` และ `confirm` ได้ 422 เหมือนเดิม
2. เว็บส่งคำขอ → ร่างถูกสร้าง `status='draft'` + `price_approval.status='pending'` + **ยังไม่มีเลขใบ**
3. ยิง `confirm` ใบที่ยัง pending ตรง ๆ → 422 (ติ๊กรับทราบปลดไม่ได้)
4. `approver` อนุมัติใบที่ตัวเองขอ → 403 · `admin` อนุมัติได้
5. อนุมัติ → ทุกใบในชุดได้เลขใบ · `price_approval.status='approved'`
6. ไม่อนุมัติ → ใบยังเป็น `draft` + `rejected` + มีเหตุผล · `confirm` ยัง 422
7. อนุมัติแล้วราคาถูกแก้ให้ต่ำลงกว่าที่อนุมัติ → บล็อกอีกครั้ง (§3.2)
8. `insertDraftQuotations` รอบใหม่ของ `user_id` เดิม → ใบที่รออนุมัติ **ไม่ถูกลบ** (§2.3)

ด่านร่วมที่ต้องผ่านด้วย: `npx tsc --noEmit` · `npm --prefix frontend run lint` ·
`npm --prefix frontend run build` · `npm run diag:web-quote` · `npm run diag:confirm-race` ·
`npm run diag:quote-validation` · `npm run diag:stock-rule-put`

**ก่อน deploy ต้องวัด** (อ่านอย่างเดียว) ว่ามีร่างเก่าที่ติ๊กรับทราบราคาขั้นต่ำไว้ค้างอยู่กี่ใบ ตาม §3.1:

```sql
SELECT COUNT(*) FROM quotations
 WHERE status = 'draft'
   AND rule_overrides->'acknowledged_keys' @> '["MIN_PRICE_VIOLATION|"]'::jsonb IS NOT FALSE
   AND rule_overrides IS NOT NULL;
```

## 8. สิ่งที่ *ไม่* ทำ (กัน regression)

* **ไม่แตะเส้น LINE** — `handlers/lineHandler.ts` และ `quotationAgent.ts` ไม่ถูกแก้แม้แต่บรรทัดเดียว
* **ไม่เพิ่มสถานะใหม่ใน `quotations.status`** (§2.3)
* **ไม่แจ้งเตือนผ่าน LINE** — ห้าม push (กฎเหล็ก) · คิวเป็นตัวเลขบนเมนูแทน
* **ไม่ทำ workflow อนุมัติหลายชั้น** — หนึ่งคำขอ หนึ่งผู้อนุมัติ จบ
* **ไม่ย้ายกฎราคาขั้นต่ำออกจาก `validateQuotationItems`** — ยังเป็นจุดเดียวของทั้งระบบ
* **ไม่ backfill ใบเก่า** — คอลัมน์ใหม่เป็น `NULL` ทั้งฐาน แปลว่า "ไม่มีคำขอ" ซึ่งถูกต้องอยู่แล้ว
