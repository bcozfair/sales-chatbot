# สถานะจัดส่งใน chatbot (ขั้น 6 ของ sync ใบสั่งขาย v3) — เอกสารส่งต่องาน

สถานะ: **ยังไม่เริ่ม · รอ API ใหม่สองเส้นจากทีม Odoo** — เขียน 2026-10-05 ตอนปิดขั้น 1–5 ของ
`docs/plan-saleorder-v3.md` · ไฟล์นี้คือจุดเริ่มของคนที่มารับงานต่อ: อะไรรู้แล้ว · อะไรมีในฐานแล้ว ·
อะไรห้ามลืม · อะไรยังไม่รู้และห้ามเดา · เริ่มทำอะไรก่อน

---

## 1. สิ่งที่เจ้าของบอกไว้ (2026-10-05 · คำต่อคำ)

> "มีแผนจะใช้ข้อมูลระดับบรรทัด/MO ในระบบการตรวจสอบสถานะการจัดส่ง order ครับ กำลังรอทีม odoo เพิ่ม api ใหม่มาให้"

> "ผมไม่สามารถขออะไรเพิ่มจากทีม odoo ได้ครับ ต้องใช้เท่าที่เขาให้มาให้มีประสิทธิภาพที่สุด
> และระบบตรวจสถานะจัดส่งจะอยู่ที่ chatbot
> API ใหม่ที่มีข้อมูลสถานะจัดส่งจะแยกเป็นเส้นใหม่ 2 เส้น MO+OP และ Messenger+OP"

นอกจากสามประโยคนี้ **ยังไม่มีข้อตกลงอื่น** — หน้าตา ผู้ใช้ ขอบเขตข้อมูล ล้วนยังไม่ได้คุย (ข้อ 5)

## 2. ของที่มีในฐานแล้ว — ใช้ได้ทันทีโดยไม่ต้องรอ API

sync v3 (prod ตั้งแต่ 2026-10-05 13:29) เก็บ MO และใบแจ้งหนี้ระดับบรรทัดไว้แล้วใน `sale_order_details.lines`
(jsonb · 1 แถว = 1 `sale_order_id` · รูปเต็มอยู่ที่ `docs/plan-saleorder-v3.md` ข้อ 4.3):

```json
"mos": [ { "ref": "Assy/2606/1249", "deadline": "…", "planned_start": "…", "planned_finished": "…",
           "qty": 3, "routing": "Immersion Heater", "status": "QC" } ]
```

วัด 2026-10-05 (ฐาน prod · อ่านอย่างเดียว):

| | จำนวน |
| --- | --- |
| ใบใน `sale_order_details` | 318,310 (294 MB รวม index) |
| ใบที่มี MO อย่างน้อย 1 ตัว | 41,719 |
| MO ทั้งหมด | 50,097 (`ref` ไม่ซ้ำข้ามใบ) |
| `status` ของ MO | QC 42,453 · Cancelled 6,042 · Done 1,391 · Confirmed 125 · Draft 71 · Planned 10 · In Progress 4 · **`4` 1 แถว** (ค่าผิดรูปจากต้นทาง) |

- **QC เป็นสถานะที่เยอะที่สุด ไม่ใช่ Done** — ยังไม่รู้ว่า QC ของ Odoo ชุดนี้แปลว่า "ผลิตเสร็จรอตรวจ" หรือ "จบแล้ว"
  ห้ามตีความเองก่อนถามเจ้าของ (ข้อ 5)
- ไม่มีข้อมูลการจัดส่ง/แมสเซนเจอร์ใน v3 เลย — ส่วนนั้นต้องรอเส้น Messenger+OP
- **ยังไม่มี GIN index บน `lines`** (ตั้งใจ · ยังไม่มีผู้อ่าน) — ถ้าต้องค้นด้วยเลข MO ให้สร้างด้วย
  `CREATE INDEX CONCURRENTLY` ในขั้นนี้ (แผน v3 ข้อ 4.1)
- **คีย์ของใบ:** `sale_order_id` ไม่เปลี่ยนตลอดอายุใบ · `order_reference` เปลี่ยนตอน Odoo ยืนยัน (QP→OP · QT→OT)
  และ `sale_orders` เหลือแถวชื่อเก่าค้างไว้ (ซาก · ไม่ลบโดยเจตนา · ดู `CLAUDE.md` หัวข้อ `sale_orders`)
  ⇒ join ด้วย `sale_order_id` ถ้า API ใหม่ให้มา · ถ้าให้แค่ชื่อ ต้องรู้ว่าเป็นชื่อหลังยืนยัน (OP) เสมอหรือไม่

## 3. แบบที่วางไว้ในแผน v3 (ข้อ 5 · ขั้น 6) และรูปแบบที่ควรลอก

แผนเดิมเขียนไว้บรรทัดเดียว: *API MO+OP / Messenger+OP → resource ใหม่ใน `syncService` (cursor + ตารางของตัวเอง)
+ บริการสถานะจัดส่ง · join ด้วย `order_reference` / `MO Reference`* — ขยายความ:

- **1 เส้น API = 1 resource** ใน `RESOURCES` ของ `services/syncService.ts` (`ResourceId` · `stateKey` ใน `sync_state` ·
  `label` · `load`) — ไล่ทุกที่ที่อ้างรายชื่อ resource ด้วย
  `grep -rn "'saleorders'" --include=*.ts --include=*.tsx --exclude-dir=node_modules --exclude-dir=public .`
  (วัด 2026-10-05: `services/syncService.ts` รวมค่าตั้งต้น `sync_settings.resources` · `frontend/src/admin/SyncPanel.tsx` ·
  `scripts/sync/syncLog.ts` · สคริปต์ sync ใบสั่งขาย)
- **ตารางของตัวเอง** ไม่ยัดลง `sale_orders` (ตารางที่ถูกอ่านตลอดเวลาและไหลออก SYNC_API ภายนอก) —
  เหตุผลเดียวกับที่ `sale_order_details` แยกตาราง (แผน v3 ข้อ 4.1)
- รูปแบบใน `scripts/sync/` ที่พิสูจน์แล้วบน prod และควรลอก ไม่ใช่เขียนใหม่:

| เรื่อง | ของที่มี | ทำไม |
| --- | --- | --- |
| เรียก gateway | `createGatewayGet()` ใน `gatewayClient.ts` | timeout ครอบทั้ง header+body · แยก error "ติดต่อไม่ได้" ให้ยกเลิกทั้งรอบ |
| แบ่งหน้า | `decideV3PageTransition()` ใน `syncPagination.ts` | **`has_more` ของ gateway เชื่อไม่ได้** (เคยตอบ false ตั้งแต่หน้าแรก) · cursor ไม่ขยับ = หยุด · หน้าไม่เต็มจบรอบได้เฉพาะ incremental |
| ด่านตรวจรูปทุกหน้า | `saleOrderV3.ts` | รูปผิด = throw แล้ว rollback ทั้งหน้า · เขียนผิดเงียบ ๆ แย่กว่าหยุด |
| เขียนเฉพาะเมื่อค่าเปลี่ยน | `syncSaleordersV3.ts` | `updated_at` ขยับเฉพาะค่าธุรกิจเปลี่ยน ⇒ ผู้อ่านปลายทางไม่ทำงานฟรี |
| กันรันซ้อน | advisory lock ต่อ resource (`sync:sale_order_v3`) | กล่องกวาดแยกกับแอปชนกันไม่ได้ |
| โหมดอ่านอย่างเดียว | `--v3-dry-run` | ตรวจกับฐานจริงก่อนเขียนฐาน |
| ด่าน | `scripts/diag/saleOrderV3Smoke.ts` | gateway ปลอม + ฐานจริงใน ROLLBACK ไม่ยิงเน็ตจริง |
| กวาดรอบแรก | กล่องแยก `docker compose run --rm` (แผน v3 ข้อ 4.8 + 6) | ไม่ถือคิว sync ของแอป · สินค้า/ลูกค้าไม่หยุด |

## 4. เงื่อนไขที่ผูกไว้แล้ว — ข้อไหนลืม งานพังหรือเสียเงิน

1. **gateway เปิดแค่ 07:00–18:00** — กวาดย้อนหลังต้องเริ่มและจบในช่วงนี้ (งาน ~2 ชม. เริ่มก่อน ~15:30) · ตั้งเวลากลางคืนไม่ได้
2. **API key ใช้ร่วมกับ Appsale · เพดาน 2 request พร้อมกัน** — กวาดได้สายเดียว · ห้ามรันพร้อม Full Sync ของ Appsale
3. **gateway v3 ตอบ 6–8 วิต่อครั้งไม่ว่าขอกี่ใบ** (วัด 2026-10-05 · v2 0.2 วิ) — ถ้าเส้นใหม่ช้าแบบเดียวกัน
   สอง resource เพิ่มรอบ sync อัตโนมัติ (ทุก 5 นาที จ–ศ 07:10–17:50 ตาม `sync_settings` · วัด 2026-10-05) อีกอย่างน้อย ~15 วิ · วัดจริงก่อนตัดสินว่าอยู่ในรอบเดียวกันหรือแยกตาราง
4. **ขออะไรเพิ่มจากทีม Odoo ไม่ได้** — ช่องที่ไม่มีมาต้องหาทางจากของที่มี หรือบอกเจ้าของว่าทำไม่ได้
5. **LINE ตอบได้ด้วย `replyToken` เท่านั้น ห้าม push** (`CLAUDE.md` · โควตา/ค่าใช้จ่าย) ⇒
   **แจ้งเตือนเซลส์/ลูกค้าเองเมื่อสถานะเปลี่ยนผ่าน LINE ไม่ได้** · ทำได้แค่ "ถามแล้วตอบ" หรือหน้าจอในแอดมิน
6. **งบตอบ LINE 48 วินาที** — คำตอบเรื่องสถานะต้องอ่านจากฐานที่ sync ไว้แล้ว ห้ามยิง gateway สดระหว่างตอบ
   (ช้า 6–8 วิ และปิดหลัง 18:00)
7. ฐาน: migration additive + ยุบเข้า `migrations/schema.sql` · ห้าม `COMMENT ON` · query วิเคราะห์ตั้ง `statement_timeout` ·
   **เขียนฐาน prod / deploy ต้องได้คำสั่งเจ้าของทุกครั้ง**
8. **ห้ามเติมหรือลบใบสั่งขายเก่า** (วันตัด 2022 + ใบเดิมคงไว้ · แผน v3 ข้อ 2) — ข้อมูลจัดส่งของใบก่อน 2022 ที่ไม่มีในฐานให้ข้าม
   แบบเดียวกับ `selectStorable`

## 5. ยังไม่รู้ — ห้ามเดา ต้องดูจาก API จริงหรือถามเจ้าของ

จาก API (ดูเองได้เมื่อได้ URL):
1. ชื่อเส้น · พารามิเตอร์ (`since` / cursor แบบไหน) · รูปหน้า · มีตัวนับต่อหน้าแบบ `sale_order_count` ไหม · `has_more` เชื่อได้แค่ไหน
2. **คีย์ที่ให้มา**: `sale_order_id`? ชื่อใบ (ชื่อก่อนหรือหลังยืนยัน)? `MO Reference`? รหัสงานแมสเซนเจอร์? ผูกถึงระดับบรรทัดไหม
3. ค่าสถานะทั้งหมดของแต่ละเส้น · ส่งย้อนหลังถึงเมื่อไหร่ · ส่งซ้ำเมื่ออะไรเปลี่ยน
4. เส้น MO+OP ซ้ำกับ `mos[]` ที่ v3 ให้อยู่แล้วแค่ไหน — **เทียบทีละช่องก่อนสร้างตาราง MO ซ้ำ**

ต้องถามเจ้าของ (พร้อมตัวเลขจากข้างบน):
5. ใครดูสถานะ และดูที่ไหน — เซลส์ถามบอทใน LINE ("OP-… ถึงไหนแล้ว") · หน้าแอดมิน · ทั้งคู่ ⇒ เปลี่ยนพื้นผิวที่ต้องทำ
   และกติกาหน้าตา (`docs/design.md` สี่พื้นผิวกติกาไม่เหมือนกัน)
6. "ส่งแล้ว" คือสถานะไหน · ใบที่ส่งหลายรอบ/หลาย MO แสดงอย่างไร · MO สถานะ `QC` แปลว่าอะไรในโรงงานนี้
7. ใบยกเลิกใน Odoo ต้องแสดงไหม (เจ้าของเคยบอกว่าไม่สนสถานะยกเลิกใน Odoo **ในเรื่องการนำเข้าใบเสนอราคา** —
   เรื่องจัดส่งยังไม่ได้ถาม อย่าเหมารวม)

## 6. ลำดับเริ่มงานเมื่อ API มา

1. **สำรวจแบบอ่านอย่างเดียว** 2–3 หน้าด้วยสคริปต์ชั่วคราว (ไม่ commit) — จดช่อง · ชนิด · เวลา/ครั้ง · พฤติกรรมแบ่งหน้า ·
   ขนาด แล้วเขียนลงไฟล์นี้เป็นหัวข้อ "ข้อเท็จจริงของ API" พร้อมวันที่ (แบบแผน v3 ข้อ 3) · ห้ามพิมพ์ API key
2. ตอบข้อ 5 ข้อ 1–4 เอง แล้วถามเจ้าของข้อ 5–7 พร้อมตัวเลข
3. ให้ `architect` วางแผน (ตาราง · resource · บริการ · พื้นผิว) — งานนี้แตะ sync + ฐาน + อย่างน้อยหนึ่งพื้นผิว
4. migration additive → ตัวแปลง + ด่านตรวจรูป → `--dry-run` อ่านอย่างเดียว → ด่าน gateway ปลอม → กวาดรอบแรกด้วยกล่องแยก
   ในเวลางาน → `up` (runbook แบบแผน v3 ข้อ 6 · ทุกบรรทัดที่เขียนฐานต้องได้คำสั่งเจ้าของ)
5. อัปเดตไฟล์นี้ + แถวขั้น 6 ใน `docs/plan-saleorder-v3.md` ข้อ 5 + `CLAUDE.md` ในคอมมิตเดียวกับงาน
