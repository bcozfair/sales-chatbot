## 0. สรุปสำหรับคนอ่านหน้าเดียว

- **สร้างเป็นโมดูลของ chatbot เอง** (`services/drawing/`) โดยยกโครงสร้างและเรขาคณิตจาก `heater-app` ของ Appsale
  มาเป็น TypeScript แล้วปรับปรุง (§2.5) · หลังพอร์ตเสร็จ **chatbot เป็นเจ้าของโค้ดชุดนี้** ไม่ดึงของใหม่จาก Appsale อีก
- **การปรับปรุงที่สำคัญที่สุด: โมดูลแบบไม่มีตัวอ่านรหัสของตัวเอง** — มันรับ "ผลการอ่านรหัส" จากหน้าคำนวณราคา
  ซึ่งเป็นการอ่านครั้งเดียวกับที่ใช้คิดราคา ⇒ **ราคากับแบบเป็นของชิ้นเดียวกันโดยโครงสร้าง** ความเสี่ยงอันดับหนึ่งของ
  ฉบับที่ 1 (Appsale อ่านรหัสจริงได้ 60.8% · BH-02 อ่านได้ 0/494) หายไปตั้งแต่ต้นเหตุ
- **ลูกค้าได้ลิงก์หน้าเว็บหมุนดูแบบ 3 มิติ + ปุ่มโหลด PDF · STEP · PNG** · ลิงก์อายุ 7 วัน ยกเลิกเองได้ ·
  เซลส์คัดลอกลิงก์ไปส่งเอง (ไม่มี LINE push)
- **หน้าเว็บ 3 มิติไม่กินทรัพยากรเซิร์ฟเวอร์** (§6.1 · วัด 2026-10-06): เซิร์ฟเวอร์สร้างไฟล์ **ครั้งเดียว** ตอนกดสร้างลิงก์ ·
  ลูกค้าเปิดกี่ครั้งเซิร์ฟเวอร์ก็แค่ส่งไฟล์ที่เก็บไว้ ส่วนการวาดภาพ 3 มิติทำบนมือถือของลูกค้า · ไฟล์ 3 มิติที่ใหญ่ที่สุด
  2.6 MB (ทั่วไป ≤ 0.14 MB) ⇒ **คุ้ม เก็บหน้าเว็บ 3 มิติไว้** · ของที่หนักจริงคือไฟล์ STEP (สูงสุด 12.9 MB หลังบีบอัด)
  ซึ่งลูกค้าได้อยู่แล้วไม่ว่าจะมีหน้าเว็บหรือไม่
- **ภาพ 3 มิติวาดด้วย three.js ตัวดูชุดเดียว** ใช้ทั้งในการ์ดแอดมิน (React) หน้าลูกค้า และภาพใน PDF/PNG ⇒ เซลส์เห็นภาพไหน
  ลูกค้าก็ได้ภาพนั้น · ความสมจริงมาจากวัสดุและแสง ไม่ได้มาจาก React (§4.6)
- **PDF ของแบบเป็นเอกสารของตัวเอง ไม่แตะ PDF ใบเสนอราคา** — แม่แบบยกจากกระดาษแบบของ Appsale (§5.4)
- **เฟส:** 0 ฐานของโมดูล + พอร์ตรุ่นแรก → 1 ใช้ภายในในหน้าคำนวณราคา → 2 ลิงก์ให้ลูกค้า → 3 ผูกกับใบเสนอราคา
- **ต้องทำได้ครบทุกอย่างที่ Appsale ทำได้** (เจ้าของ 2026-10-06) — ภาพฉาย 2 มิติ · กระดาษแบบ · PNG/SVG/PDF · ตัวตรวจสเปก ·
  มุมกล้องติดไฟล์ · รูเจาะพร้อมตำแหน่ง · ครบ 33 รุ่นรวมฮีตเตอร์ — รายการตรวจรับ §2.6

## 1. เป้าหมาย และสิ่งที่ไม่ใช่เป้าหมาย

**เป้าหมาย:** ผู้เสนอราคาพิมพ์/กรอกรหัสสินค้าสั่งทำในหน้า "คำนวณราคา" → ได้ราคา (มีอยู่แล้ว) **และ**
ได้แบบ 3 มิติของชิ้นนั้นในจอเดียวกัน → กดปุ่มเดียวได้ลิงก์ส่งลูกค้า ลูกค้าเปิดบนมือถือแล้วหมุนดูได้ทันที

**ไม่ใช่เป้าหมาย (อย่างน้อยเฟส 1–3):**
- ไม่ใช่แบบผลิต — เป็น **แบบอ้างอิงตามแคตตาล็อก** (ยึดข้อความกำกับเดียวกับ Appsale:
  *"Coloured catalogue reference; illustrative fittings; faceted geometry"*)
- ไม่ใช่ STEP แบบผิวโค้งจริง (analytic B-rep) — ผิวเหลี่ยม (faceted) พอสำหรับเฟส 1–3 (หัวหน้าเคาะ §9 ข้อ 5)
- ~~ไม่วาดรุ่นที่หน้าคำนวณราคายังคิดราคาไม่ได้~~ — **ยกเลิก 2026-10-06 ค่ำ** เจ้าของ: *"ต้องวาดแบบได้ทุกรุ่นตามที่ appsale ทำได้ ไม่จำเป็นต้องคิดราคาได้"*
  ⇒ แบบไม่ขึ้นกับราคา · รุ่นที่สมุดราคายังไม่มี (ฮีตเตอร์ 14 รุ่น · TS_-07/11L/15/17) เพิ่มลงสมุดราคาแบบ "ยังไม่มีราคา" เพื่อให้มีผลอ่านรหัส (§2.6 ข2–ข3)
- ไม่เชื่อมต่อ Appsale ขณะรัน — ไม่เรียก API ไม่อ่านไฟล์จากรีโปนั้น (รีโป Appsale ใช้แค่ในด่านช่วงพอร์ต §7)
- ไม่ส่งอะไรผ่าน LINE push (ห้ามตลอดไป · เหตุผลเชิงเงิน ดู `CLAUDE.md`)

### 2.6 ต้องทำได้ครบทุกอย่างที่ Appsale ทำได้ (เจ้าของสั่ง 2026-10-06)

> *"เราต้องมีสิ่งที่ Appsale ทำได้แต่เรายังทำไม่ได้ ทั้งหมด"* — ตารางนี้คือรายการตรวจรับ ข้อไหนยังไม่ ✅ = โมดูลยังไม่ครบ
> **แก้ 2026-10-06 ค่ำ — เจ้าของ: *"ต้องวาดแบบได้ทุกรุ่นตามที่ appsale ทำได้ ไม่จำเป็นต้องคิดราคาได้"*** และเคาะสามข้อ:
> (1) **ตัวอ่านรหัสยังเป็นของหน้าคำนวณราคาตัวเดียว** — รุ่นที่ยังคิดราคาไม่ได้ เพิ่มลงสมุดราคาแบบ "ยังไม่มีราคา" (ขึ้นว่าต้องขอราคา) ไม่มีตัวอ่านที่สอง ·
> (2) **การ์ดอยู่ที่เดิม** (หน้าคำนวณราคา · ไม่มีเมนูใหม่) · (3) **รูเจาะ BH ผู้เสนอราคากรอกตำแหน่งเอง** ระบบไม่จัดให้ กรอกครบจึงส่งได้ ·
> ผลกับโค้ด: `checks.ts` ถอด "คิดราคาไม่ได้ = ส่งไม่ได้" แล้ว ("ไม่รับผลิต" ยังปิด — ข้อห้ามการผลิต ไม่ใช่ราคา) · ตัวเลขด่าน coverage ไม่ขยับ (ทั้งสามตระกูลมีรุ่นในสมุดอยู่แล้ว)

## 4. โครงสร้างที่เสนอ

### 4.1 ภาพรวมเส้นทาง

```
หน้า "คำนวณราคา" (มีอยู่แล้ว)
   │  POST /api/admin/pricing/quote  → { code, parsed{ form | tsForm }, outcome }
   │  หน้าจอส่ง code + ตัวเลือกนอกรหัสชุดเดิมต่อ (ไม่ส่ง parsed — เซิร์ฟเวอร์อ่านเองซ้ำ ไม่เชื่อค่าจากหน้าจอ)
   ▼
POST /api/admin/drawing/preview { code, picks }                    ← routes/drawing.ts
   │  quote(code, picks)       ← ฉีดจาก index.ts = ตัวคิดราคาตัวเดียวกับหน้าคำนวณราคา (§4.3)
   │  fromReading(parsed)      → { family, spec } หรือเหตุผลที่ยังวาดไม่ได้       services/drawing/spec/
   │  families[family].model(spec) → Part[]                         ← โมเดลชุดเดียว
   │  checks(spec, outcome)    → ผ่าน / เตือน / ผลิตไม่ได้ + ส่งให้ลูกค้าได้ไหม     services/drawing/checks.ts
   │  คืน: ตระกูล · ค่าที่ใช้วาด · ผลตรวจ · previewId
   │
   ├─ GET …/preview/:id/model.glb           ← writers/glb.ts
   ├─ GET …/preview/:id/sheet.pdf · .png    ← render/ ของโมดูลแบบ (แม่แบบ §5.4 + ตัวดู §4.6) บน Chrome ตัวที่ pdfGenerator ถือไว้
   └─ GET …/preview/:id/model.step          ← writers/step.ts
   │
   ▼  [สร้างลิงก์ให้ลูกค้า] — เฟส 2 · สิทธิ์ quote.share_drawing
product_drawings + ไฟล์ตรึงใน /app/drawings/<id>/ (อายุ 7 วัน · ห้ามอยู่ใต้ data/ §6.2)  →  APP_URL/d/<uuid>
   │
   ▼
หน้าเว็บลูกค้า (TypeScript + three.js · ไม่มี React §4.6) — หมุน/ซูม · ภาพแบบ 2 มิติ · โหลด PDF / STEP / PNG · ไม่มีราคา
```

**ไม่มีส่วนใดอยู่ในเส้นทาง LINE webhook** — STEP ตัวใหญ่ใช้ 1.9–3.5 วิ และ Puppeteer ไม่ควรแย่งงบ 48 วิของบอท

### 4.5 กติกา "ส่งให้ลูกค้าได้หรือไม่" — อยู่ที่ `checks.ts` ที่เดียว

ส่งได้เมื่อ **ครบทุกข้อ**:
1. โมดูลมีแบบของตระกูลนี้ และ `fromReading` แปลงช่องที่กำหนดรูปทรงได้ครบ
2. **ความหลวมของผลอ่านรหัส — สามชั้น** (ลงโค้ดแล้ว `checks.ts` · **เจ้าของเคาะ 2026-10-06**):
   - **วาดไม่ได้** — ช่องที่ **กำหนดรูปทรง** มี issue / ไม่ได้เขียน · ท่อนหลังเลขรุ่น · **แกนหัก** (`bend:*` จาก `cfg.options`/`addons`)
     ⇒ ไม่วาดค่าที่เดา และปิดปุ่ม PDF/PNG/STEP (เจ้าของข้อ 3: *"ตอนระบบเดาบางช่อง ให้ปิดปุ่ม"*)
   - **ส่งไม่ได้ ไม่มีทางยืนยันข้าม** — issue/ไม่บอกของช่องอื่น (วัสดุ/Element/Ground/ความยาวสาย) · `BhForm.loose` · สิ่งบวกเพิ่ม ·
     BH ที่มีรูเจาะที่ยังไม่ได้กรอกตำแหน่ง (§2.6 A14) · กำลังไฟนอกรูปแบบ · ไม่รับผลิต · ~~คิดราคาไม่ได้~~ (ถอด 2026-10-06 ค่ำ — แบบไม่ขึ้นกับราคา §2.6)
   - **ท่อนท้ายที่ทับตำแหน่งช่องรูปทรงที่เป็น None = วาดไม่ได้** (QA รอบ 2 · 2026-10-06): TS_-11 สาย `''` + ท้ายรหัสขึ้นต้นด้วยตัวอักษรที่ไม่ใช่
     `S###` (`+3M-CU` · `+1MF` · `+TU` — ตัวอ่านรหัสโยนชนิดสายที่ไม่รู้จักไปไว้ใน `tail` แล้วปล่อยสาย `''`) · BH ขั้วไฟ `''` + ท่อนที่ขึ้นต้นด้วย
     PL/N/T/1–3+ตัวอักษร (`-PL(HPT)` · `3P`) ⇒ ไม่รู้ค่าช่องนั้น ไม่ใช่ "ของที่แบบไม่ได้วาด" (ข้อ 3 ของเจ้าของ: ระบบเดาช่องรูปทรง = ปิดเสมอ)
   - **ท่อนท้ายที่เป็นค่าของช่องอื่นที่ปล่อยว่าง = ส่งไม่ได้** (รอบแก้ 3 · 2026-10-06 · หลักเดียวกัน: ระบบเดา ไม่ว่าช่องรูปทรงหรือไม่ — ช่องรูปทรง = วาดไม่ได้ ·
     ช่องอื่น = ส่งไม่ได้ เพราะตารางสเปกจะพิมพ์ผิด): TS Ground/วัสดุ/Element/ความยาวสาย ว่างแต่ท้ายรหัสมีค่าของมัน (`+1.5MT-U`) · BH ตัวเลขที่สองต่อจาก
     แรงดัน/กำลังไฟ (`210-420`) · ความยาวสายที่ไม่ตรงกับขั้วไฟแบบออกสาย (`-1.5` ขณะที่ขั้วไฟ `''` = สาย 30 cm) · คำถามตัดสิน: *"ถ้าส่ง ตารางสเปกหรือภาพจะบอกอะไรผิดไหม"*
   - **ท่อนตัวอักษรต่อท้ายสาย TS_-11 ที่ระบุแล้ว = ส่งไม่ได้ ยกเว้นท่อนใน `CABLE_END_CONFIRMABLE`** (รอบแก้ 4 · 2026-10-06) — ท่อนอยู่ตรงปลายสาย
     ซึ่งแบบวาดจริง (ลวดแยก + หางปลา) ถ้าเป็นหัวต่อ ภาพจะผิด · **`MP` / `SP` (7 รหัส) = ชั้นยืนยัน** — ความหมายยังไม่มีใครรู้ เจ้าของเคาะ
     *"วาดเท่าที่มีตามรูปและแบบไปก่อน"* ⇒ วาดปลายสายตามแคตตาล็อก ผู้เสนอราคาติ๊กยืนยันท่อนนี้ · ด่านมีรายการคู่กัน `CABLE_END_OK`
   - **ส่งได้หลังผู้เสนอราคายืนยัน** — ส่วนท้ายที่ระบบไม่รู้จัก **และไม่ใช่ค่าของช่องไหนเลย** (`CONFIRMABLE`: TS ท้ายรหัส · `S###` · ท่อนนอกแคตตาล็อกของ BH เช่น `(HPT)` · `LH`/`RH` · ความยาวสายที่ตรงกับขั้วไฟ)
     เจ้าของ: *"ส่งได้ เพราะผู้เสนอราคาเป็นคนยืนยันเอง"* ⇒ `judge()` คืน `confirm[]` (ท่อนที่แบบไม่ได้วาด) · `canSend` = ไม่มีตัวปิด ·
     **หน้าจอเฟส 1 ต้องบังคับติ๊กเมื่อ `confirm` ไม่ว่าง** พร้อมโชว์ท่อนเหล่านั้น
   - "วิธีเขียนคนละแบบ" (`cableNoDash` · `clUnit` · `written` ที่ไม่มี issue · `WRITING_STYLE`) ไม่อยู่ชั้นไหน — เจ้าของยืนยันแนวนี้ 2026-10-06
   - ข้อความบนจอ (เฟส 1) บอกเหตุผลรายข้อ + *"กรอกผ่านช่องตามแคตตาล็อกแล้วคิดราคาใหม่"* (กดครั้งเดียวก็ได้รหัสที่ตรงแคตตาล็อก)
3. หน้าคำนวณราคาไม่ได้ตอบ `notManufacturable` ("ไม่รับผลิต" = ข้อห้ามการผลิตในชีต ไม่ใช่เรื่องราคา) · **คิดราคาไม่ได้ / ยังไม่มีราคา ไม่ปิด** (เจ้าของ 2026-10-06 ค่ำ)

## 6. ทรัพยากร และความปลอดภัย

### 6.1 หน้าเว็บ 3 มิติกินทรัพยากรแค่ไหน — คำตอบของคำถามหัวหน้า (§9 ข้อ 3 · วัด 2026-10-06)

| | ครั้งเดียวตอนกด "สร้างลิงก์" | ทุกครั้งที่ลูกค้าเปิด |
| --- | --- | --- |
| CPU เซิร์ฟเวอร์ | สร้างโมเดล + STEP ≤ 3.5 วิ (รุ่นหัวกะโหลก) · ทั่วไป ≤ 1.1 วิ · + Puppeteer พิมพ์ PDF/PNG (วัดเฟส 0) | **≈ 0** — อ่านไฟล์ที่ตรึงไว้ส่งออก ไม่รันตัววาด |
| ส่งข้อมูลออก | — | GLB บีบอัด ≤ 2.6 MB (ทั่วไป ≤ 0.14 MB) + ตัวดู three.js 0.16 MB ครั้งแรก (วัดแล้ว §4.6 · เบราว์เซอร์จำไว้) · PDF/PNG/STEP เฉพาะเมื่อกดโหลด |
| ที่เก็บ | ต่อหนึ่งลิงก์ ≤ ~16.5 MB (STEP 12.9 + GLB 2.6 + PDF/PNG) · ทั่วไป ≤ ~2 MB · หมดอายุ 7 วันแล้วลบ | — |
| การวาดภาพ 3 มิติ | — | **บนมือถือของลูกค้า** ไม่ใช่เซิร์ฟเวอร์ |

ประมาณปริมาณ: ใบสั่งขายใน Odoo ที่บรรทัดแรกเป็น BH/TS **18.8 ใบ/วัน** (60 วันถึง 2026-10-06 · นับเฉพาะบรรทัดแรก จึงเป็นขั้นต่ำ)
⇒ สมมติกรณีหนัก 40 ลิงก์/วัน · ลิงก์ละ 5 ครั้ง · ทุกตัวเป็นรุ่นหัวกะโหลก:
- ส่งข้อมูลออก ≤ ~560 MB/วัน ผ่าน Cloudflare Tunnel · ส่วนผสมจริงน่าจะต่ำกว่านี้มาก (รุ่นทั่วไปเล็กกว่า 18 เท่า)
- ที่เก็บ 7 วัน ≤ 280 ลิงก์ × 16.5 MB ≈ 4.6 GB · ดิสก์ว่าง 171 GB (ใช้ 27% · วัด 2026-10-06)

**ข้อสรุป: คุ้ม เก็บหน้าเว็บ 3 มิติไว้** — ต้นทุนที่เซิร์ฟเวอร์จ่ายเกิดตอนสร้างลิงก์ครั้งเดียว ไม่โตตามจำนวนคนเปิด ·
ของที่หนักที่สุดคือ STEP ซึ่งต้องมีอยู่แล้วตามคำตอบข้อ 1 · และ §2.5 ข้อ 5 (หัวกะโหลกหยาบลง) จะลดทั้ง GLB และ STEP
ของรุ่นหัวกะโหลกลงอีกหลายเท่า · ถ้าวันหนึ่งพบว่าไม่คุ้มจริง การตัดหน้าเว็บทิ้งเหลือแค่ปุ่มโหลดไฟล์ทำได้โดยไม่กระทบส่วนอื่น

### 6.2 ความปลอดภัย / ข้อมูล
- ลิงก์ลูกค้า = UUID เดาไม่ได้ · หมดอายุ 7 วัน · ยกเลิกเองได้จากการ์ดแอดมิน
- เส้นสาธารณะ **อ่านอย่างเดียวจากไฟล์ที่ตรึงไว้** — ไม่รับรหัสจากลูกค้า ไม่รันตัววาด ⇒ ลูกค้ายิงซ้ำกี่ครั้งก็ไม่กิน CPU ·
  จำกัดความถี่ต่อ IP แบบ `config/loginRateLimit.ts` กันการไล่ยิงทั้งก้อน
- ไฟล์เก็บแบบบีบอัดแล้ว ส่งด้วย `Content-Encoding: gzip` · ไม่ให้ Cloudflare cache (ไม่งั้นลิงก์ที่ยกเลิกแล้วยังเปิดได้)
- เส้นแอดมินที่รันตัววาด: จำกัดความยาวรหัส 200 ตัวอักษรเหมือนหน้าคำนวณราคา · แคชผลต่อ `(drawing_version, code, picks)` ·
  **งานวาด (STEP/PDF/PNG) เข้าคิวทีละงาน** — ภาพ 3 มิติใน Chrome ใช้ ~1.7–2.0 วิ · พีคหน่วยความจำ ~0.4 GB (devops 2026-10-06)
- **ห้ามเก็บไฟล์แบบใต้ `data/`** — `index.ts` เสิร์ฟ `/data` ด้วย `express.static` แบบไม่มี auth ⇒ ไฟล์ใต้นั้นเปิดได้ตรง ๆ
  ข้ามอายุ 7 วัน · การยกเลิกลิงก์ · การจำกัดความถี่ทั้งหมด ⇒ ใช้ `/app/drawings` (volume ของตัวเอง) แล้วส่งผ่าน route ที่ตรวจแถวเท่านั้น
- ทุก route `/api/admin/*` มีด่าน `requireCapability` ที่ `index.ts` (ด่านข้อ 12 ของ `diag:role-permissions` อ่านซอร์ส)

## 10. สิ่งที่ยังไม่รู้ — ห้ามเดา

- **ฮีตเตอร์ 14 รุ่นในสมุดราคาแบบ "ยังไม่มีราคา"** (§2.6 ข3 · เคาะแล้ว) — ช่องตามแคตตาล็อกของฮีตเตอร์ยังไม่มีใครตรวจกับรหัสจริงใน Odoo
  (ตัวอ่านของ Appsale อ่านได้แค่ 60.8% ทั้งระบบ) ⇒ วัดรหัสจริงก่อนออกแบบตาราง · การเขียนรุ่นลงฐานสมุดราคา = เขียนฐานจริง ต้องรอเจ้าของสั่งเวลา
- **TS_-11L:** ตาราง TS_-11 ของหน้าคำนวณราคาไม่มีช่อง L2 ⇒ ต้องเพิ่มตาราง/ช่องก่อน · วัดก่อนว่ารหัสจริง 331 ตัวเขียน L2 ไว้กี่ตัว
- **รูเจาะกรอกตำแหน่งเอง (A14 · เคาะแล้ว):** ตำแหน่งไม่อยู่ในรหัส ⇒ PDF/หน้าลูกค้าบอกว่าตำแหน่งรูมาจากผู้เสนอราคาไหม (ถามใน mockup) · หน้าจอต้องผ่าน mockup ก่อน
- ขนาดไฟล์ PDF/PNG ของกระดาษแบบ — วัดเมื่อมีแม่แบบจริง (เฟส 1 · เวลาวัดแล้ว: 3 มิติ ~1.7–2.0 วิ · 2D ~0.3 วิ ในกล่อง prod 2026-10-06)
- ช่องตามแคตตาล็อกของหน้าคำนวณราคามีข้อมูลพอวาดทุกตระกูลไหม (เช่น ชนิดหัว/ข้อต่อที่ราคาไม่สนใจแต่รูปทรงต้องรู้) —
  `diag:drawing-coverage` เฟส 0–1 จะบอกเป็นรายช่อง · ช่องที่ขาด = เพิ่มในผลอ่านของหน้าคำนวณราคา **ไม่ใช่**ให้โมดูลแบบอ่านรหัสเอง
- หัวกะโหลกหยาบลงได้แค่ไหนก่อนที่ตาเห็นต่าง — เครื่องนี้ไม่มี cadquery (วัด 2026-10-06) ⇒ ลดจาก mesh เดิมใน Node
  หรือ tessellate ใหม่จากไฟล์ CAD ต้นทางบนเครื่องที่มี cadquery · เลือกในเฟส 1 จากภาพก่อน/หลัง
- ความลื่นของตัวดูบนมือถือรุ่นล่าง/ใน in-app browser ของ LINE (รุ่นหัวกะโหลก 151k สามเหลี่ยมก่อนหยาบลง) — เฟส 2
- ลูกค้าเปิด STEP ผิวเหลี่ยมในโปรแกรมของเขาได้จริงไหม — ขอให้เซลส์ลองกับลูกค้าจริง 2–3 รายในเฟส 1
- ลิงก์อายุ 7 วันกับใบเสนอราคาที่อายุยาวกว่า (เฟส 3) — ไม่มี QR บนใบแล้ว (§5.3) จึงเหลือแค่ปุ่มในหน้าดูใบ/Flex ที่ชี้ลิงก์ที่หมดอายุได้ ·
  ที่แนะนำ: ปุ่มบอกว่าหมดอายุแล้ว + ให้เซลส์กดสร้างใหม่ (ไฟล์สร้างจาก `spec` เดิม)
- การ์ดควรอยู่หน้าไหนอีกนอกจากหน้าคำนวณราคา (หน้าขอใบเสนอราคา?) — ตามที่หัวหน้าเห็นจากการใช้เฟส 1
- **ความหมายของ `-MP` / `-SP` ต่อท้ายสาย TS_-11** (7 รหัส · เช่น `TSK-11P 5x80+1M-T-MP`) — เจ้าของก็ยังไม่ทราบ (2026-10-06) · ตอนนี้วาดปลายสายตามแคตตาล็อก
  + ผู้เสนอราคายืนยัน · ถ้าฝ่ายผลิตบอกว่าเป็นหัวต่อปลายสาย = ลบออกจาก `CABLE_END_CONFIRMABLE` + `CABLE_END_OK` (กลับเป็นส่งไม่ได้) หรือวาดหัวต่อ
- **`LH` / `RH` ท้ายรหัส BH-01C** (`BH-01C-90x198-240-1600W-PL-1.5-LH` · QA 2026-10-06: รูปทรงไม่เปลี่ยน) — ตัว `LH`/`RH` เองอยู่ชั้น "ส่งได้หลังยืนยัน"
  (สองรหัสจริงวันนี้ส่งไม่ได้เพราะ `1.5` ไม่ตรงกับขั้วไฟ `''` = สาย 30 cm)
  · ควรแสดงในกระดาษแบบเฟส 1 (ช่องรายละเอียดสินค้า) ความหมายยังไม่ยืนยันกับฝ่ายผลิต
- **BH ที่มี `T` แต่ไม่ได้เลือก 10A/30A ได้ "ส่งได้" 11 รหัส** (QA 2026-10-06) ทั้งที่ราคายังไม่รวมท่อนนี้ — `judge()` ยังไม่อ่าน
  `ParsedCode.warnings` / ท่อน `choose` · ตัดสินที่ §4.5 ข้อ 3 ในเฟส 1 (ราคาไม่ครบแบบนี้ปิดการส่งไหม)
