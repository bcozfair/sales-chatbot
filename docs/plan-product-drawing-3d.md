## 0. สรุปสำหรับคนอ่านหน้าเดียว

- **สร้างเป็นโมดูลของ chatbot เอง** (`services/drawing/`) โดยยกโครงสร้างและเรขาคณิตจาก `heater-app` ของ Appsale
  มาเป็น TypeScript แล้วปรับปรุง (§2.5) · หลังพอร์ตเสร็จ **chatbot เป็นเจ้าของโค้ดชุดนี้** ไม่ดึงของใหม่จาก Appsale อีก
- **การปรับปรุงที่สำคัญที่สุด: โมดูลแบบไม่มีตัวอ่านรหัสของตัวเอง** — มันรับ "ผลการอ่านรหัส" จากหน้าคำนวณราคา
  ซึ่งเป็นการอ่านครั้งเดียวกับที่ใช้คิดราคา ⇒ **ราคากับแบบเป็นของชิ้นเดียวกันโดยโครงสร้าง** ความเสี่ยงอันดับหนึ่งของ
  ฉบับที่ 1 (Appsale อ่านรหัสจริงได้ 60.8% · BH-02 อ่านได้ 0/494) หายไปตั้งแต่ต้นเหตุ
- **ลูกค้าได้ลิงก์หน้าเว็บหมุนดูแบบ 3 มิติ + ปุ่มโหลด PDF · STEP · PNG** · ลิงก์อายุ 7 วัน ยกเลิกเองได้ ·
  เซลส์คัดลอกลิงก์ไปส่งเอง (ไม่มี LINE push)
- **หน้าเว็บ 3 มิติไม่กินทรัพยากรเซิร์ฟเวอร์** (§6.1 · วัด 2026-10-06): เซิร์ฟเวอร์สร้างไฟล์ **ครั้งเดียว** ตอนกดสร้างลิงก์ ·
  ลูกค้าเปิดกี่ครั้งเซิร์ฟเวอร์ก็แค่ส่งไฟล์ที่เก็บไว้ ส่วนการวาดภาพ 3 มิติทำบนมือถือของลูกค้า · ไฟล์ 3 มิติที่ใหญ่ที่สุด
  2.6 MB (ทั่วไป ≤ 0.14 MB) ⇒ **คุ้ม เก็บหน้าเว็บ 3 มิติไว้** · ของที่หนักจริงคือไฟล์ STEP (สูงสุด 12.9 MB หลังบีบอัด)
  ซึ่งลูกค้าได้อยู่แล้วไม่ว่าจะมีหน้าเว็บหรือไม่
- **ภาพ 3 มิติวาดด้วย three.js ตัวดูชุดเดียว** ใช้ทั้งในการ์ดแอดมิน (React) หน้าลูกค้า และภาพใน PDF/PNG ⇒ เซลส์เห็นภาพไหน
  ลูกค้าก็ได้ภาพนั้น · ความสมจริงมาจากวัสดุและแสง ไม่ได้มาจาก React (§4.6)
- **PDF ของแบบเป็นเอกสารของตัวเอง ไม่แตะ PDF ใบเสนอราคา** — แม่แบบยกจากกระดาษแบบของ Appsale (§5.4)
- **เฟส:** 0 ฐานของโมดูล + พอร์ตรุ่นแรก → 1 ใช้ภายในในหน้าคำนวณราคา → 2 ลิงก์ให้ลูกค้า → 3 ผูกกับใบเสนอราคา

## 1. เป้าหมาย และสิ่งที่ไม่ใช่เป้าหมาย

**เป้าหมาย:** ผู้เสนอราคาพิมพ์/กรอกรหัสสินค้าสั่งทำในหน้า "คำนวณราคา" → ได้ราคา (มีอยู่แล้ว) **และ**
ได้แบบ 3 มิติของชิ้นนั้นในจอเดียวกัน → กดปุ่มเดียวได้ลิงก์ส่งลูกค้า ลูกค้าเปิดบนมือถือแล้วหมุนดูได้ทันที

**ไม่ใช่เป้าหมาย (อย่างน้อยเฟส 1–3):**
- ไม่ใช่แบบผลิต — เป็น **แบบอ้างอิงตามแคตตาล็อก** (ยึดข้อความกำกับเดียวกับ Appsale:
  *"Coloured catalogue reference; illustrative fittings; faceted geometry"*)
- ไม่ใช่ STEP แบบผิวโค้งจริง (analytic B-rep) — ผิวเหลี่ยม (faceted) พอสำหรับเฟส 1–3 (หัวหน้าเคาะ §9 ข้อ 5)
- ไม่วาดรุ่นที่หน้าคำนวณราคายังคิดราคาไม่ได้ — ฮีตเตอร์ CH/IMH/FH/TH/IH/HAH (14 รุ่นที่ Appsale มี) รอจนสมุดราคามีรุ่นนั้น
- ไม่เชื่อมต่อ Appsale ขณะรัน — ไม่เรียก API ไม่อ่านไฟล์จากรีโปนั้น (รีโป Appsale ใช้แค่ในด่านช่วงพอร์ต §7)
- ไม่ส่งอะไรผ่าน LINE push (ห้ามตลอดไป · เหตุผลเชิงเงิน ดู `CLAUDE.md`)

หลักการที่ Appsale ยึด และโมดูลของเรายกมาทั้งหมด:
- **ตัวเลขตรวจสเปกต้องมาจากแคตตาล็อก ห้ามเดา** ค่าที่ไม่ระบุ = เตือนให้ยืนยันกับฝ่ายผลิต

- **ไม่มีราคาในตัววาดแบบ** — ราคาอยู่ที่หน้าคำนวณราคา
- **โมเดลชุดเดียว** สร้างทั้งภาพ 3 มิติ ภาพฉาย 2 มิติ และไฟล์ STEP ⇒ สามอย่างไม่มีวันขัดกันเอง
- ชิ้นส่วนประกอบบางชิ้น (หัวกะโหลก · ข้อต่อ) เป็น "รูปทรงอ้างอิง" ถอดจาก CAD ผู้ผลิต — ส่วนแกน/ความยาว/สายเป็นพารามิเตอร์ตามรหัส

### 4.3 ทิศการพึ่งพา — ฉีดตัวคิดราคาเข้ามา ไม่ import

```
index.ts  ──import──▶  routes/pricingLab.ts  (export quoteForCode — แกนของ pricingQuoteHandler)
   │
   └─ app.use(..., createDrawingRouter({ quote: quoteForCode }))   ← จุดเดียวที่สองโมดูลเจอกัน
                         │
                         ▼
                 services/drawing/   (รู้จักแค่ type `QuoteFn` ที่ประกาศเอง)
```

- `services/drawing/` **ไม่ import** `services/pricingLab/` หรือ `routes/pricingLab.ts` และกลับกันก็ไม่ — แบบเดียวกับที่
  "เพิ่มสินค้าใหม่" ใช้ `pricingQuoteHandler` ผ่าน `index.ts` (`docs/plan-local-products.md` §13.5) และแบบเดียวกับ
  `chatChannel.ts` ที่ฉีดตัวตอบกลับเข้า `handleEvent`
- TypeScript ตรวจรูปของ `quoteForCode` กับ `QuoteFn` ให้ที่บรรทัด mount ใน `index.ts` ⇒ หน้าคำนวณราคาเปลี่ยนชื่อช่อง
  แล้วลืมโมดูลแบบ = **typecheck ล้ม** ไม่ใช่แบบเพี้ยนเงียบ ๆ
- งานที่ต้องแตะ pricingLab มีชิ้นเดียว: แยกแกนของ `pricingQuoteHandler` ออกเป็น `quoteForCode()` แล้วให้ handler เรียกต่อ ·
  บรรทัด `pricingLabRouter.post('/quote', pricingQuoteHandler);` ต้องคงเดิมทุกตัวอักษร (`localProductsSmoke` ข้อ 16 อ่านซอร์สบรรทัดนี้)
- ถอดโมดูลแบบ = ลบตามตาราง §4.2 + `DROP TABLE product_drawings` + บรรทัด mount ใน `index.ts` · ถอด pricingLab =
  บรรทัด mount ของโมดูลแบบหายไปด้วย (ไม่มีตัวอ่านรหัส = วาดไม่ได้) ซึ่งถูกต้อง เพราะแบบที่ไม่มีราคาคู่กันไม่ใช่เป้าหมาย
- ไม่ import `quotationService.ts` / `utils/pricing.ts` / `services/rules/` ในเฟส 1–2

  ปรับรูปทรงทีหลัง (หลักเดียวกับ snapshot ของรายการในใบเสนอราคา)

  สร้างใหม่เงียบ ๆ · ไม่ตรง = หน้าลูกค้าบอกว่าเป็นฉบับสร้างใหม่

### 4.5 กติกา "ส่งให้ลูกค้าได้หรือไม่" — อยู่ที่ `checks.ts` ที่เดียว

ส่งได้เมื่อ **ครบทุกข้อ**:
1. โมดูลมีแบบของตระกูลนี้ และ `fromReading` แปลงช่องที่กำหนดรูปทรงได้ครบ
2. **ช่องที่กำหนดรูปทรงไม่ได้มาจากการเดา** — ผลอ่านแบบหลวม (`tsForm.issues` · `BhForm.loose`) บนช่องเหล่านั้น =
   ดูแบบในจอได้แต่ส่งไม่ได้ บอกว่า *"ระบบอ่านบางช่องจากรหัสแบบเดา — กรอกผ่านช่องตามแคตตาล็อกแล้วคิดราคาใหม่"*
   (กดครั้งเดียวก็ได้รหัสที่ตรงแคตตาล็อก)
3. หน้าคำนวณราคาไม่ได้ตอบ `notManufacturable` ("ไม่รับผลิต")
4. ตัวตรวจสเปกของแบบไม่มีข้อ "ผลิตไม่ได้" (ข้อ "เตือน" แสดงให้คนส่งเห็น แต่ไม่ปิดปุ่ม)

"รหัสที่วาด = รหัสที่คิดราคา" **ไม่ต้องเป็นข้อตรวจอีกแล้ว** — สองอย่างมาจากการเรียก `quote()` ครั้งเดียวกัน (§4.3)

ทุกข้อที่ไม่ผ่านบอกเหตุผลเป็นภาษาคน (ยกข้อความไทยของ Appsale มา) · **ไม่มีปุ่มข้ามด่านในเฟส 1–2** (หัวหน้าเคาะ §9 ข้อ 2) —
ถ้าวันหน้าต้องการช่องทางข้าม ให้เป็นการอนุมัติแบบคิวอนุมัติราคา ไม่ใช่ติ๊กเอง ·
`quoteOnRequest` ("ต้องขอราคา") **ไม่ปิด** การส่งแบบ — ราคายังไม่ครบไม่ได้แปลว่ารูปทรงผิด

⚠️ ตัวตรวจของ Appsale ปฏิเสธรหัสที่มีอยู่จริงใน Odoo 2,775 ตัว (§2.2) ⇒ ก่อนเฟส 2 ต้องมีรายงานจากด่าน coverage ว่าข้อ 4
ปิดปุ่มกับรหัสจริงกี่ตัว แยกตามข้อตรวจ ให้ฝ่ายผลิตชี้ว่าข้อไหนเป็นข้อห้ามจริง ข้อไหนลดเป็นเตือน · ข้อที่ฝ่ายผลิตยืนยันว่าเป็น
ข้อห้ามจริง ควรย้ายไปเป็นข้อห้ามในสมุดราคา (ที่เดียวกับ "ไม่รับผลิต") ในระยะยาว

**ความสวย/สมจริงไม่ได้มาจาก React** — ไม่ว่าจะเขียนด้วย React (react-three-fiber) หรือไม่ คนวาดภาพคือ three.js

### 6.2 ความปลอดภัย / ข้อมูล
- ลิงก์ลูกค้า = UUID เดาไม่ได้ · หมดอายุ 7 วัน · ยกเลิกเองได้จากการ์ดแอดมิน
- เส้นสาธารณะ **อ่านอย่างเดียวจากไฟล์ที่ตรึงไว้** — ไม่รับรหัสจากลูกค้า ไม่รันตัววาด ⇒ ลูกค้ายิงซ้ำกี่ครั้งก็ไม่กิน CPU ·
  จำกัดความถี่ต่อ IP แบบ `config/loginRateLimit.ts` กันการไล่ยิงทั้งก้อน
- ไฟล์เก็บแบบบีบอัดแล้ว ส่งด้วย `Content-Encoding: gzip` · ไม่ให้ Cloudflare cache (ไม่งั้นลิงก์ที่ยกเลิกแล้วยังเปิดได้)
- เส้นแอดมินที่รันตัววาด: จำกัดความยาวรหัส 200 ตัวอักษรเหมือนหน้าคำนวณราคา · แคชผลต่อ `(drawing_version, code, picks)` ·
  งานสร้าง STEP/PDF ตัวใหญ่เข้าคิวทีละงาน
- ทุก route `/api/admin/*` มีด่าน `requireCapability` ที่ `index.ts` (ด่านข้อ 12 ของ `diag:role-permissions` อ่านซอร์ส)

## 10. สิ่งที่ยังไม่รู้ — ห้ามเดา

- เวลา Puppeteer พิมพ์กระดาษแบบเป็น PDF/PNG และขนาดไฟล์สองตัวนั้น — วัดเฟส 0
- ช่องตามแคตตาล็อกของหน้าคำนวณราคามีข้อมูลพอวาดทุกตระกูลไหม (เช่น ชนิดหัว/ข้อต่อที่ราคาไม่สนใจแต่รูปทรงต้องรู้) —
  `diag:drawing-coverage` เฟส 0–1 จะบอกเป็นรายช่อง · ช่องที่ขาด = เพิ่มในผลอ่านของหน้าคำนวณราคา **ไม่ใช่**ให้โมดูลแบบอ่านรหัสเอง
- หัวกะโหลกหยาบลงได้แค่ไหนก่อนที่ตาเห็นต่าง — เครื่องนี้ไม่มี cadquery (วัด 2026-10-06) ⇒ ลดจาก mesh เดิมใน Node
  หรือ tessellate ใหม่จากไฟล์ CAD ต้นทางบนเครื่องที่มี cadquery · เลือกในเฟส 1 จากภาพก่อน/หลัง
- ความลื่นของตัวดูบนมือถือรุ่นล่าง/ใน in-app browser ของ LINE (รุ่นหัวกะโหลก 151k สามเหลี่ยมก่อนหยาบลง) — เฟส 2
- **WebGL ใน Chrome ของคอนเทนเนอร์ prod** — ทดสอบแล้วบนโฮสต์ (WebGL 2 · SwiftShader · 2026-10-06) แต่ยังไม่ได้ลองในกล่อง
  `primus-chatbot-app-1` (ไม่ได้รันอะไรในกล่อง prod) ⇒ เฟส 0 ต้องยืนยันก่อนพึ่งทาง "ถ่ายภาพจากตัวดู" · ถ้าใช้ไม่ได้ ทางถอยคือ
  พอร์ตตัววาดภาพลงเงาแบบ painter's algorithm ของ Appsale (`cad-camera.js`) มาใช้กับกระดาษแบบ
