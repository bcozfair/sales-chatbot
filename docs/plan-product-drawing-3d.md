# แผน: แบบ 3 มิติของสินค้าสั่งทำ — คิดราคาแล้วส่งแบบให้ลูกค้าได้ทันที

> สถานะ: **แผน · ยังไม่มีโค้ด** (เขียน 2026-10-06) · รอหัวหน้า/เจ้าของเคาะ §9 ก่อนเริ่มเฟส 1
> ที่มา: คำสั่งหัวหน้า 2026-10-05 — *"วางแผนและออกแบบโครงสร้างสำหรับ module สร้างแบบจากไฟล์ STEP
> จาก model สินค้าตามรูปในแคตตาล็อก ให้ไปศึกษา module นี้จาก Appsale แล้วนำมาวิเคราะห์ก่อนออกแบบ ·
> จุดประสงค์คือต้องการให้ผู้เสนอราคาคิดราคาสินค้าใหม่แล้วส่งภาพแบบ 3D ให้ลูกค้าดูได้เลย"*

## 0. สรุปสำหรับคนอ่านหน้าเดียว

- **ไม่ต้องสร้างตัววาดแบบใหม่** — Appsale มีอยู่แล้วและใช้งานจริง (หน้า `/heater-design`): พิมพ์รหัส →
  แตกเป็นพารามิเตอร์ → ตรวจสเปกตามแคตตาล็อก → วาด 2D/3D → ส่งออก STEP มีสี · **33 รุ่น**
  (ฮีตเตอร์ 18 · หัววัดอุณหภูมิ 15) · และสเปกของ Appsale เองเขียน "เฟส 3 — เชื่อมกับ chatbot เสนอราคา" ไว้แล้ว
- **ตัววาดรันบนเซิร์ฟเวอร์ Node ได้เลย** (ทดลอง 2026-10-05): อ่านรหัส/ตรวจสเปก/สร้าง STEP ได้ไม่ต้องมีเบราว์เซอร์
  ⇒ chatbot เรียกใช้ "ของตัวเดียวกับ Appsale" ได้ ไม่ต้องลอกเรขาคณิตมาเขียนใหม่
- **ความเสี่ยงอันดับหนึ่งไม่ใช่การวาด แต่คือ "ราคาคิดจากขนาดหนึ่ง แบบวาดอีกขนาด"** — chatbot กับ Appsale
  มีตัวอ่านรหัสคนละตัว และวัดกับรหัสจริงในฐานแล้ว **อ่านได้ตรงกันไม่ครบ** (§2.2) ⇒ แบบจะส่งให้ลูกค้าได้
  ก็ต่อเมื่อระบบพิสูจน์ได้ว่าแบบกับราคาเป็นของชิ้นเดียวกัน
- **ข้อเสนอ:** ใช้ตัววาดของ Appsale แบบปักเวอร์ชัน (chatbot ห้ามแก้ · แก้ที่ Appsale แล้วดึงใหม่) ·
  การ์ด "แบบ 3 มิติ" ในหน้าคำนวณราคา · ลูกค้าได้ **ลิงก์หน้าเว็บหมุนดูแบบ 3 มิติ + โหลด PDF แบบ/STEP** ·
  ไม่ผ่าน LINE push (เซลส์คัดลอกลิงก์ไปส่งเอง)
- **เฟส:** 0 วัด+เคาะ → 1 ใช้ภายใน (ดูแบบ/โหลดไฟล์ในหน้าคำนวณราคา) → 2 ลิงก์ให้ลูกค้า → 3 ผูกกับใบเสนอราคา

## 1. เป้าหมาย และสิ่งที่ไม่ใช่เป้าหมาย

**เป้าหมาย:** ผู้เสนอราคาพิมพ์/กรอกรหัสสินค้าสั่งทำในหน้า "คำนวณราคา" → ได้ราคา (มีอยู่แล้ว) **และ**
ได้แบบ 3 มิติของชิ้นนั้นในจอเดียวกัน → กดปุ่มเดียวได้ลิงก์ส่งลูกค้า ลูกค้าเปิดบนมือถือแล้วหมุนดูได้ทันที

**ไม่ใช่เป้าหมาย (อย่างน้อยเฟส 1–3):**
- ไม่ใช่แบบผลิต — เป็น **แบบอ้างอิงตามแคตตาล็อก** (Appsale เขียนกำกับไว้ในหัวไฟล์ STEP อยู่แล้ว:
  *"Coloured catalogue reference; illustrative fittings; faceted geometry"*)
- ไม่ใช่ STEP แบบผิวโค้งจริง (analytic B-rep) — ของที่มีเป็นผิวเหลี่ยม (faceted) §2.4
- ไม่วาดรุ่นที่ Appsale ยังไม่มี (เช่น TS_-04 · TS_-09 · TS_-14) — ต้องเพิ่มที่ Appsale ก่อน
- ไม่ส่งอะไรผ่าน LINE push (ห้ามตลอดไป · เหตุผลเชิงเงิน ดู `CLAUDE.md`)

## 2. ผลการศึกษา module ใน Appsale

### 2.1 มันคืออะไร อยู่ที่ไหน

| ส่วน | ที่อยู่ (รีโป `/home/app_sales/Appsale`) | หมายเหตุ |
| --- | --- | --- |
| ตัวแอปวาดแบบ | `frontend/public/heater-app/` | static ES modules ไม่มี build · ~9,500 บรรทัด JS + **~24 MB mesh** ใน `src/assets/` |
| ทะเบียนรุ่น | `src/registry.js` | `PRODUCTS` 33 ตัว · `canonical()` · `findProduct()` |
| ไฟล์ต่อรุ่น | `src/products/<รุ่น>.js` | แต่ละรุ่นมี `parse` · `build` · `validate` · `modelParts` · `exportStep` · `views` (+ `defaults`) |
| engine กลาง | `src/engine/` | `code.js` (normalize) · `validate.js` · `step.js` (เขียน STEP AP214 มีสี) · `solids.js` · `sheet.js` (กระดาษแบบ 980×640) · `cad-camera.js` |
| หน้า React | `frontend/src/pages/HeaterDesign/` | แค่เปลือก — เปิดแอปผ่าน `<iframe>` ด้วย `?family=heater|sensor` |
| สเปก/ประวัติ | `docs/HEATER-DRAWING-APP-SPEC.md` (452 บรรทัด) + `public/heater-app/reference/<รุ่น>.md` | ทุกตัวเลขต้องอ้างแคตตาล็อก · ค่าที่ derive เองถูกบันทึกแยก |
| สคริปต์ส่งออก | `scripts/export-{ts,bh,heater}-step.mjs` | **import `registry.js` ตรง ๆ ใน Node** — หลักฐานว่า engine ไม่ผูกกับเบราว์เซอร์ |
| ดูไฟล์ CAD | `frontend/src/pages/CadViewer/` | ตัวเปิด STEP/IGES/DWG ที่อัปโหลด (three.js + occt-import-js) — **คนละเรื่อง** กับงานนี้ ใช้อ้างอิงวิธีแสดง 3 มิติได้ |

หลักการที่ Appsale ยึด และงานนี้ต้องยึดตาม:
- **ตัวเลขตรวจสเปกต้องมาจากแคตตาล็อก ห้ามเดา** ค่าที่ไม่ระบุ = เตือนให้ยืนยันกับฝ่ายผลิต
- **สเปกไม่ผ่าน = ปิดปุ่มส่งออกทั้งหมด** + แถบแดง + ลายน้ำ (`drawingIssue()` ใน `engine/constraints.js`)
- **ห้ามใส่ราคาในแอปวาดแบบ** — ราคาอยู่ที่ระบบเสนอราคา ⇒ ตรงกับการแยก module ใน §4
- **โมเดลชุดเดียว** สร้างทั้งภาพ 3 มิติ ภาพฉาย 2 มิติ และไฟล์ STEP ⇒ สามอย่างไม่มีวันขัดกันเอง
- ชิ้นส่วนประกอบบางชิ้น (หัวกะโหลก KSE/KNE · ข้อต่อ TS_-08/10) **ถอดจากไฟล์ CAD ของผู้ผลิต** แล้ววางเป็น
  "รูปทรงอ้างอิง" — ส่วนแกน/ความยาว/สายเป็นพารามิเตอร์ตามรหัส

ความเคลื่อนไหว: แก้ `heater-app` 7 คอมมิตตั้งแต่ 2026-08-25 · ล่าสุด 2026-10-02 · ⇒ **ยังโตอยู่ทุกสัปดาห์**
และเป็นรีโปของอีกบัญชี (`chalongbu/appsale`) ⇒ chatbot ต้องรับการเปลี่ยนแปลงของเขาได้โดยไม่พัง (§4.2)

### 2.2 วัดกับรหัสจริง — อ่านได้แค่ไหน (2026-10-05 · อ่านฐานอย่างเดียว)

เอารหัสรุ่นทั้งหมดในตาราง `products` ที่ขึ้นต้น BH / TS / N2 / N10 / P2 / P10 (**22,676 รหัสไม่ซ้ำ**)
ป้อนเข้า `canonical()` → `findProduct()` → `parse()` ของ Appsale:

| ผล | จำนวน | สัดส่วน |
| --- | ---: | ---: |
| อ่านได้ + สร้าง STEP ได้ | 13,785 | 60.8% |
| — ในนั้น `build()` กลับมาได้รหัสเดิมตรงตัว | 12,384 | 54.6% |
| — ในนั้น **ตัวตรวจสเปกบอก "ผลิตไม่ได้"** | 2,775 | (20.1% ของที่อ่านได้) |
| ไม่รู้จักรุ่น (เช่น TSK-04 3,086 · TSP-09 401 · TSK-14 212) | 5,419 | 23.9% |
| รู้จักรุ่นแต่อ่านรหัสไม่ผ่าน | 3,472 | 15.3% |

ข้อค้นพบที่เปลี่ยนการออกแบบ:
1. **Appsale อ่านรหัสตาม "แคตตาล็อก" แต่รหัสใน Odoo เขียนอีกแบบ** — เช่น BH-02 ในฐานเป็น
   `BH-02 37x100-110-125W` แต่แคตตาล็อก/Appsale เป็น `BH-02X50X300-220-500W` ⇒ **BH-02 อ่านได้ 0 / 494** ·
   ท้าย `-S###` มีใน 2,370 รหัส · `TSK-12` มีในฐาน 387 รหัสแต่ Appsale ถือว่า TS_-12 เป็น RTD เท่านั้น (0 / 387)
2. **หน้าคำนวณราคาของ chatbot แก้ปัญหาเหล่านี้ไปแล้วฝั่งตัวเอง** (`services/pricingLab/catalogBh.ts` ·
   `catalogTs.ts` · `readTsFormLoose`) ⇒ มีตัวอ่านรหัสสองตัวที่ตอบไม่เหมือนกันกับรหัสเดียวกัน — นี่คือที่มาของ
   ความเสี่ยง "ราคาขนาดหนึ่ง แบบอีกขนาด"
3. **รหัสที่มีอยู่จริงใน Odoo 2,775 ตัวถูกตัวตรวจของ Appsale บอกว่าผลิตไม่ได้** — แปลว่าตัวตรวจเข้มกว่าที่
   เคยผลิตจริง หรือรหัสเหล่านั้นอยู่นอกแคตตาล็อก ต้องให้ทีม Appsale/ฝ่ายผลิตไล่ดูก่อนเปิดให้ลูกค้า (§9 ข้อ 2)

> ตัวเลขชุดนี้วัดด้วยสคริปต์ชั่วคราว — เฟส 0 จะทำเป็นด่านถาวร `diag:drawing-parity` (§7) ที่วัดสิ่งที่สำคัญกว่า
> คือ "รหัสที่หน้าคำนวณราคาประกอบให้แล้ว" (ไม่ใช่รหัสดิบใน Odoo) Appsale อ่านได้ตรงกันกี่ %

### 2.3 รันบนเซิร์ฟเวอร์ได้แค่ไหน (ทดลอง 2026-10-05 · Node 22)

| ทำอะไร | ผล |
| --- | --- |
| `parse` / `build` / `validate` / `modelParts` / `exportStep` | **ได้** ไม่ต้องมีเบราว์เซอร์ |
| `renderSheet()` (กระดาษแบบ 2D/3D) | **ไม่ได้** — `document is not defined` เพราะภาพ 3 มิติแบบลงเงาวาดลง `<canvas>` (`engine/cad-camera.js`) ⇒ ต้องเรนเดอร์ในเบราว์เซอร์ (Puppeteer ที่ chatbot มีอยู่แล้ว) |

| ตัวอย่าง | ชิ้นส่วน | สามเหลี่ยม | STEP | เวลา |
| --- | ---: | ---: | ---: | ---: |
| `BH-01-120X60-220-800W-2` | 11 | 2,060 | 0.67 MB | 90 ms |
| `TSK-11-6X100+2M` | 14 | 8,076 | 2.81 MB | 174 ms |
| `TSK-06(S4)8AX200-2` (หัวกะโหลกจาก CAD ผู้ผลิต) | 7 | 151,080 | **58.85 MB** | **3.5 วิ** |

⇒ รุ่นที่มีหัวกะโหลก (TS_-06/07/08/15/17/18) ไฟล์ STEP ใหญ่ 49–59 MB ⇒ **ไม่เหมาะเป็นของที่ลูกค้าเปิดดูบนมือถือ**
แต่ mesh ชุดเดียวกันแปลงเป็น GLB (รูปแบบ 3 มิติของเว็บ) ได้เล็กกว่ามาก — ขนาดจริงวัดในเฟส 0

### 2.4 STEP ของ Appsale คือ "ผิวเหลี่ยม" ไม่ใช่ "ผิวโค้งจริง"

`engine/step.js` เขียน `FACETED_BREP` (ทุกผิวเป็นระนาบ) — เปิดใน SolidWorks/Fusion ได้ ประกอบเข้าเครื่องจักร
ของลูกค้าเพื่อดูขนาดภายนอกได้ แต่ **วัดรัศมี/เลือกผิวทรงกระบอกไม่ได้** ถ้าลูกค้าต้องการ STEP ผิวโค้งจริง
ต้องใช้ OpenCascade ฝั่งเซิร์ฟเวอร์ — เป็นโครงการแยก ไม่อยู่ในแผนนี้ (§9 ข้อ 5)

บั๊กรูปทรงแก้ที่ Appsale แล้วดึงใหม่ ไม่งั้นวันหนึ่งแบบในหน้า Appsale กับแบบที่ส่งลูกค้าจะคนละรูป

## 4. โครงสร้างที่เสนอ

### 4.1 ภาพรวมเส้นทาง

```
หน้า "คำนวณราคา" (มีอยู่แล้ว)
   │  POST /api/admin/pricing/quote  → { code, parsed, outcome }        ← pricingLab (ไม่แตะ)
   │
   │  ส่ง "code" ที่เซิร์ฟเวอร์ราคาประกอบแล้ว (ไม่ใช่ข้อความที่คนพิมพ์)
   ▼
POST /api/admin/drawing/preview { code }                                 ← module ใหม่
   │  services/drawing/engineHost  →  vendor/heater-app (parse · validate · modelParts)
   │  คืน: รุ่น · ค่าที่อ่านได้ · รหัสที่วาดจริง (build) · ผลตรวจสเปก · คำเตือน
   │
   ├─ GET  …/model.glb   ← mesh ชุดเดียวกับ STEP แปลงเป็น GLB (เขียนใน Node · ไม่ใช้ DOM)
   ├─ GET  …/sheet.pdf   ← renderSheet() ในเบราว์เซอร์ของ pdfGenerator.ts (ตัวเดียวทั้งระบบ)
   └─ GET  …/model.step  ← exportStep() (gzip ตอนเก็บ)
   │
   ▼  [สร้างลิงก์ให้ลูกค้า]  — เฟส 2
product_drawings (ตรึงไฟล์ ณ ตอนกด)  →  APP_URL/drawing/<uuid>
   │
   ▼
หน้าเว็บลูกค้า (vanilla HTML + three.js) — หมุน/ซูม · ภาพแบบ 2D · โหลด PDF / STEP · ไม่มีราคา
```

**ไม่มีส่วนใดอยู่ในเส้นทาง LINE webhook** — STEP บางรุ่นใช้ 3.5 วิ และ Puppeteer ไม่ควรแย่งงบ 48 วิของบอท

### 4.2 module ถอดออกได้ทั้งก้อน (แบบเดียวกับ `services/pricingLab/`)

| ไฟล์/ที่ | หน้าที่ |
| --- | --- |
| `vendor/heater-app/` | สำเนา `frontend/public/heater-app/` ของ Appsale ณ คอมมิตที่ปักไว้ — **ห้ามแก้** |
| `vendor/heater-app.lock.json` | `{ repo, commit, syncedAt, treeSha256, products: 33 }` — commit เข้า git เสมอ |

### 4.3 ข้อมูล — `product_drawings` (เฟส 2)

| คอลัมน์ | ความหมาย |
| --- | --- |
| `id uuid` | กุญแจของลิงก์ลูกค้า (แบบเดียวกับ `/download-pdf/{uuid}` — เดาไม่ได้) |
| `priced_code text` · `drawn_code text` | รหัสที่คิดราคา · รหัสที่ `build()` วาดจริง — เก็บทั้งคู่เพื่อสืบย้อนได้เสมอ |
| `product_id text` · `values json` | รุ่นของ Appsale + ค่าที่อ่านได้ทั้งก้อน |
| `engine_commit text` | คอมมิตของ Appsale ที่สร้างไฟล์ชุดนี้ |
| `checks json` | ผลตรวจสเปก + สถานะราคา ณ ตอนกด |
| `files json` | path/ขนาด/sha256 ของ GLB · PDF · STEP.gz · PNG ย่อ ใน `data/drawings/<id>/` |
| `created_by` · `created_at` · `expires_at` · `revoked_at` · `view_count` · `last_viewed_at` | ใครส่ง · หมดอายุ · ยกเลิกเอง · ลูกค้าเปิดหรือยัง |
| `quotation_id uuid null` · `local_product_id null` | ผูกกับใบ/สินค้าเพิ่มเอง (เฟส 3) |

**ตรึงไฟล์ตอนกดสร้างลิงก์ ไม่สร้างใหม่ทุกครั้งที่ลูกค้าเปิด** — Appsale แก้รูปทรงทุกสัปดาห์ ลิงก์ที่ส่งไปแล้ว
ต้องแสดงของที่ส่งไปจริง (หลักเดียวกับ snapshot ของรายการในใบเสนอราคา) · ⚠️ ไฟล์อยู่บนดิสก์ ⇒ ต้องเพิ่ม
`data/drawings/` เข้าชุดสำรองตีสาม (ตอนนี้สำรองเฉพาะฐาน) — ไฟล์หายยังสร้างใหม่ได้จาก `drawn_code` แต่จะได้
รูปทรงของ engine เวอร์ชันปัจจุบัน และหน้าลูกค้าต้องบอกว่าเป็นฉบับสร้างใหม่

### 4.4 กติกา "ส่งให้ลูกค้าได้หรือไม่" — อยู่ที่ `drawingService.ts` ที่เดียว

ส่งได้เมื่อ **ครบทุกข้อ**:
1. Appsale รู้จักรุ่นและอ่านรหัสผ่าน
2. **รหัสที่วาด = รหัสที่คิดราคา** (เทียบหลัง normalize ของ Appsale) — ไม่ตรง = การ์ดขึ้น
   "แบบนี้วาดจาก `X` ไม่ใช่ `Y` ที่คิดราคา" และปิดปุ่มส่ง ⇒ ตัดความเสี่ยงอันดับหนึ่งที่ต้นทาง
3. ตัวตรวจสเปกของ Appsale ไม่มีข้อ "ผลิตไม่ได้" (ข้อ "เตือน" แสดงให้คนส่งเห็น แต่ไม่ปิดปุ่ม)
4. หน้าคำนวณราคาไม่ได้ตอบ `notManufacturable` ("ไม่รับผลิต")

ทุกข้อที่ไม่ผ่านต้องบอกเหตุผลเป็นภาษาคน (ใช้ข้อความของ Appsale ที่เป็นไทยอยู่แล้ว) · **ไม่มีปุ่มข้ามด่านในเฟส 1–2**
(การส่งแบบของสิ่งที่ผลิตไม่ได้ให้ลูกค้า แย่กว่าไม่ส่ง) — ถ้าเจ้าของต้องการช่องทางข้าม ให้เป็นการอนุมัติแบบคิว
อนุมัติราคา ไม่ใช่ติ๊กเอง

`quoteOnRequest` ("ต้องขอราคา") **ไม่ปิด** การส่งแบบ — ราคายังไม่ครบไม่ได้แปลว่ารูปทรงผิด

## 5. หน้าจอ

ต้องอ่าน `docs/design.md` ก่อนลงมือ และส่ง mockup ให้เจ้าของดูที่พอร์ต 5174 ก่อนเขียนจริง

### 5.1 แอดมิน — การ์ด "แบบ 3 มิติ" ในหน้าคำนวณราคา (เฟส 1)
- อยู่ใต้การ์ดราคา · โหลดเมื่อคิดราคาเสร็จ (ไม่ขวางการแสดงราคา — แบบช้าหรือพัง ราคายังขึ้นปกติ)
- สลับ "3 มิติ (หมุนได้)" / "แบบ 2 มิติ" · แถบผลตรวจ ผ่าน / เตือน / ผลิตไม่ได้ ตามกติกาของ Appsale
- ปุ่ม: ดาวน์โหลด PDF แบบ · ดาวน์โหลด STEP (บอกขนาดไฟล์ก่อนกด — บางรุ่น ~59 MB) · **สร้างลิงก์ให้ลูกค้า** (เฟส 2 · ต้องมี `quote.share_drawing`)
- รุ่นที่ Appsale ไม่มี = บรรทัดเดียว "รุ่นนี้ยังไม่มีแบบ 3 มิติ" ไม่ใช่ error

### 5.2 หน้าเว็บของลูกค้า — **พื้นผิวที่ห้า** (เฟส 2)
`docs/design.md` วันนี้มีสี่พื้นผิว (Admin · LIFF · Flex · PDF) — หน้านี้ไม่ใช่ทั้งสี่ (คนดูคือลูกค้า ไม่ได้ล็อกอิน
เปิดจาก LINE/อีเมลบนมือถือ) ⇒ เฟส 2 ต้องเพิ่มหัวข้อพื้นผิวที่ห้าใน `design.md` ในคอมมิตเดียวกับหน้า
- vanilla HTML + three.js (กติกาเดียวกับ LIFF: ไม่มี React/Vite) · ใช้ได้ที่ความกว้างมือถือ
- โลโก้/ชื่อบริษัทจาก `utils/companyProfile.ts` · รหัสสินค้า · ภาพ 3 มิติหมุน/ซูม · ภาพแบบ 2 มิติ · ปุ่มโหลด PDF / STEP
- **ไม่มีราคา ไม่มีชื่อเซลส์/ลูกค้า** (ลิงก์ถูกส่งต่อได้)
- ข้อความกำกับถาวร: "แบบอ้างอิงตามแคตตาล็อก — ขนาดหลักตามรหัสสินค้า ชิ้นส่วนประกอบบางชิ้นเป็นรูปทรงอ้างอิง ไม่ใช่แบบผลิต"
- ลิงก์หมดอายุ/ถูกยกเลิก = หน้าบอกให้ติดต่อเซลส์ ไม่ใช่ 404 เปล่า

### 5.3 ใบเสนอราคา (เฟส 3)
- รายการในใบผูกกับ `product_drawings.id` · PDF ใบเสนอราคาเพิ่มหน้า "แบบอ้างอิง" + QR ไปหน้าลูกค้า

  `enrichQuotationData()` (whitelist สองชั้น — `CLAUDE.md` เคยพลาดมาแล้ว)
- หน้าต่าง `LocalProductModal` (เพิ่มสินค้าใหม่) แสดงการ์ดเดียวกัน · ปุ่ม "ดูแบบ 3 มิติ" ใน Flex = แค่ลิงก์ไปหน้าที่สร้างไว้แล้ว
  (ห้ามสร้างแบบระหว่างตอบ LINE)

- รหัสที่หน้าคำนวณราคาประกอบแล้ว Appsale อ่านได้กี่ % (ตัวเลข §2.2 วัดจากรหัสดิบใน Odoo ซึ่งน่าจะต่ำกว่า) — `diag:drawing-parity` เฟส 0
- ลูกค้าเปิด STEP ผิวเหลี่ยมขนาด ~59 MB ในโปรแกรมของเขาได้จริงไหม — ขอให้เซลส์ลองกับลูกค้าจริง 2–3 ราย ในเฟส 1
