## 0. สรุปสำหรับคนที่อ่านแค่หน้าแรก

แอดมินเพิ่ม "สินค้า" ที่ยังไม่มีใน Odoo ได้เองจากหน้าเว็บ โดยระบบ **ออกรหัส `internal_reference`
ให้ต่อจากรหัสเดิมของตระกูลนั้นทุกกรณี และพิมพ์ทับได้ทุกกรณี**
(หัวหน้าสั่ง: สืบทอดจากรหัสเดิม เพราะแต่ละ model มีรูปแบบของตัวเองอยู่แล้ว)
ของใหม่ไปอยู่ในทะเบียนของตัวเองชื่อ `local_products` **และมีแถวจริงใน `products`** ⇒ ค้นหาเจอ ·
ใส่ในใบได้ · กฎราคา/สต็อก/บล็อกทำงานเหมือนสินค้าอื่นทุกตัว โดยไม่ต้องแก้โค้ดที่อ่านสินค้าสักบรรทัด

ของที่ตามมาอีกสองชิ้น: **ไฟล์ xlsx/csv รายการสินค้าใหม่** ให้แอดมินเอาไปคีย์ใน Odoo เอง
และ **ธง `custom_product`** ที่กันใบซึ่งอ้างสินค้าตัวนี้ออกจากไฟล์ export ปกติ ไม่ให้ไปตกตอนนำเข้า

**สิ่งที่ไม่มีในโมดูลนี้คือปุ่มให้คนติ๊กว่า "คีย์เข้า Odoo แล้ว"** — ระบบตรวจเอง (§7)

**สามอย่างที่โมดูลนี้ต้องไม่ทำให้พัง และเป็นเหตุผลของการตัดสินใจเกือบทุกข้อในไฟล์นี้**

| ของที่พังได้ | พังยังไง | กันไว้ที่ |
| --- | --- | --- |
| `npm run sync:products` ทั้งรอบ | Odoo ส่งสินค้าที่แอดมินคีย์เข้าไปแล้วกลับมา → `internal_reference` ซ้ำกับแถว local → **ชน unique index → หน้านั้น rollback → sync ค้างถาวร** | §6 (กวาดก่อน upsert) |
| ช่องรหัสสินค้าในไฟล์ export | `model` ซ้ำกับสินค้าเดิม → `buildItemSnapshots()` หยิบ `internal_reference` ของอีกตัว → **ไฟล์ส่งรหัสผิดเข้า Odoo เงียบ ๆ** | §5 (บังคับ `model` ไม่ซ้ำ) |
| การเสนอราคาสินค้าที่เพิ่งเพิ่ม | สืบทอด `production = 'Production 2(PM)'` จากต้นแบบ → **ติดกฎบล็อกทันที เสนอราคาไม่ได้เลย** | §2.1 (ต้องให้เจ้าของเคาะ) |

## 1. รหัสสินค้ามีรูปแบบอะไร — อ่านจากข้อมูลจริง 51,648 รหัส

> วัดบนฐาน dev 2026-09-21 · `products` มี **51,665 แถว** · มี `internal_reference` **51,648 แถว**
> (ไม่ซ้ำกันทั้งหมด 51,648 ค่า) · **ยาว 14 อักขระเท่ากันหมด** (min = max = 14)

### 1.1 โครงของ 14 อักขระ

```
F  CU  P2  TSK  04  0073          FCUP2TSK040073   TSK-04(S2)6x50+5M-S000
│  │   │   │    │   └── เลขวิ่ง
│  │   │   │    └────── รุ่นย่อย/ขนาด ยกมาจากชื่อ model
│  │   │   └─────────── ซีรีส์ 3 ตัว
│  │   └─────────────── แหล่งที่มา
│  └─────────────────── ประเภทสินค้า
└────────────────────── หมวด
```

| ช่อง | อักขระ | แปลว่า | หลักฐาน |
| --- | --- | --- | --- |
| หมวด | 1 | `F` = FinishGoods · `S` = Service | F 51,647 แถว · S 1 แถว (ตรงกับ `product_category` เป๊ะ) |
| ประเภท | 2–3 | ประเภทสินค้า **104 รหัส** — `CU` = สั่งทำ · `TC` = Thermocouple · `RD` = RTD · `HT` = Heater · `TL` = Tower light … | ดู §1.2 — **ถอดจากคอลัมน์ไหนก็ไม่ได้** |
| แหล่ง | 4–5 | `P1`/`P2`/`P3` = Production 1/2/3(PM) · `BY` = Buy to Sell · ตัวอักษรอื่น+เลข = แบรนด์นำเข้า (`O1` = OPTEX · `T1` = TOHO · `T2` = TRAFAG …) | P2 35,292 · P1 6,306 · BY 4,549 · ที่เหลือ Import(PM) กระจาย 40+ รหัส |
| ซีรีส์ | 6–8 | `series` ของสินค้า · **เติม `X` ข้างหน้าเมื่อซีรีส์มี 2 ตัวอักษร** (`BH-01,02` → `XBH` · `LP` → `XLP` · `CM-013B` → `XCM`) | `TSK`→series TSK 9,053 · `XCH`→series CH-01,02 3,842 |
| รุ่นย่อย + เลขวิ่ง | 9–14 | **6 หลัก แต่แบ่งไม่เท่ากันทุกตระกูล** | §1.3 — ข้อสำคัญที่สุดของหัวข้อนี้ |

**`CU` = สินค้าสั่งทำ และมันไม่ใช่หมวดสินค้า** — 4,559 แถว กระจายทั่ว 22 `product_sub_category`
(RTD 1,121 · Thermocouple 1,008 · Cartridge Heater 615 …) และ **98.5% ของมันมี `-S0…` ในชื่อ model**
⇒ `CU` บอกว่า "สั่งทำ" ไม่ได้บอกว่าเป็นของประเภทอะไร

### 1.2 ห้ามคำนวณ prefix จากคอลัมน์ในฐาน — ต้องสืบทอดจากรหัสเดิม

ช่อง 2–3 กับ `product_sub_category` **ไม่ใช่ความสัมพันธ์หนึ่งต่อหนึ่ง**: 104 รหัส ต่อ 171 sub-category ·
**67 รหัสครอบมากกว่า 1 sub-category** และ **89 sub-category มีมากกว่า 1 รหัส**
ตัวอย่างที่แรงที่สุดคือ `AE` ซึ่งครอบ 33 sub-category ตั้งแต่ Accessorie ถึง Protection Relay

⇒ **นี่คือเหตุผลเชิงข้อมูลที่ยืนยันคำสั่งของหัวหน้า** — ระบบต้อง "สืบทอดจากรหัสเดิม" เพราะ
**ไม่มีสูตรจากคอลัมน์ไหนที่ประกอบ prefix ขึ้นมาใหม่ได้** ใครพยายามเขียนตารางแมป
`sub_category → รหัส 2 ตัว` จะได้ตารางที่ผิดทันทีสำหรับ 89 sub-category

| 3 + 3 | `FCDT1TTM214` **`000`** | `TTM-214-IR-R-M` | รุ่นย่อย `214` + วิ่ง `000` | 3 |
| 6 รวด | `FTGP1TGM` **`060035`** | `TGM-60035` | **เลขท้ายคือเลขรุ่นเอง ไม่ใช่เลขวิ่ง** | 0 — ตระกูลนี้ไม่มีเลขวิ่ง |

`FTGP1TGM06*` มี 815 แถว แต่เลขท้ายวิ่งจาก 0035 ถึง 9122 ⇒ **ตระกูลนี้ "เลขท้าย" ไม่ใช่ตัวนับ

**ไม่ปฏิเสธ** แต่ต้อง**บอกบนจอว่าเลขนี้มาจากชั้นไหน** เพื่อให้คนที่รู้เลขรุ่นจริงพิมพ์ทับได้
(§1.4 ชั้น 2 · §4.3 เส้น `GET /next-ref`)

### 1.4 อัลกอริทึมออกรหัส 2 ชั้น — **ออกเลขให้ทุกกรณี · พิมพ์ทับได้ทุกกรณี**

**ข้อตัดสินของเจ้าของ 2026-09-21: ตระกูลที่หาขอบเลขวิ่งไม่ได้ ก็ให้ `max+1` ไปเลย
แล้วแอดมินพิมพ์ทับได้** ⇒ ระบบไม่มีสถานะ "ออกรหัสให้ไม่ได้" อีก มีแต่ **"ความมั่นใจของเลขที่ออกให้"**
ซึ่งต้องบอกบนจอ

แทนที่จะเดาว่าเลขวิ่งกว้างกี่หลัก **ให้ข้อมูลบอกเอง** แล้วถอยเป็น `max+1` เมื่อข้อมูลบอกไม่ได้:

```
nextInternalReference(parentRef):
  # ── ชั้น 1 · "ขอบที่พิสูจน์ได้" ─────────────────────────────────────────────
  สำหรับ L = 8 .. 13:                      # L = ความยาว prefix ที่ตรึงไว้
    พี่น้อง = ทุก ref ยาวเท่ากัน · left(ref,L) = left(parentRef,L) · ส่วนที่เหลือเป็นเลขล้วน
    ถ้า พี่น้อง < 2 ตัว → ข้าม L นี้
    ถ้า (max - min + 1) <= max(1.5 * จำนวนพี่น้อง, จำนวนพี่น้อง + 5)   # ตัวนับจริง ไม่ใช่เลขรุ่น
       และ max+1 ไม่ล้นช่อง (14 - L หลัก):
      คืน { L, max, tier: 'boundary' }     # เอา L ที่สั้นที่สุดที่ผ่าน

  # ── ชั้น 2 · "max+1 ของกลุ่มที่ใกล้ที่สุด" ───────────────────────────────────
  สำหรับ L ตามลำดับ 10 → 9 → 8 → 11 → 12 → 13:
    พี่น้อง = เหมือนข้างบน                  # ไม่บังคับว่า parent เองต้องมีหางเป็นเลข
    ถ้า มีพี่น้อง >= 1 ตัว และ max+1 ไม่ล้นช่อง:
      คืน { L, max, tier: 'max_plus_one' }

รหัสใหม่ = left(parentRef, L) + zeroPad(max + 1, 14 - L)
```

**สามข้อที่ทำให้ลำดับในโค้ดนี้เป็นอย่างที่เห็น — เปลี่ยนแล้วผลเปลี่ยน**

1. **ชั้น 1 เอา L ที่สั้นที่สุด ไม่ใช่ยาวที่สุด** — ยาวที่สุดจะเจอ "กลุ่มหนาแน่น" ปลอมเสมอ
   (10 ตัวที่ขึ้นต้นเหมือนกัน 13 หลักก็หนาแน่นทั้งนั้น) แล้วได้ตัวนับกว้าง 1 หลักซึ่งล้นทันที
2. **ชั้น 2 ลอง `L=10` ก่อน ไม่ใช่ไล่จาก 8** — เพราะอักขระที่ 9–10 คือ **ช่องรุ่นย่อย/ขนาด**
   ซึ่งยกมาจากชื่อ model (§1.1) ⇒ **มันต้องไม่ขยับ** · ถ้าไล่จาก L=8 แล้วตัวนับ 6 หลักวิ่งข้าม
   `069999 → 070000` ช่องรุ่นย่อยจะเปลี่ยนจาก `06` เป็น `07` = **กลายเป็นรหัสของรุ่นอื่น**
3. **ชั้น 2 ไม่บังคับว่า parent เองต้องมีหางเป็นเลข** — มี 37 รหัสที่หางมีตัวอักษรปน
   (`FTGP1TGM65129R` · `FCDT1PCB09W000`) ⇒ ถ้าบังคับ กลุ่มนี้จะออกรหัสให้ไม่ได้เลย
   แต่พี่น้องที่หางเป็นเลขล้วนมีอยู่ ⇒ นับต่อจากพี่น้องได้

`POST /` ต้อง**คำนวณรหัสใหม่อีกครั้งในทรานแซกชันเดียวกับการบันทึก** (§3.4) แล้วเทียบกับรหัสที่ฟอร์ม
ส่งมา — ไม่ตรงแปลว่ามีคนแทรกไปก่อน ให้ตอบ 409 พร้อมรหัสใหม่ ไม่ใช่บันทึกทับเงียบ ๆ

### 1.5 ห้ามเติมรู — ต้องเป็น max+1 เสมอ

ในฐานมี **"รู" รวม 73,383 ช่อง** (ผลรวมของ `max−min+1−จำนวน` ทุกกลุ่ม) และ **128 กลุ่มจาก 3,147 กลุ่ม
มีรู** ⇒ อย่าคิดว่ารูคือเลขว่างที่หยิบไปใช้ได้

**เหตุผลที่รูส่วนใหญ่ไม่ว่าง:** gateway ตัด `active=false` ออกก่อนส่ง — **พิสูจน์แล้วกับฝั่งลูกค้า
เมื่อ 2026-07-23** (full sync จากปี 1970 ได้ 77,434 contact พอดีทุกครั้ง ทั้งที่มี contact จริง 5,906 ราย
ที่ออกใบสั่งขายแล้วแต่ไม่โผล่) ⇒ รูในรหัสสินค้าก็คือ **สินค้าที่ถูก archive ใน Odoo ซึ่งยังถือรหัสนั้นอยู่
แต่เราไม่มีทางเห็น**

⇒ **max+1 เสมอ ห้ามเติมรู** และแม้ max+1 ก็ยังแพ้ได้ถ้ามีของ archive อยู่เหนือ max
(เรามองไม่เห็น) ⇒ ต้องมีปุ่ม **"ออกเลขใหม่"** (§4.3 เส้น `POST /:id/reissue-ref`) เพราะ**ตัวที่รู้ความจริง
คือ Odoo ตอนนำเข้า ไม่ใช่เรา** — Odoo จะปฏิเสธ `default_code` ซ้ำเอง แล้วแอดมินกดขอเลขถัดไป
รหัสที่ถูกปฏิเสธต้องเก็บไว้ในประวัติ ไม่ใช่ทับทิ้ง (ไม่งั้นไม่มีใครรู้ว่าเคยลองเลขไหนไปแล้ว)

ที่เดียวแล้วของใหม่โผล่ครบ **สินค้าไม่มีประตูแบบนั้น** — `products` ถูก `SELECT` ตรงจาก

`services/quotationService.ts` · `scripts/diag/*` การสร้าง view ใหม่มาคร่อมแล้วไล่แก้ทุกจุด
**เป็นงานที่ใหญ่กว่าตัวโมดูลเอง และเสี่ยงกว่ามาก**

⇒ **ตัดสิน: แถว local เป็นแถวจริงใน `products`** แล้ว `local_products` ทำหน้าที่เป็น "ทะเบียน"

เข้า Odoo แล้วหรือยัง · เคยขอเลขไหนไปแล้ว)

**มีของเดิมยืนยันว่าท่านี้ใช้ได้จริงในรีโปนี้แล้ว** — บรรทัดค่าบริการคือแถวที่ระบบยัดเข้า `products`
เองด้วย `product_template_id = -1` และ [migration 2026-07-22_01](../migrations/changes/2026-07-22_01_shipping_fee.sql)
เขียนเหตุผลของทุกช่องไว้ครบ อ่านก่อนเขียน J1

**และ `sync:products` ไม่เคย `DELETE` หรือ `TRUNCATE` สักบรรทัด** (ตรวจแล้ว: ไม่มีคำเหล่านั้นใน
`scripts/sync/syncProducts.ts` เลย) มันเป็น `INSERT … ON CONFLICT (product_template_id) DO UPDATE`
ล้วน ⇒ แถวที่ `product_template_id` อยู่นอกช่วงของ Odoo **ปลอดภัยจากรอบ sync ทุกรอบ**

### 3.2 ตาราง `local_products` — `migrations/changes/2026-09-XX_01_local_products.sql`

```sql
-- เลขประจำตัวของสินค้า local: Odoo ใช้ช่วง -1 ถึง 180,634 (วัด 2026-09-21)
-- เลือก 900,000,001 ขึ้นไป ด้วยเหตุผลเดียวกับ local_contact_id_seq ทุกข้อ:
--   เป็นเลข "บวก" จึงรอดตัวกรอง `> 0` ที่มีอยู่หลายที่ · ห่างจากช่วงของ Odoo 5,000 เท่า
--   ของอัตราการโตปัจจุบัน · และไม่ใช่เลขลบซึ่งถูกจองความหมายไปแล้วโดยบรรทัดค่าบริการ
-- AS integer ไม่ใช่ bigint — คอลัมน์ products.product_template_id เป็น integer
-- (เพดาน 2,147,483,647 เหลือที่ให้ช่วง local อีก 1.2 พันล้าน มากเกินพอ)
CREATE SEQUENCE IF NOT EXISTS public.local_product_template_id_seq
  AS integer START WITH 900000001 INCREMENT BY 1 MINVALUE 900000001 MAXVALUE 2147483647;

CREATE TABLE IF NOT EXISTS public.local_products (
  product_template_id integer PRIMARY KEY
                      DEFAULT nextval('public.local_product_template_id_seq'),

  -- รหัสที่ระบบออกให้ (หรือคนพิมพ์เอง) — ตรงกับ products.internal_reference ของแถวคู่กัน
  internal_reference  text        NOT NULL,
  -- รหัสต้นแบบที่สืบทอดมา · เก็บไว้เป็นหลักฐาน ไม่ใช่ FK (ต้นแบบถูก archive ใน Odoo แล้วหายได้)
  parent_reference    text,
  -- รหัสนี้มาจากไหน — 3 ค่า ไม่ใช่ boolean เพราะ "ระบบออกให้" มีสองระดับความมั่นใจ (§1.4)
  --   boundary     = ชั้น 1 · ขอบเลขวิ่งพิสูจน์ได้จากพี่น้อง (96.63% ของเคส)
  --   max_plus_one = ชั้น 2 · นับต่อจากกลุ่มที่ใกล้ที่สุดให้เฉย ๆ (3.37%) ⇒ จอต้องเตือน
  --   manual       = แอดมินพิมพ์ทับเอง
  -- เก็บไว้เพื่อให้ตอบได้ว่า "รหัสที่ Odoo ปฏิเสธ มาจากชั้นไหน" — ถ้าชั้น 2 ถูกปฏิเสธบ่อยกว่าชั้น 1
  -- อย่างมีนัย นั่นคือหลักฐานว่าต้องปรับกฎ ไม่ใช่ความรู้สึก
  ref_tier            text        NOT NULL DEFAULT 'boundary',
  -- รหัสที่ขอไปแล้วแต่ Odoo ปฏิเสธ (ซ้ำกับของที่ archive อยู่) — ประวัติ ห้ามทับทิ้ง (§1.5)
  rejected_refs       text[]      NOT NULL DEFAULT '{}',

  model               text        NOT NULL,   -- ไม่ซ้ำกับ products.model ทั้งตาราง (§5)
  name                text        NOT NULL,
  sales_description   text,
  brand               text,
  series              text,
  product_group       text,
  product_category    text,
  product_sub_category text,
  -- ⚠️ ไม่มีคอลัมน์ production ที่นี่ ตามทางเลือก (ก) ใน §2.1 — ว่างไว้จนกว่า Odoo จะเติมให้เอง
  --    เปลี่ยนเป็นทางเลือก (ข) เมื่อไหร่ ให้เพิ่มที่นี่พร้อมกับคอลัมน์ mode ของ product_block_rules
  unit_of_measure     text,
  sales_price         numeric     NOT NULL DEFAULT 0,
  minimum_sales_price numeric     NOT NULL DEFAULT 0,

  created_by          integer,                -- admin_users.id · ไม่มี FK (ลบแอดมินแล้วหลักฐานต้องอยู่)

```

**ทำไมต้องมีคอลัมน์ ทั้งที่ดูจาก `product_template_id >= 900000000` ก็ได้** — เพราะทุกจุดที่อยากรู้
(ป้ายบนจอ · ธงใน snapshot · ตัวกวาดตอน sync · ไฟล์ export) จะต้องฝังเลข 900 ล้านไว้ในตัวเอง
กลายเป็นค่าคงที่ที่กระจายอยู่หลายไฟล์ — ตรงข้ามกับหลักการข้อ 2 ใน `AGENTS.md`
⇒ **ช่วงเลขเป็นกลไก (อยู่ที่ sequence + CHECK ที่เดียว) · `source` เป็นความหมาย (ทุกคนอ่านตัวนี้)**

**`sync:products` ไม่แตะคอลัมน์นี้** — `upsertProductRows()` ระบุชื่อคอลัมน์ที่จะเขียนไว้ครบ 24 ตัว
และ `source` ไม่อยู่ในนั้น ⇒ `INSERT` ได้ `'odoo'` จาก DEFAULT · `ON CONFLICT DO UPDATE` ไม่แตะ
**ห้ามเติม `source` เข้าไปในลิสต์ของ upsert** ไม่งั้นแถว local จะถูกเปลี่ยนเป็น odoo โดยไม่มีใครรู้

### 3.4 เขียนสองที่ในทรานแซกชันเดียว

```
withTransaction:
  1. INSERT local_products (...)  RETURNING product_template_id, internal_reference
  2. INSERT products (product_template_id, internal_reference, name, model, …, source='local',
                      is_system_item=false, quantity_on_hand=0, …=0)
  COMMIT
```

**`is_system_item` ต้องเป็น `false`** — `true` คือธง "ซ่อนจากผลค้นหา" ([index.ts:578](../index.ts#L578),
[3642](../index.ts#L3642), [4266](../index.ts#L4266)) ซึ่งตรงข้ามกับสิ่งที่โมดูลนี้ต้องการ
สินค้า local ต้องค้นเจอเหมือนสินค้าอื่นทุกตัว

**สต็อกทุกช่องเป็น 0 ตามความจริง** ไม่ใช่โกหกตัวเลขให้คำเตือนหาย — เหตุผลเดียวกับที่
migration ของบรรทัดค่าบริการเขียนไว้ · ผลคือกฎระงับสต็อกจะทำงานตามปกติ ซึ่งถูกต้อง:
สินค้าที่ยังไม่มีในระบบ Odoo ก็ไม่มีของในสต็อกจริง

### 4.1 หน้าตาของ `utils/productRefPattern.ts`

```ts
export const REF_LENGTH = 14;                // วัด 2026-09-21: ทั้ง 51,648 รหัสยาวเท่ากันหมด
export const REF_SHAPE = /^[A-Z0-9]{14}$/;

/** ถอด 14 อักขระเป็นช่องที่คนอ่านได้ — ใช้โชว์ให้แอดมินตรวจก่อนกดบันทึก (§1.1) */
export function describeRef(ref: string): {
  category: string; kind: string; origin: string; series: string; tail: string;
};

/** ความมั่นใจของเลขที่ออกให้ — จอต้องแสดงต่างกัน (§1.4) */
export type RefTier =
  | 'boundary'      // ชั้น 1 · ขอบเลขวิ่งพิสูจน์ได้จากพี่น้อง ⇒ แสดงเป็นค่าตั้งต้นเฉย ๆ
  | 'max_plus_one'; // ชั้น 2 · max+1 ของกลุ่มที่ใกล้ที่สุด ⇒ ต้องมีคำเตือนให้คนตรวจ

export interface RefBoundary {
  tier: RefTier;
  prefixLength: number;   // L
  width: number;          // 14 - L
  count: number;          // พี่น้องกี่ตัว
  min: number; max: number;
}

/** ขอบของชั้น 1 เท่านั้น — คืน null เมื่อพิสูจน์ไม่ได้ (ชั้น 2 ไปใช้ nextReference) */
export function findCounterBoundary(
  siblingRefs: readonly string[], parentRef: string
): RefBoundary | null;

/**
 * รหัสถัดไป — **ออกให้ทุกกรณีตามที่เจ้าของเคาะ 2026-09-21**
 * คืน null เฉพาะเมื่อไม่มีพี่น้องที่หางเป็นเลขเลยสักตัวในทุก L (วัด 2026-09-21: 0 เคสในฐาน)
 * ⇒ ผู้เรียกยังต้องเผื่อ null ไว้ เพราะข้อมูลโตแล้วอาจมีเคสใหม่ — ไม่ใช่เพราะวันนี้มี
 */
export function nextReference(
  siblingRefs: readonly string[], parentRef: string
): { ref: string; boundary: RefBoundary } | null;
```

**ฟังก์ชันพวกนี้รับ `siblingRefs` เข้ามา ไม่ยิง query เอง** — ตัว query อยู่ที่ repo ที่เดียว
และด่านทดสอบส่งชุดข้อมูลปลอมเข้าไปได้โดยไม่ต้องแตะฐาน

**`tier` ไม่ใช่ของประดับ** — มันคือสิ่งเดียวที่บอกคนหน้างานว่า "เลขนี้เชื่อได้" หรือ "เลขนี้แค่นับต่อ
ให้เฉย ๆ ช่วยตรวจก่อน" · ถ้าจอไม่แสดงมัน 3.37% ของเคสจะดูเหมือนเลขที่ระบบยืนยันแล้ว
ทั้งที่ไม่ใช่ (กฎเดียวกับธง `guess` ของ `services/pricingLab/code.ts`)

### 4.2 `describeRef` ต้องคืน "ไม่รู้" ไม่ใช่เดา

ช่อง 2–3 (ประเภท) กับ 4–5 (แหล่ง) เป็นรหัสที่ไม่มีตารางคำแปลในฐาน — มีแต่สิ่งที่เดาได้จากการ

ต้องออกมาเป็น `unknown` ห้ามเดาแล้วปล่อยผ่านเงียบ ๆ"*

## 5. `model` ต้องไม่ซ้ำ — และทำไมต้องตรวจฝั่ง server ไม่ใช่ unique index

`buildItemSnapshots()` แปลงบรรทัดในใบเป็น snapshot ด้วย query นี้
([quotationService.ts:609](../services/quotationService.ts#L609)):

```sql
SELECT product_template_id AS product_id, internal_reference, name, …
  FROM products WHERE model = $1 ORDER BY quantity_on_hand_unreserved DESC LIMIT 1
```

⇒ **`model` คือกุญแจที่ใบใช้หาสินค้า** และ `internal_reference` ที่ไหลต่อไปถึงช่อง
`order_line/product` ของไฟล์ Odoo มาจาก query นี้

**ในฐานมี `model` ซ้ำอยู่แล้ว 418 ค่า กระจายใน 849 แถว** (วัด 2026-09-21) เช่น
`BH-02 50x400-220-800W-S000` มี 3 รหัส · `HDH/B 100x270mm. 220V 2000W` มี 3 รหัส
⇒ `ORDER BY quantity_on_hand_unreserved DESC LIMIT 1` คือการตัดสินใจแบบ "เอาตัวที่มีของมากสุด"
ซึ่งเป็นท่าแก้ขัดที่มีอยู่ก่อนแล้ว **ไม่ใช่ของที่โมดูลนี้จะไปแก้**

**แต่สินค้า local มีสต็อก 0 ทุกช่อง** (§3.4) ⇒ ถ้า `model` ซ้ำกับของเดิม มันจะ**แพ้เสมอ** แล้ว
snapshot จะได้ `internal_reference` ของสินค้าตัวอื่น ⇒ **ไฟล์ export ส่งรหัสผิดเข้า Odoo
โดยไม่มีอะไรฟ้อง** — ความผิดชนิดที่แย่ที่สุดของฟีเจอร์นี้

⇒ **`POST /` ต้องปฏิเสธ 409 เมื่อ `model` ตรงกับแถวใดในตาราง `products` ทั้งตาราง**
(ไม่ใช่แค่ใน `local_products`) และด่านต้องมีข้อที่พิสูจน์ข้อนี้

**ทำไมไม่ทำเป็น unique index บน `products.model`** — เพราะ 849 แถวเดิมละเมิดอยู่แล้ว
สร้าง index ไม่ผ่านตั้งแต่ต้น และการ "ไล่แก้ 849 แถวให้ไม่ซ้ำ" คือการแก้ข้อมูลของ Odoo จากฝั่งเรา
ซึ่งรอบถัดไปของ sync จะเขียนทับกลับทั้งหมด ⇒ **ข้อบังคับนี้อยู่ได้แค่ชั้น server เท่านั้น
และต้องมีด่านเฝ้า เพราะ DB ช่วยไม่ได้**

## 6. รอบ sync — จุดที่พังได้ทั้งระบบถ้าทำไม่ครบ

### 6.1 อาการ

`idx_products_internal_reference` เป็น **UNIQUE index** (partial · [schema.sql:1554](../migrations/schema.sql#L1554))
วันที่แอดมินคีย์สินค้าเข้า Odoo สำเร็จ รอบ sync ถัดไปจะได้แถวใหม่ที่มี
**`product_template_id` ของ Odoo (เลขใหม่) แต่ `internal_reference` ตัวเดิม**

`upsertProductRows()` เป็น `ON CONFLICT (product_template_id) DO UPDATE` ⇒ มันไม่เห็นการชนที่
`internal_reference` ⇒ **unique violation → `ROLLBACK` ทั้งหน้า → `decidePageTransition` ดึง cursor เดิมซ้ำ
→ ชนซ้ำ → ค้ายอยู่ที่หน้านั้นจนครบ `MAX_STALL_RETRIES` แล้วรอบ sync ตาย**

**นี่ไม่ใช่บั๊กของโมดูล มันคือ "ข้อมูลสินค้าทั้งระบบหยุดอัปเดต"** ⇒ ต้องกันที่ต้นทาง ไม่ใช่กันด้วยการ
เตือนคนให้ระวัง

### 6.2 ทางแก้ — กวาดก่อน upsert หนึ่งคำสั่งต่อหน้า

เพิ่มในหัวของ `upsertProductRows()` **หนึ่งคำสั่งต่อหน้า (500 แถว) ไม่ใช่ต่อแถว**:

```sql
DELETE FROM products
 WHERE source = 'local'
   AND internal_reference = ANY($1::text[])   -- รหัสทุกตัวในหน้านี้
   AND product_template_id <> ALL($2::int[]); -- กันตัวเองไว้ เผื่อ id ตรงกันโดยบังเอิญ
```

ต้นทุน: **1 คำสั่งต่อหน้า × ~104 หน้าต่อ full sync** และมี
`idx_products_source_local` รองรับ ⇒ ไม่มีผลกับเวลา sync ที่วัดได้
**ทำใน `upsertProductRows()` ไม่ใช่ท้ายรอบ sync** เพราะการชนเกิดกลางหน้า — กวาดทีหลังไม่ทัน

⇒ แถว local **ถูกแทนที่ด้วยแถวจริงของ Odoo** ซึ่งเป็นสิ่งที่ต้องการอยู่แล้ว: พอ Odoo มีของจริงแล้ว
ของปลอมต้องหายไป ไม่ใช่อยู่คู่กันเป็นสินค้าซ้ำในผลค้นหา

### 6.3 `reconcileLocalProductOdooLinks()` ท้ายรอบ sync

ต่อท้ายรอบเหมือน `reconcileLocalContactOdooLinks()` ทุกข้อ รวมถึง**การข้ามเงียบ ๆ เมื่อยังไม่มีตาราง**
(`information_schema.tables` ก่อน แล้ว `swarn` + `return null` — **ห้าม `CREATE TABLE` ให้เอง**
เหตุผลอยู่ใน [localContacts.ts:376](../services/localContacts.ts#L376)) และ **ห้าม throw** เพราะเป็น
guard ท้าย sync

หน้าที่:
1. แถวใน `local_products` ที่ `odoo_matched_at IS NULL` แต่ `internal_reference` มีอยู่ใน `products`
   โดยที่แถวนั้น `source = 'odoo'` แล้ว ⇒ ประทับ `odoo_matched_at` · `odoo_matched_template_id`
   · `odoo_matched_by = 'product_sync'`
2. นับที่ยังค้าง แล้ว `slog` เหมือนฝั่งผู้ติดต่อ

**`imported_order` เป็นทางที่สองเหมือนฝั่งผู้ติดต่อ** — สินค้าที่โผล่ใน `sale_orders.model` แปลว่า
ใบสั่งขายถูกนำเข้า Odoo สำเร็จแล้ว ⇒ สินค้านั้นมีจริงใน Odoo แม้รอบ sync สินค้ายังไม่ทัน
(รัน `product_sync` ก่อน `imported_order` ในรอบเดียวกัน)

### 6.4 ผลข้างเคียงที่ต้องเขียนไว้ ไม่ใช่ปล่อยให้คนรุ่นหลังไปเจอเอง

**`item_details[].product_id` ของใบเก่าจะชี้ไปที่แถวที่ถูกลบแล้ว** (เลข 900 ล้าน) ⇒ **ไม่เป็นไร
และห้ามไป backfill**:
- ไฟล์ export ใช้ `internal_reference` ไม่ใช่ `product_id` ([odooSaleOrderExport.ts:440](../services/odooSaleOrderExport.ts#L440))
- `PUT /api/quotation/:id` แค่ต้องการให้ `product_id` **ไม่เป็น null** (มันทิ้งรายการที่ไม่มี product_id
  ทิ้งเงียบ ๆ — เหตุผลที่บรรทัดค่าบริการต้องมี id ตั้งแต่แรก)
- สต็อกบนจอ join ด้วย `model` ใหม่ทุกครั้งใน `enrichQuotationData()` อยู่แล้ว

การไป backfill `product_id` ให้เป็นเลขใหม่ของ Odoo **จะทำลายความหมายของ snapshot** ซึ่งคือ
"ข้อเท็จจริงตอนออกใบ" ไม่ใช่ "ข้อเท็จจริงวันนี้"

## 7. ระบบรู้เองว่าคีย์เข้า Odoo แล้ว — ไม่มีปุ่มให้คนติ๊ก

เหมือนที่เจ้าของเคาะไว้กับผู้ติดต่อเมื่อ 2026-09-17 และเหตุผลแรงกว่าฝั่งนั้นด้วย:
**สินค้าที่คีย์เข้า Odoo แล้วจะเดินกลับมาหาเราเองทางรอบ sync** (ต่างจากผู้ติดต่อที่ต้องรอ
ใบสั่งขายหรือรอบ sync ลูกค้า) ⇒ ปุ่ม "ติ๊กว่าเสร็จแล้ว" มีแต่จะสร้างสถานะที่ขัดกับความจริงได้

สถานะที่จอแสดง — คำนวณทั้งหมด ไม่มีคอลัมน์สถานะให้ใครกด:

| ป้าย | เงื่อนไข |
| --- | --- |
| 🟡 รอส่งออก | `exported_at IS NULL` |
| 🔵 ส่งออกแล้ว รอคีย์ Odoo | `exported_at IS NOT NULL AND odoo_matched_at IS NULL` |
| 🟢 เข้า Odoo แล้ว | `odoo_matched_at IS NOT NULL` |
| 🔴 รหัสถูกปฏิเสธ | `array_length(rejected_refs, 1) > 0 AND odoo_matched_at IS NULL` |

**`ref_tier` เป็นคอลัมน์แยกจากสถานะ ไม่ใช่ป้ายในชุดเดียวกัน** — สถานะตอบว่า "ไปถึงไหนแล้ว"
ส่วน `ref_tier` ตอบว่า "รหัสนี้เชื่อได้แค่ไหน" ⇒ แถวที่ `ref_tier = 'max_plus_one'` ต้องเห็นได้จากรายการ
ตั้งแต่ก่อนกดส่งออก เพราะนั่นคือช่วงเวลาเดียวที่แก้ได้ฟรี (หลังคีย์เข้า Odoo แล้วรหัสเป็นของ Odoo แล้ว)

## 8. ธง `custom_product` — สวิตช์ที่โค้ดรออยู่แล้ว

**ช่องถูกจองไว้ครบตั้งแต่ 2026-09-15 · ที่ขาดคือคนกดสวิตช์** (ตรวจแล้วทั้ง 4 จุด):

| จุด | ที่ไหน |
| --- | --- |
| ชนิด | `ODOO_MANUAL_REASON_KINDS` [quotationService.ts:335](../services/quotationService.ts#L335) |
| ประโยคบนจอ | `buildManualReasonDisplay()` [:354](../services/quotationService.ts#L354) — *"📦 รหัสสินค้า … ยังไม่มีใน Odoo ⇒ ต้องสร้างก่อน"* |

| ป้ายในหน้าประวัติ | [Quotations.tsx:121](../frontend/src/admin/Quotations.tsx#L121) |

### 8.1 ธงต้องอยู่ใน snapshot — ไม่ใช่ query ตอนยืนยัน

`buildOdooManualReview()` **เรียกอยู่ใน transaction ของ `confirmQuotationAtomic` จึงห้ามยิง query เพิ่ม**
(หัวฟังก์ชันเขียนไว้เอง) ⇒ ธงต้องอยู่ในตัว snapshot

เพิ่ม `is_local_product: boolean` ใน `buildItemSnapshots()` โดยดึง `source` มาใน query เดิม
(เพิ่มชื่อคอลัมน์ 1 ตัว ไม่เพิ่ม query)

**และต้องเพิ่มใน `legacyItems` ของ `enrichQuotationData()` ด้วย** — นี่คือ whitelist สองชั้นที่
`CLAUDE.md` เตือนไว้ · เกณฑ์ตัดสินผ่านชัด: **field นี้สร้างใหม่ไม่ได้** เพราะพอ Odoo มีสินค้าแล้ว
แถว local ถูกลบ (§6.2) แล้ว `products` จะไม่มีอะไรบอกอีกเลยว่าตอนออกใบนั้นสินค้ายังไม่มีใน Odoo
⇒ ตกหล่นเมื่อไหร่ ป้ายบนหน้าประวัติกับ LIFF หายเงียบ ๆ ทั้งที่คิวยังถูกต้อง (อาการโผล่คนละที่กับสาเหตุ
เหมือนเคส `linked_to_product_id` เมื่อ 2026-07-24)

### 8.2 ธงผูกกับ "ใบ" ไม่ใช่ "endpoint"

`buildItemSnapshots()` เป็นทางผ่านของ **ทุกเส้น** (LINE · LIFF · เว็บ) ⇒ ใส่ที่นั่นแล้วใบจากทุกทางเข้า
ติดธงเท่ากัน · **ห้ามย้ายไปไว้ที่ `POST /api/webquote/*`** เพราะ `PUT /api/quotation/:id` และ
`/confirm` เป็นของที่ LIFF ใช้ร่วมกัน ⇒ ใบจาก LINE ที่อ้างสินค้า local จะทะลุไปอยู่ในไฟล์ export ปกติ
แล้วตกตอนนำเข้าทั้งกอง (กฎเดียวกับที่ `CLAUDE.md` เขียนไว้เรื่อง `odoo_manual_review`)

### 8.3 ลำดับของเหตุผล

`new_contact → custom_product → payment_terms_override` — เรียงตามของที่ต้องสร้างใน Odoo ก่อน
(นิยามอยู่ที่ `ODOO_MANUAL_BUCKET_SQL` ที่เดียว · ที่มาอยู่ที่ [plan-web-quote-request.md §N.4](plan-web-quote-request.md))

⚠️ **ใบหนึ่งใบเก็บได้หลายเหตุใน `reasons[]` แต่ "อยู่ได้กลุ่มเดียว" ในเมนูส่งออก** — `ODOO_MANUAL_BUCKET_SQL`
เลือกกลุ่มตามลำดับข้างบน เพื่อให้ยอดทุกกลุ่มบวกกันได้เท่าจำนวนใบค้างพอดีและไม่มีใบไหนโผล่สองไฟล์
จนนำเข้าซ้ำ ⇒ ใบที่ทั้งมีผู้ติดต่อใหม่และสินค้าใหม่จะไปอยู่กลุ่ม `new_contact` **ซึ่งถูกต้องแล้ว
อย่าไป "แก้" ให้มันโผล่สองกลุ่ม**

**`custom_product` ไม่ใช่กฎบล็อก** — มันไม่ห้ามออกใบ ไม่ห้ามพิมพ์ PDF ไม่เข้าคิวอนุมัติ
มันแค่กันใบออกจากไฟล์ export ปกติ ⇒ **ห้ามเอาไปนับรวมกับ `rule_overrides` หรือ `price_approval`
เป็นตัวเลขเดียว**

## 12. วิธีวัดซ้ำ

ตัวเลขทุกตัวในไฟล์นี้วัดจากฐาน dev 2026-09-21 ด้วย `psql` ที่
`C:\Program Files\PostgreSQL\18\bin\` (**ไม่ได้อยู่ใน PATH**) เช่น:

```sql
-- §1: ความยาวรหัส · จำนวน · ไม่ซ้ำ
SELECT count(*), count(internal_reference), count(DISTINCT internal_reference),
       min(length(internal_reference)), max(length(internal_reference)) FROM products;

-- §1.2: ช่อง 2-3 กับ sub_category เป็นหลายต่อหลาย
WITH m AS (SELECT substr(internal_reference,2,2) c23, product_sub_category sc
             FROM products WHERE internal_reference IS NOT NULL GROUP BY 1,2)
SELECT (SELECT count(DISTINCT c23) FROM m), (SELECT count(DISTINCT sc) FROM m),
       (SELECT count(*) FROM (SELECT c23 FROM m GROUP BY c23 HAVING count(*)>1) x),
       (SELECT count(*) FROM (SELECT sc  FROM m GROUP BY sc  HAVING count(*)>1) y);

-- §1.5: รูทั้งหมด
WITH g AS (SELECT left(internal_reference,10) p, count(*) n,
                  min(right(internal_reference,4)::int) mn, max(right(internal_reference,4)::int) mx
             FROM products WHERE internal_reference ~ '^.{10}[0-9]{4}$' GROUP BY 1)
SELECT count(*), sum(mx-mn+1-n) FROM g;

-- §5: model ซ้ำ
SELECT count(*), sum(n) FROM (SELECT model, count(*) n FROM products
  WHERE model IS NOT NULL GROUP BY 1 HAVING count(*)>1) x;

-- §2.1: กฎบล็อกคลุมกี่รายการ
SELECT count(*) FROM products p WHERE EXISTS (
  SELECT 1 FROM product_block_rules r WHERE r.is_active AND r.production = p.production
    AND r.brand IS NULL AND r.series IS NULL AND r.model IS NULL AND r.internal_reference IS NULL);
```
