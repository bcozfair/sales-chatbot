# กฎหน้าตาของแอปนี้

**ไฟล์นี้คือกฎของ "สิ่งที่มีอยู่แล้ว" ไม่ใช่ข้อเสนอให้สร้างดีไซน์ซิสเทมใหม่** ทุกบรรทัดข้างล่าง
อธิบายของที่อยู่ในทรีนี้วันนี้ พร้อมเหตุผลว่าทำไมถึงเป็นแบบนั้น ตัวเลขทั้งหมดวัดเมื่อ **2026-09-12**
เว้นที่ระบุวันอื่น

**การรื้อทำใหม่คือความผิดพลาดที่ไฟล์นี้มีไว้กัน** ข้อเสนอที่ขึ้นต้นว่า "ตั้งชุดโทเคนใหม่ให้สะอาดกว่านี้"
หรือ "ย้าย LIFF ไป React" หรือ "ทำ component library ให้ admin ใหม่ทั้งชุด" — ถ้าของที่มีอยู่ทำงาน
ไม่ได้กับสิ่งที่กำลังจะทำ นั่นคือคำถามที่ต้องกลับไปถามเจ้าของ (`AGENTS.md` ข้อ 7) ไม่ใช่ใบอนุญาต
ให้สร้างระบบคู่ขนาน

## 0. ลำดับก่อนแตะโค้ด

ห้าขั้น และขั้นที่ 4 คือขั้นเดียวที่ข้ามไม่ได้:

1. **ตอบให้ได้ก่อนว่าจอนี้อยู่พื้นผิวไหน** (หัวข้อ 1) — กติกาของสี่พื้นผิวไม่เหมือนกันเลย
2. **เปิดจอที่ใกล้เคียงที่สุดที่มีอยู่แล้วดูจริง** ไม่ใช่เดาว่ามันหน้าตาอย่างไร
3. **เขียนคำถามที่ยังไม่รู้ออกมาเป็นคำถาม** (เช็กลิสต์หัวข้อ 10 ใช้ย้อนกลับเป็นรายการคำถามได้ตรง ๆ)
4. **ส่ง mockup ที่ render แล้ว รอคำยืนยันจากเจ้าของ** — เงียบไม่ใช่โอเค ตอบเรื่องใกล้เคียงไม่ใช่โอเค
5. เขียนโค้ด แล้วเดินเช็กลิสต์หัวข้อ 10 ก่อนบอกว่าเสร็จ

ถ้ารอบนั้นทำให้ประโยคในไฟล์นี้ไม่จริงอีกต่อไป **ให้แก้ไฟล์นี้ในคอมมิตเดียวกัน**

## 1. สี่พื้นผิว กติกาคนละชุด

นี่คือรากของบั๊กดีไซน์ที่เกิดซ้ำที่สุดในโปรเจคนี้ — เอากติกาของพื้นผิวหนึ่งไปใช้กับอีกพื้นผิว

  ส่วน LIFF ใช้ `#1e8f1e` (`--green`) สองค่านี้เกิดคนละรอบและ **ไม่เคยอยู่บนจอเดียวกัน**
  จะรวมเมื่อไหร่เป็นการตัดสินใจของเจ้าของ ไม่ใช่การเก็บกวาดระหว่างทาง
- **Flex ไม่ได้ใช้สีแบรนด์เลย** — `flexTemplates.ts` ใช้ `#2563EB` (11 จุด) `#1F2937` (13)

- **อีโมจิเป็นไอคอนที่ถูกต้องบน LIFF/Flex/ข้อความ LINE** (วัดได้: LIFF 150 ตัว · Flex 76 ·

  ของไฟล์** — ตัวนั้นไม่ใช่ปัญหา — และ **6 จุดอยู่บนจอจริง**: `👋` ในคำทักทาย, `©` ในฟุตเตอร์
  หน้าล็อกอิน, `⚠` ในคำเตือน pool ไม่พอ, `❌` ในตัวอย่างข้อความ Flex ที่หน้า `BlockRules`

## 2. Admin — สีอยู่ที่ `index.css` ที่เดียว

**สีดิบใน `.tsx` / `.ts` = 0 จุด (วัดแล้ว) และนี่คือตัวเลขที่ต้องคงไว้ที่ 0**

`frontend/src/index.css` ทำงานสองชั้น และการแยกสองชั้นคือประเด็นทั้งหมด:

1. `:root` ประกาศ **จานสีจริง** เป็น `--c-*` (พื้นผิว 4 ระดับ · หมึก 6 ระดับ) + `--brand-*`
2. `@theme` เอาจานนั้นไป **ทับ token ของ Tailwind** (`--color-slate-*`, `--color-red-*`, …)

ผลคือคอมโพเนนต์ยังเขียน `bg-card` / `text-slate-900` / `border-slate-200` ตามปกติ แล้วได้สีมืด
อัตโนมัติทุกหน้า **ไม่ต้องแก้ทีละไฟล์** — และนั่นคือเหตุผลที่ห้ามพิมพ์ hex ลง `.tsx`: hex ที่พิมพ์มือ
จะเป็นจุดเดียวที่ไม่สลับตามธีม แล้วมันจะไม่พังตอนที่พิมพ์ แต่พังตอนที่มีคนกดปุ่มสลับธีม

**บันไดกลับด้านในธีมมืด** — `slate-50` = มืดสุด, `slate-900` = สว่างสุด ส่วน `50–300` ของสีสถานะ
คือ **พื้น/ขอบ** และ `400–800` คือ **ตัวอักษร/ไอคอน** ถ้าเขียนกลับกันจะได้ตัวอักษรที่อ่านไม่ออกบน
ธีมหนึ่งและอ่านออกบนอีกธีมหนึ่ง ซึ่งเป็นบั๊กที่คนเขียนไม่มีทางเห็นเพราะเปิดอยู่ธีมเดียว

**ธีมมืดเป็นค่าเริ่มต้น** (`ThemeToggle.tsx` + `localStorage['admin-theme']`) และตัวเซ็ตธีมตอนโหลด
อยู่ใน `<head>` ของ `admin.html` / `index.html` **โดยตั้งใจ** เพื่อไม่ให้จอวาบขาวก่อน React ทำงาน —
ย้ายไปไว้ใน React เมื่อไหร่ อาการวาบขาวกลับมาทันทีโดยไม่มี error
`:root { color-scheme: dark }` ก็เป็นของจำเป็น ไม่ใช่ของประดับ: มันทำให้ date picker, dropdown
และ autofill ของ native มืดตาม

**เฉดที่ `.tsx` ใช้ ต้องมีอยู่ใน `@theme` เสมอ — เขียนคลาสเฉย ๆ ไม่พอ** (2026-09-17)
จานสีของแอปนี้ไม่ได้ต่อยอดจากจานของ Tailwind แต่**ทับมัน** ⇒ เฉดที่ไม่ได้ประกาศไว้จะได้ผลสองแบบ
และแย่ทั้งคู่: หล่นไปใช้**ค่าเริ่มต้นของ Tailwind ซึ่งออกแบบมาสำหรับพื้นสว่าง** (สีเข้มบนพื้นเข้ม)
หรือ **ไม่ถูกสร้างเป็น CSS เลย** แล้วตัวอักษรไปรับสีที่สืบทอดมาแทน · ทั้งสองแบบ **คอมไพล์ผ่าน
lint ผ่าน และดูปกติในธีมที่คนเขียนเปิดอยู่**

เคสจริงที่วัดได้ 2026-09-17 (เกณฑ์ตัวอักษรปกติคือ 4.5:1)

| คู่สี | ก่อนแก้ | หลังแก้ | ที่เจอ |
| --- | --- | --- | --- |
| `bg-violet-50` + `text-violet-800` | **2.46:1** (มืด) | 10.09:1 | กล่อง "ต้องขออนุมัติราคา" |
| `bg-violet-100` + `text-violet-700` | **2.56:1** (มืด) · **1.02:1** (สว่าง) | 5.83 / 5.98:1 | ป้ายตัวเลขข้างเมนู "อนุมัติราคา" |
| `bg-blue-50` + `text-blue-800` | **2.10:1** (มืด) | 9.77:1 | กล่องน้ำเงินในหน้า "ข้อมูลสินค้า"/"ข้อมูลลูกค้า" |

⇒ **เพิ่มเฉดใหม่ต้องเพิ่มทั้งสองบล็อก** (`@theme` = มืด · `:root[data-theme="light"]` = สว่าง)
เพิ่มข้างเดียวคือการย้ายบั๊กไปอีกธีมหนึ่ง · และ **ห้ามเดาว่า "สีนี้น่าจะพอ"** — วัดด้วยคอนทราสต์จริง
จาก CSS ที่ build แล้ว ไม่ใช่จากค่าที่เขียนไว้ในไฟล์

**กรณี "ไม่ถูกสร้างเป็น CSS เลย" มีด่านแล้ว: `npm run diag:dead-classes`** (2026-09-21 ·
ต้อง `npm --prefix frontend run build` ก่อน) — มันเทียบคลาสตระกูลสีในซอร์สกับ CSS ที่ออกมาจริง
เกิดมาสองรอบ: `bg-surface` 7 จุด (2026-09-18) และเฉด 55 · 105 · 150 · 450 อีก 6 จุด (2026-09-21)
**อาการไม่ได้เป็นแค่ "ไม่มีสี" — บางตัวกลับด้าน** เพราะ `border` เปล่า ๆ ให้แค่ความหนา สีตกเป็น
`currentColor` ส่วน `text-*` ที่หายตกไปรับสีจาก `body` = `--c-text-max` ⇒ เส้นคั่น/คำบอกใบ้
ที่ตั้งใจให้จางที่สุด กลายเป็นสว่างที่สุด (วัดระยะสีก่อน→หลัง 343 · 182 · 182)
· **"ผ่าน" ไม่ได้แปลว่าสะอาดแน่นอน** — ด่านครอบคลุมเฉพาะลิสต์คลาสที่เป็นสตริงตรง ๆ
ไม่ตรวจโทเคนที่ประกอบขึ้นในนิพจน์ JS (เหตุผลและตัวเลขอยู่หัวไฟล์ `scripts/diag/deadClasses.ts`)

**ป้ายจำนวนบนแถบเมนูใช้ "คู่พื้น + หมึก" ของปุ่มหลัก ไม่ใช่สีจาง ๆ ของหน้าปลายทาง**
(เจ้าของสั่ง 2026-09-17 หลังเห็นของจริง) — `--btn-primary-bg` + `--btn-primary-ink` เป็นคู่ที่
วัดคอนทราสต์มาแล้วทั้งสองธีม และ **พื้นทึบยังอ่านออกตอนเมนูนั้นถูกเลือกอยู่** ซึ่งพื้นแถวเป็น
เขียวจาง · ป้ายพื้นจางบนแถวพื้นจางจะกลายเป็นป้ายที่ไม่มีรูปร่าง
วัด 2026-09-17: อักษรบนป้าย 9.35:1 (มืด) · 5.43:1 (สว่าง) · ป้ายบนแถวที่ถูกเลือก 7.39:1 (มืด) ·
4.95:1 (สว่าง) — เทียบแบบผสมความโปร่งของพื้นแถวกับพื้นข้างหลังแล้ว ไม่ใช่เอา `rgba` ไปเทียบตรง ๆ
ซึ่งให้เลขที่ไม่มีความหมาย (โทเคน `violet-100`/`violet-800` ยังอยู่ในจานสี เพราะเฉดที่ประกาศไว้
ถูกต้องแล้วมีค่ากว่าเฉดที่หายไป — คนถัดไปที่เขียน `violet-100` จะได้สีที่ใช้ได้ทันที)

**เฉดที่ไม่มีอยู่จริงในบันได Tailwind ก็เงียบเหมือนกัน** — `slate-55` `slate-150` `slate-350`
`slate-450` `emerald-55` `emerald-105` `emerald-150` `red-550` ที่ค้างอยู่ใน `Promotions.tsx`
กับ `StockRules.tsx` **ไม่ถูกสร้างเป็น CSS สักคลาสเดียว** (วัด 2026-09-17: 0 rule ในไฟล์ที่ build
ออกมา) ⇒ พื้นที่ตั้งใจให้มีกลายเป็นโปร่ง และตัวอักษรไปรับสีที่สืบทอดมา

**เบรกพอยต์เป็นค่าดีฟอลต์ของ Tailwind** (`sm 640 · md 768 · lg 1024 · xl 1280`) — ไม่มี
`--breakpoint-*` ใน `@theme` **อย่าเพิ่ม** การใช้งานจริงกระจุกที่ `sm:` (63 จุด) แล้วค่อย `lg:` (19)
`xl:` (10) `md:` (5) แปลว่าแอปนี้คิดเป็น "มือถือ ↔ จอทำงาน" สองขั้นเป็นหลัก จอที่เขียนใหม่ควรอยู่ใน
บันไดเดิม ไม่ใช่หยิบเส้นที่ยังไม่มีใครใช้

## 2.1 Admin — สีปุ่ม: บทบาท ไม่ใช่รสนิยม (2026-09-14)

**ปุ่มเลือกสีจาก "บทบาท" ห้าอย่าง ไม่ใช่จากว่าอยากให้เด่นแค่ไหน** — และ "สีเทา" ไม่ใช่บทบาท
มันคือ **สถานะ `disabled` ของทุกบทบาท** ซึ่งหน้าตาเหมือนกันหมด ไม่งั้นคนอ่าน "ปุ่มแดงจาง ๆ"
ว่าอันตราย ทั้งที่มันแค่กดไม่ได้

| บทบาท | สี | ใช้กับ |
| --- | --- | --- |
| `primary` | เขียวแบรนด์ | เป้าหมายของจอนั้น (ยืนยัน · ออกใบ) — **หนึ่งปุ่มต่อหนึ่งจอ** |
| `secondary` | น้ำเงิน | สำคัญรองลงมาที่ยังเป็นการ "เพิ่ม/ทำ" ไม่ใช่แค่ปิดหน้าต่าง |
| `danger` | แดง | ยกเลิก · ลบ · ห้าม — ของที่ย้อนยาก |
| `warning` | เหลือง | ของที่ต้องทำเพราะมีอะไรไม่ปกติ (ข้อมูลเก่า · ยังไม่ครบ) |
| `neutral` | ขาว/พื้นการ์ด | ทางเลือกปกติ ที่ไม่เด่นและไม่อันตราย |

`tone` แยกจากบทบาท: **`solid`** = ปุ่มหลักของกล่องนั้น · **`soft`** = สีเดียวกันแบบพื้นอ่อน
สำหรับปุ่มที่อยู่ในแถบแจ้งเตือนหรือข้าง ๆ ของอื่น ซึ่งถ้าใช้พื้นทึบจะแย่งสายตากับปุ่มหลักของจอ

**หมึกของปุ่มพื้นทึบขึ้นกับ "ความสว่างของพื้น" ไม่ใช่ธีม** — ธีมมืดใช้พื้นสีสว่างจึงต้องหมึกเข้ม ·
ธีมสว่างใช้พื้นสีเข้มจึงต้องหมึกขาว · **สีเหลืองใช้หมึกเข้มทั้งสองธีม** เพราะหมึกขาวบนเหลือง
ไม่เคยผ่านเกณฑ์เลย (วัดได้ 2.15:1) ⇒ คนเขียนปุ่มไม่ต้องมานั่งคิด: ใช้คู่โทเคน
`--btn-<บทบาท>-bg` / `-ink` ใน `index.css` ที่จับคู่มาให้แล้ว

**ทำไมถึงต้องมีกติกานี้ — ของเดิมตกเกณฑ์ทั้งหมด (วัด 2026-09-14):** ปุ่มพื้นสีทุกตัวใช้

## 2.2 Admin — ความสูงของปุ่ม: ตัวเลขเดียว ที่เดียว (2026-09-15)

**ปุ่มสั่งงานทุกตัวสูง 36px และตัวเลขนั้นอยู่ที่ `--btn-h` ใน `index.css` ที่เดียว**
หน้าอื่นเขียนแค่คลาส `btn-h` — **ห้ามเขียน `py-*` หรือ `h-9` แทน** ไม่งั้นตัวเลขจะกระจาย
กลับไปอยู่ 19 ไฟล์เหมือนเดิมภายในไม่กี่คอมมิต

**ทำไมถึงต้องมีกติกานี้ (วัด 2026-09-15 ก่อนแก้):** ปุ่มที่มีข้อความ 214 ตัวใน 31 ไฟล์
เลือก `py-*` ของตัวเองทีละจุด ⇒ ปุ่มสั่งงานกระจายอยู่ **7 ความสูง: 28 · 32 · 34 · 36 · 38 ·
40 · 42px** และของที่วางเรียงกันในแถบเดียวก็สูงไม่เท่ากันโดยไม่มีใครตั้งใจ — ตัวอย่างที่เห็นชัด
ที่สุดคือแถบปุ่มท้ายโมดัลเกือบทุกกล่อง: `ยกเลิก` (`px-4 py-2` + `border` = 34px) คู่กับ
`ยืนยัน` (`px-5 py-2` ไม่มี border = 32px) **ต่างกัน 2px ทุกกล่อง** เพราะเส้นขอบถูกนับ
เข้าความสูงแค่ฝั่งเดียว
เจ้าของชี้ปุ่ม **"ส่งออก CSV" (36px)** เป็นต้นแบบ ⇒ 60 ปุ่มใน 19 ไฟล์ย้ายมาที่ 36px พร้อมกัน

**`padding-block: 0` ในคลาสไม่ใช่ของประดับ** — ปุ่มที่เคยเป็น `py-2.5` + `border` รวมแล้ว 42px
ถ้าเหลือ padding ไว้ กล่องจะดันสูงเกิน 36px กลับมาเหมือนเดิมทั้งที่ตั้ง `height` ไปแล้ว
· rule นี้ **อยู่นอก `@layer`** จึงชนะ utility ของ Tailwind เสมอโดยไม่ต้องพึ่งลำดับใน
`className` (เหตุผลเดียวกับกับดัก `border-transparent` ในหัวข้อ 2.1 — ลำดับตัวอักษรใน
`className` ไม่เคยเป็นตัวตัดสิน)

**`Button` ใช้ `btn-h` ทั้ง `sm` และ `md`** ⇒ สองขนาดนั้นต่างกันที่ขนาดตัวอักษร ระยะห่าง
ซ้ายขวา และความมน **ไม่ใช่ความสูง** — หน้าที่ย้ายมาใช้ `Button` จึงได้ความสูงเดียวกับหน้าที่
ยังเขียนปุ่มเองอยู่ ไม่มีช่วงเปลี่ยนผ่านที่สองแบบสูงไม่เท่ากัน

**อะไรที่ไม่ใช้ `btn-h` — คนละงานคนละขนาด ไม่ใช่ข้อยกเว้นที่รอแก้**

| ของ | ความสูงที่ใช้ | เพราะ |
| --- | --- | --- |

โค้ดก้อนเดียวกัน **ยาว 42 บรรทัด เหมือนกันทุกตัวอักษร** ต่างกันแค่ชื่อตัวแปรที่ส่งให้ปุ่มย้อนกลับ
(`policy` / `config`) ไม่ใช่แค่บรรทัด `⚠️ ยังไม่ได้บันทึก` อย่างที่เห็นตอนแรก — ทั้งกล่อง error,
กล่อง "บันทึกแล้วเมื่อ …" และแถบปุ่มทั้งแถบ ตอนนี้อยู่ที่ `admin/SettingsSaveBar.tsx` ที่เดียว
**เป็น 2 component ไม่ใช่ตัวเดียว เพราะแถบสถานะอยู่ในตัวการ์ดส่วนแถบปุ่มอยู่นอกการ์ด**
มี `</div>` ของการ์ดคั่นกลาง — ข้อจำกัดของโครงสร้าง ไม่ใช่การแบ่งเพื่อความสวยงาม
พิสูจน์ว่าหน้าตาไม่เปลี่ยน: เทียบ `className` / `style` / ไอคอน / ข้อความไทย ระหว่างของเดิม
กับ component ใหม่ ตรงกันครบทุกรายการ · `npm --prefix frontend run lint` สะอาด · `run build`
ผ่าน และ bundle ลดจาก **708.07 → 706.82 kB** ซึ่งเป็นหลักฐานว่าสำเนาหายไปจริง

**กติกาจากข้อเท็จจริงนี้** — ไม่ใช่ "ไปรื้อ 15 ไฟล์ให้ใช้ของร่วม" (นั่นคือการรื้อที่หัวไฟล์นี้ห้ามไว้)
แต่คือ:

- **หน้าใหม่ใช้ของใน `logs/ui.tsx` ก่อนเสมอ** ถ้ามันไม่พอ ให้เพิ่ม prop ที่นั่น ไม่ใช่ก๊อปไปแก้
- **ชื่อไฟล์ `logs/ui.tsx` เป็นร่องรอยของประวัติ ไม่ใช่ขอบเขตการใช้งาน** — มันเริ่มจากกลุ่มบันทึก
  แล้วกลายเป็นชุดคอมโพเนนต์ที่สมบูรณ์ที่สุดของแอป การย้ายมันขึ้นไปหนึ่งชั้นเป็นงานที่ทำได้
  แต่ต้องเป็นงานของตัวเอง ไม่ใช่ผลข้างเคียงของงานอื่น
- **สำเนาไม่เคยพังตอนที่ก๊อป มันพังตอนที่ตัวจริงถูกปรับปรุงแล้วสำเนาไม่ได้ตามไป** —
  `logs/format.ts` มีคอมเมนต์บันทึกไว้เองว่ามันเคยเป็นสำเนาแล้วถูกยุบกลับ

## 5. LIFF — สามไฟล์ที่ถือโทเคนชุดเดียวกันคนละสำเนา

`product-search.html` (1,275 บรรทัด) · `quote-edit.html` (4,120) · `register.html` (1,302)
แต่ละไฟล์มี `:root { --green … --border … --radius … }` **ของตัวเอง** ไม่มีไฟล์ CSS กลาง

**เคยขัดกันจริงและไม่มีใครเห็นมาสองปี — แก้แล้ว 2026-09-12:** `--danger-bg` เป็น `#ffe7e7`
ใน `product-search.html` แต่เป็น `#fff0f0` ในอีกสองไฟล์ **และมันต่างกันมาตั้งแต่คอมมิตแรก
(`beff3ad`)** ไม่ใช่การเพี้ยนระหว่างทาง — ซึ่งแย่กว่า เพราะแปลว่าไม่มีจังหวะไหนเลยที่มันเคยตรงกัน
ให้ใครสังเกตเห็น
**ตัวที่แปลกแยกคือตัวที่ตกเกณฑ์ contrast ด้วย** (วัดเอง ไม่ใช่เดา): `--danger` `#d42b2b`
บน `#ffe7e7` ได้ **4.27:1** ซึ่ง **ตก** เกณฑ์ 4.5 ของตัวอักษรขนาดปกติ — และของที่วางบนพื้นนั้น
คือ `.prod-stock-badge.out` (12px/600 = ตัวอักษรปกติ) กับปุ่ม `.btn-remove`
ส่วน `#fff0f0` ได้ **4.54:1** ผ่านพอดี ⇒ ยุบมาที่ `#fff0f0` ทั้งสามไฟล์ ตอนนี้
**ไม่มีโทเคนตัวไหนที่ค่าขัดกันแล้ว** (ที่เหลือต่างแค่ช่องว่างใน `rgba()` ซึ่งเป็นค่าเดียวกัน)
สิ่งที่ยังไม่สมมาตรคือ `quote-edit.html` มีโทเคนเพิ่มอีก 5 ตัวที่อีกสองไฟล์ไม่มี
(`--blue` `--blue-dark` `--success` `--success-hover` `--warning-bg`) — นั่นเป็น "ของเกิน"
ไม่ใช่ "ของขัดกัน" จึงปล่อยไว้ได้

⇒ **แก้สีของ LIFF หนึ่งครั้ง แปลว่าต้องแก้สามที่ และพลาดไปหนึ่งที่จะไม่มีใครเห็นจนกว่าจะเปิด
สองหน้าเทียบกัน** — ตรวจซ้ำได้เร็ว ๆ ด้วยการดึง `:root` ของทั้งสามไฟล์มาเทียบคีย์ต่อคีย์

**กฎวันนี้:** แก้โทเคนตัวไหน **ต้องไล่ให้ครบทั้งสามไฟล์ในคอมมิตเดียวกัน** และเขียนในข้อความ commit
ว่าไล่ครบแล้ว การทำไฟล์ CSS กลางเป็นงานที่ถูกต้องแต่เป็นงานของตัวเอง — ต้องถามเจ้าของก่อน เพราะ
มันแตะทั้งสามหน้าพร้อมกันซึ่งเป็นความเสี่ยงคนละระดับกับการแก้สีหนึ่งค่า

**`@media` มี 1 จุดในทั้งสามไฟล์รวมกัน** (`min-width: 520px` ใน `product-search.html`) และ
`quote-edit.html` ทั้ง 4,120 บรรทัด **ไม่มีเลย** — นี่ไม่ใช่ความผิดพลาด: LIFF เปิดในมือถือเป็นหลัก
และหน้าถูกเขียนมาเป็นคอลัมน์เดียวตั้งแต่ต้น **แต่มันแปลว่าห้ามสมมติว่า "หน้านี้ responsive อยู่แล้ว"**
ของที่กว้างเกินมือถือจะล้นเงียบ ๆ

**`viewport` ไม่เหมือนกันสามไฟล์** — `product-search.html` ใส่ `maximum-scale=1.0,
user-scalable=no` ส่วนอีกสองไฟล์ไม่ใส่ คนสายตาไม่ดีจึงซูมได้สองหน้าและไม่ได้หนึ่งหน้า
เป็นเรื่องที่เจ้าของต้องเลือกว่าจะเอาแบบไหนทั้งชุด ไม่ใช่เรื่องที่แก้เงียบ ๆ ทีละไฟล์

**สองกฎเหล็กของ LIFF ที่มาจากบั๊กจริง**

- **`quote-edit.html`: DOM ไม่ใช่ source of truth** — ห้ามอ่านบริษัท/ผู้ติดต่อจาก DOM
  ต้องใช้ `getSelectedCustomer()` เพราะ `render()` รีเซ็ต dropdown แล้วเติมค่าแบบ async
  อ่านจาก DOM จะได้ค่าว่างหรือค่าเก่าโดยไม่มี error
- **สต็อกบนหน้า LIFF เป็น badge เตือนเท่านั้น ห้ามบล็อก** — client ไม่รู้ว่าสินค้าไหนติดกฎระงับ
  เคยใส่ guard `newQty > stock` แล้วบล็อกสินค้าที่ไม่มีกฎไปด้วยทั้งหมด (ถอดออกใน `e141cea`)
  server เป็นด่านจริงเสมอ

**`sendMessages` ของ LIFF ใช้บน LINE PC ไม่ได้ถาวร** — LINE บน PC เปิด LIFF ในเบราว์เซอร์นอก
จึงต้องมีโมดัลคัดลอกเป็นทางสำรองเสมอ ไม่ใช่ทางเลือกเสริม

## 6. LINE Flex — ข้อจำกัดคือดีไซน์

- **`type` ต้องเป็น literal** — `const msg: FlexMessage = { type: 'flex', … }` หรือ
  `type: 'flex' as const` ไม่งั้น TS มองเป็น `string` แล้ว type error
- **ไม่มีตัวแปร CSS ไม่มีธีม ไม่มี media query** ทุกอย่างเป็นค่าคงที่ในไฟล์
- **ข้อความที่เซลล์เห็นคือสิ่งที่หน้า Admin เอาไปแสดงตัวอย่างด้วย** (`BlockRules.tsx:657`
  แสดงประโยค `❌ ระงับการเสนอราคา …` ที่ Flex จะส่งจริง) — แก้ถ้อยคำที่ `flexTemplates.ts`
  แล้วต้องไล่ดูว่าหน้า Admin ที่ยกมาโชว์ยังตรงอยู่ไหม
- **`npm run diag:line-parity` เป็นด่านของพื้นผิวนี้** — มันเทียบ prompt และรูปร่าง Flex กับ
  golden file ทีละตัวอักษร

## 7. PDF — ความกว้างที่ไม่มีใครหุบได้

- **A4 ตายตัว** (`format: "A4"` ใน `pdfGenerator.ts`) ไม่มี responsive ไม่มีธีม
- **เกือบไม่มีสี** — ทั้งไฟล์มี hex 2 ค่า (`#ef4444`, `#000000`) เอกสารที่ลูกค้าได้รับจึงอ่านได้
  เท่ากันทั้งบนจอและบนกระดาษขาวดำ **อย่าเพิ่มสีเข้าไปโดยไม่ถาม** — ใบเสนอราคาถูกพิมพ์จริง
- **ฟอนต์ Sarabun โหลดจาก Google Fonts** ⇒ ต้องมีเน็ต และในกล่อง Docker มี `fonts-thai-tlwg`
  เป็น fallback ไว้แล้ว เปลี่ยนฟอนต์เมื่อไหร่ต้องคิดถึงทั้งสองทาง
- **ลายเซ็นต้องชื่อ `{salesperson_id}.png`** ใน `data/sale_sigs/` — ชื่อไฟล์คือสัญญา ไม่ใช่ธรรมเนียม
- Chromium ในคอนเทนเนอร์ต้องมี `init: true` ใน `docker-compose.yml` ไม่งั้น zombie process สะสม

## 8. กฎที่ข้ามทุกพื้นผิว

- **ห้ามสื่อความหมายด้วยสีอย่างเดียว** — ทุกที่ที่ใช้สีต้องมีข้อความหรือไอคอนกำกับ
  (กฎนี้เขียนไว้เองแล้วใน `admin/logs/format.ts`) คนตาบอดสีและกระดาษขาวดำเห็นเหมือนกันคือ "ไม่เห็น"
- **เวลาปัก `Asia/Bangkok` เสมอ ห้ามใช้ TimeZone ของเบราว์เซอร์** — ต้องตรงกับตัวกรองวันที่ฝั่ง SQL
  ที่ตีความเป็นวันตามเวลาไทย ไม่งั้นเครื่องที่ตั้งโซนอื่นเห็นวันในตารางไม่ตรงกับช่วงที่กรอง
  · เวลาสัมพัทธ์ใช้ได้ แต่ **เวลาเต็มต้องอยู่ใน tooltip ของทุกจุดที่ใช้ค่านั้น**
- **สามสถานะ ไม่ใช่สถานะเดียว** — ว่าง / กำลังโหลด / พัง ต้องออกแบบครบทั้งสาม
  พื้นที่ว่างเปล่าที่ไม่บอกว่าทำไมถึงว่าง คนอ่านว่า "พัง" (`EmptyState` และ `SkeletonRows`
  มีอยู่แล้วใน `logs/ui.tsx`)
- **ปุ่มที่มีแต่ไอคอนต้องมี `aria-label` ที่เป็นประโยคจริง** (มี 17 ไฟล์ที่ทำแล้ว)
- **ป้ายสต็อกใช้คำและเกณฑ์ชุดเดียวกันทุกพื้นผิว** — `สินค้าหมด` (≤ 0) · `ไม่พอ (เหลือ N)`
  (น้อยกว่าจำนวนที่ขอ) · `พร้อมส่ง N` · ต้นฉบับคือ `liff_pages/product-search.html`
  (คลาส `out`/`low`/`ok`) และหน้า Admin ยกมาใช้คำเดียวกันตั้งแต่ 2026-09-14 — เซลส์คนเดียวกัน
  สลับไปมาสองพื้นผิว ถ้าคำหรือเกณฑ์ต่างกัน เขาจะเชื่อหน้าที่เปิดอยู่แล้วสรุปว่าอีกหน้าผิด

  ปุ่ม ↺ ที่ล้าง **ทั้งประเภทและจำนวนวัน** · บรรทัด "ตั้งเอง" ที่บอกค่าอัตโนมัติไว้ให้เทียบ ·
  สีตามสถานะสต็อก (เขียว = ของครบ · เหลือง = ต้องสั่งผลิต) ต้นฉบับคือ `liff_pages/quote-edit.html`
  หน้า Admin ยกมาทั้งชุด · **คำของประเภทห้ามเขียนซ้ำใน `.tsx`** — ต้องมาจาก `DELIVERY_TYPES`
  ฝั่ง server (ผ่าน `delivery_types` ใน `/preview`) เพราะคำพวกนั้นต้องตรงกับ dropdown ของ Odoo
  ทุกอักขระ · ดู `utils/deliveryTerms.ts`
- **ค่าที่ "คนตั้งเอง" ต้องบอกว่าตั้งเอง และบอกว่าค่าที่ระบบคิดให้คืออะไร** — ทุกช่องที่เขียนทับ
  ของที่ระบบหามาให้ (กำหนดส่ง · เครดิต) ต้องมีครบสามอย่าง: ป้าย **"ตั้งเอง"** · ปุ่มกลับไปใช้ค่าเดิม
  · บรรทัดที่บอกค่าเดิมไว้ ไม่งั้นคนที่มาอ่านใบทีหลังจะเข้าใจว่าเป็นข้อมูลจริงจากฐาน
  (ป้ายใช้ขอบ/ตัวอักษรสีน้ำเงิน + คำว่า "ตั้งเอง" — ไม่ได้สื่อด้วยสีอย่างเดียว)
- **สิทธิ์บนหน้าจอเป็นแค่การซ่อน UI** — `roles` ใน `NAV_GROUPS` ซ่อนเมนู ตัวบังคับจริงคือ
  `requireRole` ฝั่ง backend เสมอ ห้ามถือว่าการซ่อนปุ่มคือการป้องกัน
- **จอที่ "เลียนแบบเอกสาร" ต้องเลียนแบบ *ข้อมูลและลำดับ* ไม่ใช่ *พิกเซล*** (2026-09-17) —
  เอกสารของหน้าขอใบเสนอราคาเรียงบล็อกเหมือนใบ PDF ทุกบล็อก (หัวบริษัท → ผู้ซื้อ/เลขที่ →
  ตาราง 6 คอลัมน์ → สรุปยอดพร้อม VAT และตัวอักษร → เงื่อนไข → ช่องลงนาม) แต่วาดด้วยโทเคน
  ของแอดมินและยุบเป็นการ์ดต่อบรรทัดที่ ≤768px · **ห้ามก๊อป HTML/CSS ของใบมาจาก
  `pdfGenerator.ts`** — สองสำเนาไม่มีวันถูกแก้พร้อมกัน และ A4 ที่ย่อลงจอมือถืออ่านไม่ออก
  คำถาม "ของจริงหน้าตาเป๊ะแบบไหน" ตอบด้วยปุ่มพรีวิว PDF ที่เจนจากตัวจริง (ดู
  `docs/plan-web-quote-request.md` §P)
  · **ใบแยก PM/THT มีบล็อกผู้ซื้อชุดเดียวที่ใบแรก** (เจ้าของสั่ง 2026-09-25) — ใบถัดไปเหลือบรรทัด
  "นามผู้ซื้อ · ข้อมูลลูกค้าและผู้ติดต่อเดียวกับใบ PM ด้านบน" ⇒ ช่องเลือกบริษัท/ผู้ติดต่อมีชุดเดียว
  และไม่ขยับที่ตอนผลตรวจแตกใบ · **PDF ของทุกใบยังมีผู้ซื้อครบ** (ข้อยกเว้นของจอ ไม่ใช่ของกระดาษ)
  · **แถว "ส่วนลดเดิม" ใต้ "สถานที่ส่งของ" เป็นของที่กระดาษไม่มี** (เจ้าของเลือกแบบ C แล้วสั่งย้ายมาที่นี่
  2026-09-25) — ปุ่ม `30%, 30%, 25% ▾` กดแล้วกางตาราง 3 ใบสั่งขายล่าสุด · ข้อมูลชุดเดียวกับหน้า
  "ข้อมูลลูกค้า" (`summarizeDiscounts`) · ไม่พิมพ์ลง PDF · อ่านไม่ได้ต้องบอก "โหลดไม่สำเร็จ" ไม่ใช่
  "ไม่เคยมีใบ" · gate: `scripts/diag/webDiscountHistoryProbe.ts`
  · **ยอดเงินใช้ทศนิยม 2 ตำแหน่งเสมอ ทั้งหน้า** (`money2()` — แก้จาก "เฉพาะบล็อกเอกสาร"
  เมื่อ 2026-09-17 ตามที่เจ้าของสั่ง) เพราะใบพิมพ์ `1,234.00` และ `฿274,628.5` อ่านผิดเป็น
  จำนวนสตางค์ได้ · `money()` เหลือไว้กับของที่ **ไม่ใช่เงิน** เท่านั้น — จำนวนชิ้น สต๊อกคงเหลือ
  เปอร์เซ็นต์ส่วนลด (ตรงนั้น `.00` คือขยะ)
  · **แถบสรุปท้ายจอไม่ใช่ท้ายใบ** — มันมีไว้บอกสิ่งที่กระดาษบอกไม่ได้ (ยอดส่วนลดรวมของทั้งคำขอ)
  ค่าที่ใช้คือ `totals.discount_total` ที่ server ส่งมา **ห้ามบวกเองบนจอ และห้ามเอาไปลงช่อง
  "ส่วนลด" ของใบ** ซึ่งพิมพ์ `0.00` เสมอ · แต่ละช่องปัดทศนิยมของตัวเอง ⇒ ผลบวกคลาดได้ 1 สตางค์
  จึงห้ามวางเลขสามตัวที่ต้องบวกกันลงตัวไว้ติดกันโดยไม่มีคำอธิบาย
- **เอกสารที่แก้ได้ ต้องแก้ได้ "ในคอลัมน์ของมันเอง" ไม่ใช่งอกคอลัมน์ใหม่** (2026-09-17) —
  หน้าขอใบเสนอราคายุบขั้นฟอร์มกับขั้นใบร่างเป็นจอเดียวแล้ว ("เอกสารคือฟอร์ม") ⇒ ช่องกรอก
  จำนวน/หน่วยละ/ส่วนลด อยู่ในคอลัมน์ที่ใบจริงมีอยู่แล้ว และ**ปุ่มลบเป็นไอคอนในเซลล์ "ราคา"**
  ไม่ใช่คอลัมน์ที่ 7 — ใบจริงมี 6 คอลัมน์ เพิ่มคอลัมน์เมื่อไหร่หัวตารางบนจอกับบนกระดาษ
  เริ่มไม่ตรงกัน และคนที่เทียบสองอย่างนี้ทุกวันจะเลิกเชื่อจอ
  · **ช่องกรอกเห็นกรอบตลอดเวลา** (เจ้าของเคาะ) — เอกสารนี้เป็นที่ทำงาน ไม่ใช่รูปถ่ายของใบ
  คนที่เพิ่งเปิดต้องรู้ตั้งแต่แรกเห็นว่าตรงไหนพิมพ์ทับได้ ไม่ใช่ต้องเอาเมาส์ไปไล่ชี้หา
  · **ยังไม่รู้คำตอบให้พูดว่ายังไม่รู้** — ก่อนผลตรวจกลับมา หัวใบเป็นกรอบเส้นประ
  "ระบบจัดใบให้เองตอนตรวจ" และยอดท้ายใบเป็น `—` · ห้ามเดาบริษัทแล้วเอาโลโก้ขึ้นไว้ก่อน
  หัวใบที่ผิดคือสิ่งที่คนเชื่อโดยไม่ตรวจซ้ำ
- **ข้อเสนอที่ระบบยื่นให้เอง ห้ามเป็นโมดัล** (2026-09-17) — ชิป "ใช้ส่วนลดนี้กับรายการอื่น"
  โผล่หลังหยุดพิมพ์ ~0.6 วิ และหายไปเองเมื่อพิมพ์ต่อ กดที่อื่น ย้ายไปช่องอื่น หรือกด Esc
  **โดยไม่มีอะไรเปลี่ยน** — สิ่งที่ผู้ใช้ไม่ได้ขอ ต้องไม่บังคับให้เขาตอบก่อนทำงานต่อ
  · **ข้อเสนอเล็ก ๆ ที่ผูกกับช่องเดียว ให้อยู่ในเซลล์ของช่องนั้น ไม่ใช่กล่องลอย** (เจ้าของเลือก
  2026-09-24 จาก mockup 3 แบบ) — กล่องลอยเดิมสูง ~131px บังแถวถัดไปทั้งแถว และปิดตัวเองทุกครั้ง
  ที่จอขยับ ซึ่งเกิดเองได้โดยไม่มีใครเลื่อน (แถบสถานะเหนือตารางเปลี่ยนความสูงตอนตรวจรายละเอียด
  ⇒ scroll anchoring ของเบราว์เซอร์) จนแวบหายภายใน 0.1 วิ · ราคาที่จ่ายคือแถวนั้นสูงขึ้นชั่วคราว
  · กล่องลอยที่ยังต้องมี ต้องกันขอบด้วย**ความกว้างของตัวเอง** ไม่ใช่ยึดขอบเดียว
  (วัด 2026-09-17: ยึดขอบขวาอย่างเดียว ที่ 390px ขอบซ้ายเลยจอไป 3px)

## 9. รายการห้าม

- **ห้ามเขียน hex ลง `.tsx` / `.ts` ของ admin** — สีอยู่ใน `index.css` ที่เดียว (ตอนนี้ 0 จุด)
- **ห้ามใช้อีโมจิเป็นไอคอนใน Admin** — ใช้ `lucide-react` (อีโมจิบน LIFF/Flex/ข้อความ LINE
  เป็นคนละเรื่องและถูกต้องที่นั่น)
- **ห้ามเพิ่มเบรกพอยต์ใหม่** — ใช้ค่าดีฟอลต์ของ Tailwind ที่มีอยู่
- **ห้ามวาง dropdown แบบ `absolute` ไว้ในกล่องที่มี `overflow-*-auto`** — Tailwind ตั้งให้แกนเดียว
  แต่ตามสเปค CSS อีกแกนที่เป็น `visible` จะถูกคำนวณเป็น `auto` เอง กล่องนั้นจึงกลายเป็น clipping
  context ที่ **ตัดรายการทิ้งและงอก scrollbar ซ้อนขึ้นมาอีกชั้นพร้อมกัน** (วัด 2026-09-14 ที่ตาราง
  สินค้าของหน้า "ขอใบเสนอราคา" ที่ 1280px: ตัดทิ้ง **219px จากรายการสูง 224px** และกล่องตาราง
  งอก scroll 219px) — ท่าที่ถูกคือ `createPortal` ไป `document.body` แล้ววางด้วย `position: fixed`
  จากพิกัดของช่อง เหมือนที่ dropdown สินค้าใน `QuoteRequest.tsx` ทำไว้แล้วด้วยเหตุผลเดียวกัน
- **ห้ามแก้โทเคนของ LIFF ไฟล์เดียว** — สามไฟล์ในคอมมิตเดียวกัน
- **ห้ามเอา React/Vite/build step เข้า `liff_pages/`**
- **ห้ามแก้ไฟล์ใน `public/`** — นั่นคือ build output ของ `frontend/`
- **ห้ามอ่านค่าที่ผู้ใช้เลือกจาก DOM ใน `quote-edit.html`** — ใช้ state
- **ห้ามให้ client บล็อกจากสต็อกดิบ**
- **ห้ามปล่อยพื้นที่ว่างเปล่าโดยไม่บอกเหตุผล**
- **ห้ามแตะไฟล์ UI ก่อนเจ้าของตอบโอเค** (`AGENTS.md` ข้อ 7)

## 10. เช็กลิสต์ก่อนบอกว่าจอเสร็จ

**ความกว้างที่ต้องเปิดดูจริง** — และต้องดูในรอบเดียวกัน ไม่ใช่คนละวัน

```
390     มือถือจริง  ← LIFF ทุกหน้าต้องผ่านความกว้างนี้
640     เส้น sm ของ admin (ฝั่งแคบ)
641     เส้น sm ของ admin (ฝั่งกว้าง) — ต้องไม่มีอะไรค้างจากฝั่งซ้าย
1280    จอทำงานจริงของแอดมิน
A4      ถ้างานนี้แตะ PDF — เปิดไฟล์ที่ออกมาดู ไม่ใช่ดูแค่ HTML
```

**รายการที่ต้องตอบได้ทุกข้อ**

- [ ] จอนี้อยู่พื้นผิวไหน และใช้กติกาของพื้นผิวนั้น ไม่ใช่ของพื้นผิวที่เพิ่งทำงานมา
- [ ] เจ้าของเห็น mockup และตอบโอเคแล้ว
- [ ] ของใหม่ใน admin ประกอบจากคอมโพเนนต์ที่มีอยู่ (หัวข้อ 3) ไม่ได้ก๊อปบล็อกจากหน้าอื่นมาแก้
- [ ] ไม่มี hex ใหม่ใน `.tsx` · **เปิดดูทั้งธีมมืดและธีมสว่าง** (กดปุ่มสลับจริง)
- [ ] ดูครบทั้งสามสถานะ: ว่าง / กำลังโหลด / พัง
- [ ] คำบนจอตรงกับหัวข้อ 4 · ปุ่มไอคอนมี `aria-label`
- [ ] ไม่มีที่ไหนสื่อความหมายด้วยสีอย่างเดียว
- [ ] แตะ LIFF → ไล่ครบทั้งสามไฟล์ที่เกี่ยวข้อง และเปิดบนมือถือจริง (ไม่ใช่แค่ย่อหน้าต่าง)
- [ ] แตะ Flex → `npm run diag:line-parity` ผ่าน · แตะ PDF → `npm run diag:pdf-render` ผ่าน
- [ ] `npm --prefix frontend run lint` และ `run build` ผ่าน **และเปิดดูด้วยตา** —
      build ผ่านไม่ได้แปลว่าหน้าไม่ขาว
- [ ] ถ้ารอบนี้ทำให้ประโยคในไฟล์นี้ไม่จริง แก้ไฟล์นี้ในคอมมิตเดียวกัน

## 11. สิ่งที่ไฟล์นี้จะไม่เก็บ

- **กฎ git และกฎหลาย session** — อยู่ใน `AGENTS.md`
- **เหตุผลของฟีเจอร์และกับดักฝั่ง server** — อยู่ใน `CLAUDE.md` และในหัวไฟล์ของแต่ละไฟล์
- **ถ้อยคำที่บอทพูดกับเซลล์และลูกค้า** — เป็นเนื้อของ `flexTemplates.ts` / `lineHandler.ts`
  คนละเรื่องกับหน้าจอแอดมินโดยสิ้นเชิง
- **ค่าที่ยังไม่มีคนใช้ซ้ำ** — โทเคนหรือคอมโพเนนต์ใหม่เกิดขึ้นเมื่อของซ้ำแล้วเท่านั้น
  **การตั้งของกลางให้ผู้ใช้คนเดียวคือการเดาว่าคนที่สองจะต้องการอะไร** ตัวอย่างที่เดินครบรอบแล้ว:
  ท้ายฟอร์มตั้งค่าซ้ำ 2 ที่ → ยุบเป็น `SettingsSaveBar` (2026-09-12) · เปลือกกล่องโต้ตอบซ้ำ 2 ที่
  → ยุบเป็น `Modal` (2026-09-15 ตอนที่กล่องที่สองเกิดขึ้นจริง **ไม่ใช่ตอนเดาว่าจะมี**) และตอนยุบ
  ก็ **แปลง `ChangePasswordModal` ให้ใช้ของกลางในรอบเดียวกัน** ไม่ทิ้งสำเนาไว้ให้เพี้ยนทีหลัง —
  คลาสทุกตัวยกมาทั้งดุ้น จอเปลี่ยนรหัสผ่านจึงหน้าตาเท่าเดิมทุกพิกเซล และตอนยุบก็ **ไม่ใส่ prop
  ให้ประโยค "มีผลกับใบที่บันทึก/ยืนยันหลังจากนี้ทันที"** เพราะผู้ใช้ทั้งสองรายพูดประโยคเดียวกันจริง
  วันที่มีหน้าที่สามซึ่งความหมายไม่ตรง ค่อยเพิ่ม prop ตอนนั้น — สิ่งที่ห้ามทำคือก๊อปไฟล์ไปแก้ประโยค
  ซึ่งพากลับไปที่เดิม
