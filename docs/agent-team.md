# ทีม agent และ loop การพัฒนา

ใครทำอะไร งานหนึ่งชิ้นเดินยังไง และอะไรที่ **ห้าม**ให้ agent ตัดสินใจเอง
นิยามของแต่ละบทบาทอยู่ใน `.claude/agents/*.md` — ไฟล์นี้คือวิธีใช้พวกเขา

รีโปพี่น้อง `primus-chat` มีไฟล์ชื่อเดียวกันและโครงเดียวกันโดยตั้งใจ (เจ้าของคนเดียวกัน
เครื่องเดียวกันทั้ง dev และ PMSV) **แต่รายชื่อบทบาทไม่เหมือนกันทุกตัว** เพราะสองรีโปมี
ของจริงไม่เหมือนกัน — ความต่างทุกข้อมีเหตุผลเขียนไว้ข้างล่าง

## ทีม

**PM คือ session หลัก ไม่ใช่ subagent** เพราะจุดหยุดถามในโฟลว์ข้างล่างต้องคุยกับเจ้าของ
โดยตรง ถ้า PM เป็น subagent คำถามจะเดินทางผ่านคนกลางหนึ่งชั้น และคำตอบจะกลับมาถึง
คนลงมือช้าไปหนึ่งชั้นเสมอ

| บทบาท | สายงาน | ทำอะไร |
| --- | --- | --- |
| PM (session หลัก) | — | แตกงาน เรียกทีม ถือจุดหยุด merge เขียน `CLAUDE.md` |
| `data-analyst` | อ่าน | เปลี่ยนความรู้สึกเป็นตัวเลข ก่อนใครแก้โค้ด · SELECT เท่านั้น |
| `architect` | อ่าน | บอกว่าจุดแก้ที่ถูกอยู่ตรงไหน และกฎเหล็กข้อไหนถูกกระทบ |
| `fullstack-dev` | เขียน | Node/Express/TypeScript + React admin + LIFF vanilla |
| `qa-tester` | เขียน | รัน/เขียน diag ที่พิสูจน์ — และรู้ว่าตัวไหนเขียนฐานจริง |
| `ai-engineer` | เขียน | สกัดคำสั่งซื้อ, prompt, งบเวลา 48 วิ, eval การจับคู่ |
| `ux-designer` | เขียน | สี่พื้นผิวที่คนมองเห็น (mockup ก่อนเสมอ) |
| `devops` | อ่าน+รัน | สุขภาพระบบ พอร์ต log งานเฝ้าประจำวัน |

**ไม่มี `biz-marketing` ในรีโปนี้ ต่างจาก `primus-chat`** — ที่นั่นมีสคริปต์การขายกับ
knowledge base เป็นข้อมูล runtime ที่ร้านแก้เอง จึงมีของให้บทบาทนั้นถือ ส่วนรีโปนี้
**ไม่มีตาราง/ไฟล์สคริปต์การขายเลย** (วัด 2026-09-12: `grep -ril "sales_script\|knowledge"`
ใน `services/` `db/` `migrations/` = 0) ถ้อยคำที่ลูกค้าอ่านอยู่ใน `utils/flexTemplates.ts`
กับหน้า LIFF ซึ่งเป็นพื้นผิวของ `ux-designer` อยู่แล้ว ⇒ เพิ่มบทบาทที่ไม่มีของถือ
คือจ่ายค่า context เปล่า

**และไม่มี Security Engineer แยก** — กฎขอบระบบ (auth, IP, parameterized query, secret)
อยู่ในกฎเหล็ก `AGENTS.md` B4 ซึ่งอยู่ในเช็คลิสต์ของ architect/qa อยู่แล้ว
งานที่แตะขอบระบบใช้ `/security-review` หลัง merge แทน

**สองวง อย่าจ่ายค่าทั้งทีมทุกงาน**
วงประจำ: PM · data-analyst · architect · fullstack-dev · qa-tester
วงตามเงื่อนไข: ai-engineer (แตะ prompt/โมเดล/การจับคู่) · ux-designer (แตะอะไรที่คนเห็น) ·
devops (แตะ deploy/พอร์ต/ข้อมูลเข้าออก)

## `effort` ต่อบทบาท — ตั้งไว้ในไฟล์แล้ว ไม่ต้องสั่งตอนเรียก

`effort` ใน frontmatter คุมว่ายอมให้โมเดลคิดลึกแค่ไหนก่อนตอบ รับ `low` `medium` `high`
`xhigh` `max` **ถ้าไม่ใส่จะสืบทอดจาก session** ซึ่งแปลว่างานเฝ้าประจำวันจ่ายเท่างานออกแบบ

| effort | บทบาท | ทำไม |
| --- | --- | --- |
| `xhigh` | `architect` · `data-analyst` · `ai-engineer` | ตัดสินว่าแก้ตรงไหน · วัด before/after · ของที่แตะข้ามไฟล์เสมอ |
| `high` | `fullstack-dev` · `qa-tester` · `ux-designer` | ลงมือตามแผนหรือ mockup ที่ตัดสินไปแล้ว ขอบเขตมาจากขั้นก่อนหน้า |
| `medium` | `devops` | เฝ้าและรายงาน ห้ามซ่อมเอง ไม่มีการตัดสินใจอยู่ในงาน |

เกณฑ์: **`xhigh` เฉพาะตอนวางแผน วิเคราะห์ ตัดสินจุดแก้ งานข้ามหลายไฟล์ และการวัด
before/after** ที่เหลือไม่ต้อง — ค่าที่สูงเกินกว่าที่งานต้องการ ถูกจ่ายเป็นเวลารอทุกครั้งที่เรียก
โดยไม่ได้คำตอบที่ดีขึ้นกลับมา

**คีย์สะกดว่า `effort` เท่านั้น และคีย์ที่สะกดผิดถูกมองข้ามเงียบ ๆ ไม่มี error**
จะเปลี่ยนค่าให้แก้ในไฟล์ ไม่ใช่สั่งทับตอนเรียก เพราะค่าที่สั่งทับหายไปพร้อม session นั้น

## ไฟล์ไหนถูกโหลดให้อัตโนมัติ และไฟล์ไหนไม่

วัดจาก session หลักเมื่อ 2026-09-12: **`CLAUDE.md` ถูกโหลดเข้า context ให้เอง**
ส่วน **`AGENTS.md` และ `docs/design.md` ไม่ถูกโหลด** — ทั้งสองไฟล์ถูก "ชี้" จาก `CLAUDE.md`
เท่านั้น ยังไม่ได้ยืนยันว่าฝั่ง subagent เหมือนกันเป๊ะ ⇒ **ไฟล์ agent ทุกตัวจึงสั่งให้เปิด
`AGENTS.md` เอง** ซึ่งถูกต้องทั้งสองทาง

ผลที่ตามมาที่ต้องจำ: อะไรที่เขียนเพิ่มลง `CLAUDE.md` **ทุกงานหลังจากนั้นจ่ายค่าอ่านเสมอ**
ไม่ใช่แค่งานที่เกี่ยวข้อง — นั่นคือเหตุผลของกติกา "ยาวเกิน ~15 บรรทัดให้ย้ายลง `docs/`"

## worktree: หนึ่งงาน หนึ่ง working tree — รวม session หลักด้วย

**ตั้งแต่ 2026-09-14 ทุกงานที่แก้ไฟล์อยู่ในทรีของตัวเอง ไม่มีเกณฑ์ให้ตัดสินอีก**
(`AGENTS.md` A5) เกณฑ์เดิม "แยกเมื่อมีตั้งแต่สองสายพร้อมกัน" แปลว่าต้องรู้ก่อนว่าตอนนี้
มีอีกเซสชันอยู่ไหม ซึ่ง A4 บอกเองว่าไม่มีทางรู้ — ของจริงที่วัดได้ระหว่างเซสชันวันที่ 2026-09-14
ซึ่งเป็นเซสชันที่เขียนย่อหน้านี้เอง: ทรีหลักมีไฟล์ค้างของสายอื่น **15 บรรทัดใน `git status`**
ตั้งแต่เทิร์นแรก และระหว่างที่กำลังแก้เอกสารอยู่นี่เอง อีกสายหนึ่ง **commit เข้าทรีเดียวกัน
ไป 2 คอมมิต** (`1f7f075` + `3681a79` รวม 19 ไฟล์) โดยไม่มีอะไรแจ้งเซสชันนี้เลย
**และหนึ่งในนั้นแก้ `AGENTS.md` ซึ่งเป็นไฟล์ที่เซสชันนี้กำลังแก้อยู่พอดี**

- **subagent สายเขียน** — `isolation: worktree` อยู่ใน frontmatter แล้วทั้งสี่ตัว
  (`fullstack-dev` `qa-tester` `ai-engineer` `ux-designer`) ผู้เรียกไม่ต้องส่งมาอีก
  ถ้า agent พบว่าตัวเองอยู่บน branch ประจำเครื่อง (`dev` บนเครื่อง dev, `main` บน PMSV)
  ให้ **หยุดและรายงาน**
- **PM / session หลัก** — สั่ง `EnterWorktree` ก่อนแตะไฟล์แรก แล้วกลับมา merge ที่ทรีหลัก
  **นี่คือช่องที่กฎเดิมเปิดทิ้งไว้** เพราะ PM ไม่มี frontmatter ให้ใครไปตั้ง `isolation` แทน
  งานที่ PM ลงมือเองจึงเป็นงานเดียวที่ยังอยู่บนทรีร่วมมาตลอด
- **สายอ่าน** — `architect` `data-analyst` `devops` อยู่ทรีหลักตามเดิม **ไม่ใช่ข้อยกเว้น
  แต่เป็นผลของกฎเดียวกัน**: ไม่เขียนไฟล์ก็ไม่มีอะไรให้ทับ · และ `.env` เป็นไฟล์ gitignore
  ที่ไม่เดินทางไปทรีใหม่ บังคับแยกทรีเมื่อไหร่ `data-analyst`/`devops` ต่อฐานจริงไม่ได้ทันที

**ตรวจ `baseRef` ก่อนเชื่อว่าทรีใหม่คือโค้ดล่าสุด** — ค่าเริ่มต้นของ harness แตกจาก
`origin/main` ไม่ใช่ trunk ของเครื่อง (วัด 2026-09-14: ทรีที่ได้ตามหลัง `dev` 22 คอมมิต
และนำหน้าไปอีก 5) `.claude/settings.json` ของรีโปนี้จึงตั้ง `"worktree": { "baseRef": "head" }`
ไว้แล้ว **และไฟล์นั้น commit อยู่ใน repo** ⇒ PMSV ได้ค่าเดียวกันตอน pull

**worktree ไม่ได้แยกฐานข้อมูลและไม่ได้แยกพอร์ต** — diag ที่เขียนฐานในทรีไหนก็เขียนลงของจริง
และ **stash stack เป็นของ repo ไม่ใช่ของทรี** ⇒ `git stash` ยังห้ามตาม A4.3 ในทุกทรี
(pre-approval ของ `git stash push`/`pop` ใน `.claude/settings.json` ถูกถอดออกแล้ว 2026-09-14)

## loop ของงานหนึ่งชิ้น

```
0  PM อ่านคำขอ → งานนี้แตะอะไร → เรียกใครในวงตามเงื่อนไขบ้าง
1  วัดก่อน        data-analyst: เกิดกี่ครั้ง กับกี่แถว เทียบกับอะไร
2  ตัดสินจุดแก้    architect: ไฟล์ไหน ลำดับไหน กฎเหล็กข้อไหนถูกกระทบ ด่านไหนพิสูจน์
   └ แตะหน้าจอ  → ux-designer ส่ง mockup   ⏸ หยุด รอเจ้าของยืนยัน
3  ลงมือ          ทุกคนที่แก้ไฟล์ อยู่ในทรีของตัวเอง — PM ด้วย (`EnterWorktree`)
4  พิสูจน์        qa-tester: tsc --noEmit + diag ที่ตรงกับสิ่งที่แก้ (ทั้งก่อนและหลัง)
5  ตรวจ           PM: เช็คลิสต์ข้างล่าง + /code-review (+ /security-review ถ้าแตะขอบระบบ)
6  merge          จาก checkout ที่ trunk อยู่ → ลบ worktree → ลบ branch
7  บันทึก         แก้ CLAUDE.md / docs ในคอมมิตเดียวกับงาน ไม่ใช่คอมมิตถัดไป
```

**จุดหยุดที่ข้อ 2 ไม่ใช่ธรรมเนียม** — หน้าตาของแอปเป็นของเจ้าของ (`AGENTS.md` A9)
เช่นเดียวกับนโยบายร้าน ราคา และถ้อยคำที่ลูกค้าอ่าน: รายงานต้นเหตุก่อนแล้วรอเลือก
ห้าม agent ตัดสินเอง แม้จะเห็นชัดว่านั่นคือต้นเหตุ
