## กติกา

1. **ทำทุกชั้นที่งานแตะถึง** ชั้นไหนไม่ได้ทำให้เขียน NOT TESTED พร้อมเหตุผล ห้ามละไว้เฉย ๆ
   เพราะคนอ่านจะเข้าใจว่าผ่าน
2. **ตัวเลขในรายงานต้องมาจากการรันในรอบนั้น** ไม่ใช่จากรายงานรอบก่อน และไม่ใช่ตัวเลขในเอกสาร
3. **ห้ามลด assertion · ห้ามลบหรือ skip ข้อที่ตก · ห้ามปิด validation เพื่อให้ผลเป็นสีเขียว**
   ในรีโปนี้หมายความรวมถึง: ห้ามเปลี่ยน `ROLLBACK` เป็น `COMMIT` · ห้ามบันทึก baseline/golden ใหม่ตอนด่านแดง
   (`diag:customer-search -- --save`) · ห้ามใช้สวิตช์ที่เปลี่ยนชุดข้อสอบตอนเทียบก่อน/หลัง (`--refresh-corpus` · `--mine`)
   ถ้าเห็นว่าด่านผิดเอง ให้เขียนเหตุผลในข้อความ commit และแยกเป็นงานของมัน
4. **บั๊กที่แก้ต้องมีด่านที่ตกก่อนแก้และผ่านหลังแก้** ในรีโปนี้ "เทสต์" = ข้อใน `scripts/diag/*` (ข้อใหม่ในไฟล์เดิม
   หรือไฟล์ใหม่ตามรูปที่ `qa-tester` อธิบาย) · รันบนโค้ดก่อนแก้ให้เห็นว่าตก แล้วรันบนโค้ดหลังแก้ให้เห็นว่าผ่าน
   ทั้งสองรอบแนบ output · ถ้าเขียนด่านอัตโนมัติไม่ได้ (เวลาตอบ · ภาพที่แอป LINE แสดงจริง) ให้บันทึกตัวเลขหรือ
   หลักฐานของก่อนแก้และหลังแก้แทน
5. **ด่านที่เป็น gate รันทั้งก่อนและหลังแล้วเทียบผล** (`AGENTS.md` A7.6) — ด่านที่ตกอยู่แล้วก่อนแก้ ให้รายงานว่า
   "ตกก่อนแก้อยู่แล้ว" พร้อมข้อที่ตก และยืนยันว่าหลังแก้ไม่มีข้อใหม่ตกเพิ่ม
6. **ห้ามแตะฐานของร้าน · ห้ามยิง LINE จริง · deploy เป็นการตัดสินใจของเจ้าของ** — ชั้นที่ 2 คือที่เดียวที่ทดสอบ
   แบบเขียนฐานได้ (`AGENTS.md` A1 · B2)
7. **ห้ามใส่ secret รหัสผ่าน token หรือข้อมูลลูกค้าลงรายงานหรือ commit** — ฐานบนเครื่อง dev คือสำเนาข้อมูลลูกค้าจริง
   ⇒ ยกชื่อบริษัท เบอร์โทร หรือเนื้อแชทมาวางในรายงานไม่ได้ ใช้ id หรือจำนวนแทน
8. **เรื่องหน้าตาไม่แก้เอง** (`AGENTS.md` A9) ให้บันทึกไว้ในรายงานหัวข้อ "รอเจ้าของตัดสิน" · บั๊กที่ทำให้ข้อมูลผิด
   ระบบล่ม หรือข้ามสิทธิ์ได้ ให้รายงานเป็น FAIL ร้ายแรงทันที ส่วนจะแก้ในงานนี้เลยหรือไม่ ให้ตัดสินตาม A7.1/A7.2

### สถานะของแต่ละข้อ

| สถานะ | ความหมาย |
| --- | --- |
| PASS | รันแล้ว ผลตรงกับที่คาด และมีหลักฐาน (output ของคำสั่ง · HTTP status · ค่าในฐาน) |
| FAIL | รันแล้วไม่ผ่าน หรือพบบั๊ก |
| BLOCKED | ทดสอบไม่ได้ ต้องบอกว่าขาดอะไร (สิทธิ์ · เครื่องมือ · ข้อมูล · เครื่อง) |
| NOT TESTED | ไม่ได้ทดสอบ ต้องบอกเหตุผล (เช่น "งานนี้ไม่แตะพื้นผิวนี้") |

**FAIL ร้ายแรง** ในรีโปนี้คือ: ราคา ส่วนลด ยอดท้ายใบ หรือเลขที่ใบผิด · ชื่อลูกค้าหรือข้อมูลที่ส่งไป Odoo ผิด ·
บอทหยุดตอบหรือคำสั่งของเซลส์หายเงียบ · แอปไม่บูต · เห็นหรือทำสิ่งที่ role นั้นไม่มีสิทธิ์ได้ · ใบจาก LINE ทะลุกฎ

**ห้ามเขียนว่า "พร้อม merge" หรือ "พร้อม deploy"** ถ้ายังมี FAIL ร้ายแรง หรือมีข้อ BLOCKED/NOT TESTED
ในเรื่องที่งานรอบนี้เปลี่ยน

```bash
npm --prefix frontend run build     # typecheck + build ลง public/ · 13 วิ · แตะ frontend/ เท่านั้น
```

- แล้วรัน **diag ที่ตรงกับสิ่งที่แก้ตามตาราง `AGENTS.md` B5** ทั้งก่อนและหลัง · ด่านที่ไม่แตะฐาน หรือแตะแล้ว ROLLBACK
  เสมอ รันกับฐานของเครื่อง dev ได้เลยไม่ต้องตั้งอะไรเพิ่ม · ด่านกลุ่มที่ "commit แล้วลบใน `finally`" (B2) ต้องรันตาม
  ชั้นที่ 2
- **"ผ่าน" ต้องดูเนื้อ ไม่ใช่ดูแค่ exit code** — `diag:odoo-export` ที่ขึ้น `(ตรวจ 0 ชื่อ)` คือผ่านแบบว่างเปล่า

- ถ้า `npx tsc --noEmit` ชี้ไปที่ `services/__customerServiceEval.gen.ts` แปลว่าเป็นไฟล์ค้างจาก

## ชั้นที่ 2 — ฐาน QA และ server สำหรับทดสอบ

**ฐาน QA = `chatbot_primus_dev` บน Postgres ของเครื่อง dev** (เจ้าของเลือก 2026-10-10 · เปลี่ยนชื่อจาก `chatbot_primus`
วันเดียวกัน) — เป็นสำเนาที่กู้มาจาก dump
ของ prod (`backup/*.dump`) ไม่ใช่ฐานของร้าน · **บน PMSV ไม่มีฐาน QA** ฐานที่นั่นคือของจริง (B2) ⇒ ข้อของชั้นนี้ที่ต้อง
เขียนฐานให้รายงานเป็น BLOCKED ถ้า session อยู่บน PMSV

**ด่านเช็กดูสามอย่างที่ต้องตรงพร้อมกัน** — ข้อเดียวไม่พอ เพราะ `.env` ถูกก๊อปข้ามเครื่องได้:

| สัญญาณ | เครื่อง dev | PMSV (ฐานของร้าน) |
| --- | --- | --- |
| ตัวเซิร์ฟเวอร์ Postgres (`version()`) | `x86_64-windows` | กล่อง Linux |
| ชื่อฐาน | `chatbot_primus_dev` | `chatbot_primus` |
| `NODE_ENV` | `development` (`.env`) | `production` (`docker-compose.yml` + `Dockerfile` ตั้งให้กล่อง) |

ด่านบังคับ `NODE_ENV` ต้องเป็น `development` เป๊ะ ไม่ใช่แค่ "ไม่ใช่ production" ⇒ ไม่ได้ตั้ง = หยุด ·
ด่านเดิมใน `scripts/dev/` ที่ดูแค่ว่าชื่อมีคำว่า "prod" ไหม ยังจับฐานของร้านไม่ได้ ⇒ ใช้คำสั่งนี้ก่อนทุกครั้ง:

```bash
uname -s                            # ต้องขึ้น MINGW… / MSYS… (A1)
node --input-type=module -e "import pg from 'pg';import d from 'dotenv';d.config({quiet:true});const c=new pg.Client({host:process.env.PG_HOST,port:+process.env.PG_PORT,user:process.env.PG_USER,password:process.env.PG_PASSWORD,database:process.env.PG_DATABASE});await c.connect();const {rows:[r]}=await c.query('select current_database() db, version() v');await c.end();const ok=/windows/i.test(r.v)&&r.db==='chatbot_primus_dev'&&/^(localhost|127\.0\.0\.1)$/.test(process.env.PG_HOST)&&process.env.NODE_ENV==='development';console.log(ok?'QA-DB OK':'STOP: ไม่ใช่ฐาน dev',r.db,'|',r.v.split(',')[0],'| NODE_ENV='+process.env.NODE_ENV);process.exit(ok?0:1)"
# → QA-DB OK chatbot_primus_dev | PostgreSQL 18.4 on x86_64-windows | NODE_ENV=development   (2026-10-10)
```

ขึ้น `STOP` = หยุดทั้งชั้น ห้ามหาทางเลี่ยง

**server QA บนพอร์ต 3099** — ไม่ใช่ 3011 (`npm run dev` ของเครื่องนี้ใช้ `.env` จริงทุกตัว) และไม่ใช่ 5180
(พรีวิวร่วมบน PMSV ใช้ฐานของร้าน · `docs/dev-preview.md`):

```bash
QA_JWT=$(node -e "console.log(require('crypto').randomBytes(32).toString('hex'))")
PORT=3099 APP_URL=http://127.0.0.1:3099 PREVIEW_MODE=1 \
LINE_CHANNEL_ACCESS_TOKEN=qa-dummy LINE_CHANNEL_SECRET=qa-dummy gateway_host= \
JWT_SECRET=$QA_JWT npx tsx index.ts        # ขึ้นใน 12–28 วิ บนเครื่องนี้
```

ค่าที่ทับแต่ละตัวมีเหตุผล (`dotenv` ไม่ทับค่าที่ตั้งไว้ใน env แล้ว ⇒ ค่าข้างบนชนะ `.env` เสมอ):

| ค่า | ทำไม |
| --- | --- |
| `LINE_CHANNEL_*=qa-dummy` | webhook จริงที่หลงเข้ามาจะไม่ผ่านลายเซ็น และ reply ออกไปไม่ได้ ⇒ **ไม่มีทางส่งข้อความ LINE จริงได้** |
| `APP_URL=http://127.0.0.1:3099` | `diag:confirm-race` ยิงไปที่ `APP_URL` และค่าใน `.env` ของ dev คือ URL ของ ngrok ⇒ ถ้าไม่ทับ ด่านจะไปยิง server ตัวอื่น |
| `PREVIEW_MODE=1` | ไม่เริ่มตัวตั้งเวลา auto sync (ซึ่งจะดึง Odoo) และตัวลบร่างเว็บที่ค้างเกิน 7 วัน · ปิดการอัปลายเซ็น |
| `gateway_host=` | ถ้ามีอะไรหลุดไปเรียก sync ก็ยิง gateway ของ Odoo ไม่ได้ |
| `JWT_SECRET` สุ่มใหม่ | token ของ server QA กับของ `.env` ใช้แทนกันไม่ได้ (วัด: token QA → 200 · token ที่เซ็นด้วย secret ใน `.env` → 401) |

- LLM ยังเรียกของจริง (`DEEPSEEK_API_KEY` จาก `.env`) — มีค่าใช้จ่ายต่อครั้ง แต่ไม่มีผลกับร้าน (บันทึกความจำ `dev-verify-local-only`)
- token แอดมินสำหรับยิง API: `JWT_SECRET=$QA_JWT npx tsx scripts/dev/mintAdminToken.ts` (ใช้บัญชีแรกที่เป็น superadmin/admin)
- **ปิด server ต้องตามฆ่าจากเจ้าของพอร์ต** — Ctrl-C หรือ `TaskStop` ฆ่าแค่ตัวแม่ แต่ node ตัวหลานยังถือ 3099 อยู่
  (วัด 2026-10-10) ⇒ `Get-NetTCPConnection -LocalPort 3099 -State Listen` แล้ว `Stop-Process` ทั้งตัวนั้นและ
  `ParentProcessId` ของมัน · ก่อนเปิดให้ดูก่อนว่าใครถือ 3099 อยู่ — session อื่นอาจใช้อยู่ ห้ามฆ่าของเขา (ความจำ `preview-server-port-and-cleanup`)

**ด่านที่เขียนฐานแล้วลบใน `finally`** (`web-quote` · `confirm-race` · `line-parity` · `price-approval` · `pdf-issuer` ·
`shipping-fee` · `company-name` · `product-match-line` · ข้อ 6 ของ `local-contacts` — รายชื่อเต็มอยู่ B2/B5)
**รันบนฐานของ dev ได้โดยไม่ต้องขอเพิ่ม** หลังผ่านคำสั่งเช็กข้างบน · ด่านที่ต้องมี server ให้ส่งพอร์ตของ server QA ไปด้วย:

```bash
PORT=3099 APP_URL=http://127.0.0.1:3099 npm run diag:confirm-race     # ผ่าน 4 วิ (2026-10-10)
```

- ถูกฆ่ากลางทาง = แถวทดสอบค้างในฐาน dev ⇒ เขียนไว้ในรายงาน ถ้าจะล้างทั้งหมดให้กู้ฐาน dev ใหม่จาก dump (ความจำ
  `restore-auto-dump-on-dev`) · ห้ามตั้ง timeout สั้นจนด่านถูกตัดกลางทาง
- ด่านที่ต้องมี API ของทรีตัวเอง (`EH_PORT` · `QH_PORT` · `RP_PORT` · `QPM_PORT` = 3099) ใช้ server ตัวเดียวกันนี้ที่เปิดจากทรีของงาน

**webhook — ยิงได้แค่แบบที่ต้องถูกปฏิเสธ** · ห้ามยิง webhook ที่เซ็นถูกเข้า server QA (มันจะไปถึง `handleEvent`
แล้วพยายามตอบ LINE) · ทางของ `handleEvent` ใช้ด่านที่แทน LINE ด้วยตัวปลอมอยู่แล้ว (`line-parity` · `product-match-line`
· `abort-check` · `webhook-recorder`)


## ชั้นที่ 5 — สิ่งที่ผู้ใช้ควรลองเองก่อน deploy

เขียน **"สิ่งที่คุณควรลองเองก่อน deploy"** 3–5 ข้อไว้ในรายงาน เป็นขั้นตอนที่เจ้าของทำเองได้ด้วยบัญชีของตัวเอง
ไม่ใช่บัญชีที่ด่านสร้าง และไม่ใช่ token ที่ automation ถือไว้ (เจ้าของเลือก 2026-10-10):

- **Admin · PDF** — ลองบน server QA ที่ `http://127.0.0.1:3099` ล็อกอินด้วยรหัสของตัวเอง (บัญชีในฐาน dev
  คือสำเนาของบัญชีจริง) · agent เปิด server ไว้ให้ และบอกว่าปิดยังไง
- **LIFF · Flex** — ต้องใช้แอป LINE กับ LINE OA จริง ⇒ **ลองได้หลัง deploy เท่านั้น** · เขียนเป็นขั้นตอนที่ทำหลัง deploy
  (เช่น "พิมพ์ข้อความนี้ในห้องแชท แล้วการ์ดต้องมีปุ่ม …") และในรายงานต้องบอกตรง ๆ ว่าก่อน deploy ยังไม่มีใครเห็นของจริง

แต่ละข้อต้องบอกว่า: ทำอะไร · ที่ไหน · ควรเห็นอะไร · ถ้าไม่เห็นแปลว่าอะไร

ถ้างานแตะ login รหัสผ่าน หรือสิทธิ์ ให้ตอบในรายงานด้วยว่าถ้าแอดมินเข้าระบบไม่ได้หลัง deploy จะกู้กลับมาอย่างไร
(`DEPLOY.md` หัวข้อ "ตั้ง / กู้รหัสผ่านผู้ใช้ Admin Portal ด้วย SQL")

## รายงาน

อยู่ในข้อความส่งงานทุกครั้ง (กฎ `AGENTS.md` B9) ตามลำดับนี้

1. **ข้อสรุป** — พร้อม merge หรือไม่ ถ้าไม่พร้อม ติดอะไร
2. **ตารางผลแยกตามชั้น** — ทุกชั้นต้องมีแถว แม้ไม่เกี่ยว (NOT TESTED + เหตุผล) · คอลัมน์: ชั้น · ข้อ · คำสั่ง · ผลก่อน · ผลหลัง · สถานะ
3. **บั๊กที่แก้** — อาการ · สาเหตุ · ด่านที่ตกก่อนแก้และผ่านหลังแก้ (แนบ output ทั้งสองรอบ)
4. **รอเจ้าของตัดสิน** — เรื่องหน้าตา หรือเรื่องที่มีคำตอบที่ถูกได้มากกว่าหนึ่งแบบ
5. **สิ่งที่คุณควรลองเองก่อน deploy** (ชั้นที่ 5)

บอกด้วยว่ารันบนเครื่องไหน (dev หรือ PMSV) และอะไรที่ยังไม่ได้รันบนอีกเครื่อง — ด่าน `diag:migrations` ·
`diag:backup` และการ build ในกล่อง Docker มีบนเครื่อง PMSV เท่านั้น
