## 2. ของเดิมที่ต้องเข้าใจก่อน — ไม่งั้นแก้ผิดจุด

### 2.1 กฎมีสามชั้นอยู่แล้ว และอยู่ที่ฟังก์ชันเดียว

`services/quotationService.ts` — `blockingViolations()` · `violationKey()` · `isBypassableViolation()`
· `requiresPriceApproval()` คือกติกาเดียวของทั้งระบบว่า "ข้อไหนทะลุได้ ด้วยอะไร":

```
ติ๊กรับทราบเองได้   BLOCKED · OUT_OF_STOCK · MOQ_VIOLATION · CUSTOMER_BLACKLISTED · CUSTOMER_CREDIT_HOLD
ต้องมีคนอนุมัติ      MIN_PRICE_VIOLATION            (APPROVAL_REQUIRED_TYPES)
ทะลุไม่ได้ทุกกรณี     SYSTEM_ERROR                   (isBypassableViolation)
```

**ของใหม่ไม่ได้เพิ่มชั้นที่สี่** — มันทำให้ "ข้อไหนอยู่ชั้นไหน" กลายเป็นค่าที่ **ขึ้นกับ role
ของคนที่กำลังออกใบ** แทนที่จะเป็นค่าคงที่ของทั้งระบบ

### 2.2 การปลดล็อกผูกกับ "ใบ" ไม่ใช่ "endpoint" — ข้อนี้ห้ามเปลี่ยน

`PUT /api/quotation/:id` และ `POST /api/quotation/:id/confirm` เป็นของที่ **LIFF ของเซลส์ใช้
ร่วมกับหน้าเว็บ** ⇒ ถ้าเอา role ไปตรวจที่ endpoint พวกนี้ **ใบจาก LINE จะเปลี่ยนพฤติกรรม
ตามไปเงียบ ๆ** ตัวปลดล็อกจริงคือคอลัมน์บนแถวของใบ:

| คอลัมน์ | ใครเขียน | ใบจาก LINE |
| --- | --- | --- |
| `quotations.rule_overrides.acknowledged_keys` | `createDraftFromWeb()` ตอนสร้างร่าง | `NULL` เสมอ |
| `quotations.price_approval` | คิวอนุมัติ | `NULL` เสมอ |

⇒ **จุดบังคับใช้ของ role ใหม่คือ "ตอนตัดสินว่าจะเขียนคีย์อะไรลงใบ" ไม่ใช่ `requireRole` ของ route**
นี่คือประโยคที่สำคัญที่สุดในเอกสารนี้ ทำผิดข้อนี้ = ใบจาก LINE โดนลูกหลงโดยไม่มีอะไรฟ้อง

### 2.3 วันนี้สิทธิ์กระจายอยู่ 3 ที่ และไม่มีที่ไหนแก้ได้จากหน้าจอ

| ที่ | รูปแบบ | ตัวอย่าง |
| --- | --- | --- |
| `index.ts` | `requireRole(...)` ต่อ route | 94 จุด — `admin` ล้วน 58 · `admin+approver+subadmin` 24 · `admin+user` 9 · `admin+approver` 3 (วัด 2026-09-18) |
| `services/quotationService.ts` | ค่าคงที่ `APPROVAL_REQUIRED_TYPES` | กฎข้อไหนต้องอนุมัติ (ทั้งระบบ ไม่แยก role) |
| `frontend/src/admin/AdminApp.tsx` | `roles: ['admin','approver','subadmin']` ต่อเมนู | ซ่อน UI เท่านั้น ไม่ใช่ด่านจริง |

### 2.4 ขนาดที่เกี่ยวข้อง (วัด 2026-09-18)

`quotations` **2,069 แถว** · ใบที่ออกจากหน้าเว็บ **1 ใบ** · มี `idx_quotations_user_id` อยู่แล้ว
⇒ ตัวกรอง "เฉพาะใบของตัวเอง" ไม่มีประเด็นเรื่องความเร็วในระดับนี้ · `admin_users` 8 แถว

## 3. ข้อตัดสินใจที่เสนอ

### 3.1 ตารางเดียว: `role_permissions` (role × ความสามารถ → โหมด)

```sql
role_permissions(role, capability, mode, updated_by, updated_at)
  mode ∈ ('deny', 'approval', 'allow')
```

**ตารางเดียวรับทั้งสองชนิด** เพราะสวิตช์เปิด/ปิดคือกรณีที่ใช้แค่ `deny`/`allow` ส่วนกฎใช้ครบสามค่า
— ถ้าแยกสองตารางจะได้ cache สองตัว หน้าจอสองหน้า และด่านตรวจสองชุด เพื่ออธิบายเรื่องเดียวกัน

| โหมด | กับ "กฎ" | กับ "ความสามารถ" |
| --- | --- | --- |
| `allow` | ติ๊กรับทราบเองได้ (ของเดิม) | ทำได้ |
| `approval` | ต้องส่งให้ผู้อนุมัติ | *(ไม่ใช้ — แคตตาล็อกไม่เปิดให้เลือก)* |
| `deny` | ออกใบไม่ได้ ต้องแก้ใบ | ทำไม่ได้ (403) |

### 3.2 แคตตาล็อกอยู่ในโค้ด · ค่าอยู่ใน DB · **ตารางว่าง = พฤติกรรมวันนี้เป๊ะ**

`config/capabilities.ts` ถือ "รายการความสามารถทั้งหมด + ค่าเริ่มต้นของแต่ละ role" เพราะ
ความสามารถหนึ่งตัวมีความหมายก็ต่อเมื่อมีโค้ดเรียกใช้มัน — ของที่เพิ่มจากหน้าจอได้ต้องเป็น **ค่า**
ไม่ใช่ **ชนิด** · DB เก็บเฉพาะแถวที่ "ต่างจากค่าเริ่มต้น"

⇒ **ล้างตารางทิ้งเมื่อไหร่ ระบบกลับไปเป็นเหมือนวันนี้ทุกข้อ** นี่คือด่านกัน regression ที่ถูกที่สุด
และเป็นสิ่งที่ `diag` ข้อแรกต้องพิสูจน์

### 3.3 `SYSTEM_ERROR` ไม่มีสวิตช์ — ไม่อยู่ในแคตตาล็อก

"ตรวจกฎไม่สำเร็จ" ไม่ได้แปลว่า *ใบนี้ผิดกฎข้อนี้* แต่แปลว่า **ยังไม่รู้ว่าผิดหรือไม่** การเปิดช่อง
ให้ตั้งค่าเป็น `allow` ได้ คือการเปลี่ยนด่าน fail-closed ให้เป็น fail-open ด้วยปุ่มบนหน้าจอ
(เหตุผลเต็มอยู่ที่ `isBypassableViolation()`) · **ห้ามใส่เข้าเมทริกซ์ ไม่ว่าใครจะขอ**

### 3.4 `admin` แก้ไม่ได้ — ทั้งแถวถูกล็อกไว้บนหน้าจอ

เหตุผลเดียวกับ `assertNotLastAdmin()` ที่มีอยู่แล้ว: ระบบที่ล็อกคนสุดท้ายออกจากตัวเองได้
คือระบบที่ต้องแก้ด้วย `psql` ตอนตีสอง · `admin` = `allow` ทุกข้อเสมอ อ่านจากโค้ด ไม่อ่านจากตาราง

### 3.5 ผูกบัญชีเข้ากับ **รหัสพนักงานขาย** — ตารางเชื่อม `admin_user_salespersons`

คำว่า "ใบของตัวเอง" ตอบไม่ได้ถ้าไม่รู้ว่าบัญชีนี้คือเซลส์คนไหน — และ **กุญแจที่ถูกต้องคือ
รหัสพนักงานขาย ไม่ใช่ `user_id`** (เจ้าของเคาะ 2026-09-18) เพราะคนหนึ่งคนมีได้หลาย `user_id`:

```
web:<adminId>:<spUserId>   ใบที่ออกจากหน้าเว็บ (แถวพร็อกซี — คัดลอก salesperson_id มาด้วย)
<spUserId>                 ใบที่ออกทาง LINE — บัญชี LINE ซ้ำกันได้ (วัดแล้ว 5 คน มีคนละ 2 บัญชี)
```

**และผูกได้มากกว่าหนึ่งรหัสต่อบัญชี** — ไม่ใช่การเผื่ออนาคต มันมีอยู่แล้ววันนี้ (วัด 2026-09-18):

| รหัส | ชื่อในระบบ | ใบ | ใช้ล่าสุด |
| --- | --- | --- | --- |
| 441 | `คุณวิรุณ` | 44 | 2026-09-14 |
| 688 | `คุณวิรุณ ภาคอีสาน ` | 29 | **2026-09-18** |

สองรหัสนี้เป็น **คนเดียวกัน** (`employee_quotation_id` = `วิรุณ ผ่านจังหาร` ทั้งคู่) และ **ยังใช้งาน
อยู่ทั้งคู่** ⇒ ผูกได้รหัสเดียวเมื่อไหร่ เขาจะมองไม่เห็นใบของตัวเอง 29 หรือ 44 ใบ · เป็นคนเดียว
ในระบบที่เป็นแบบนี้ (เซลส์ 37 แถว) แต่ต้นทุนของการรองรับคือตารางเชื่อมแทนคอลัมน์เดียว
ซึ่งถูกกว่าการมาแก้ทีหลังมาก

```
admin_user_salespersons(admin_user_id, salesperson_id)     PK = ทั้งคู่
```

ตอบสามเรื่องพร้อมกัน: **(1)** ตัวกรอง "เฉพาะใบของตัวเอง" = `salesperson_id IN (รหัสที่ผูกไว้)`
(นิยามเต็มที่ **§13.7 ข้อ 7**) · **(2)** dropdown "ออกใบในนาม" ของ `salesperson` เหลือเฉพาะ
**รหัสของตัวเอง** — ปกติมีตัวเลือกเดียว = ถูกล็อกโดยปริยาย · คนที่มีสองรหัสเลือกได้ว่าจะออกในนาม
สาขาไหน ซึ่ง **ยังเป็นตัวเขาเองทั้งสองทาง** · **(3)** ใบที่ออกทาง LINE โผล่ในประวัติของเขาด้วย

ไม่มีแถว = บัญชีนี้ไม่ผูกกับเซลส์คนไหน (แอดมิน/ผู้เสนอราคา)
· ⚠️ **ไม่มีสิทธิ์ไหนขึ้นกับตารางนี้** มันตอบแค่ "ใบไหนเป็นของใคร" — สิทธิ์อยู่ในเมทริกซ์ที่เดียว
ไม่งั้นจะมีสิทธิ์สองแหล่งที่ขัดกันได้
· **ไม่มี FK ไป `salesperson`** เพราะ `salesperson_id` ไม่ unique ในตารางนั้น ⇒ ตรวจว่ามีอยู่จริง
ที่ชั้น API + `diag` ไล่หาแถวที่ชี้ไปรหัสที่ไม่มีแล้ว

### 3.6 คิวอนุมัติรับกฎชนิดอื่นด้วย — และผูกกับ "ตัวเลขที่อนุมัติ" เหมือนที่ราคาทำ

วันนี้ `approvedViolationKeys()` เทียบ **ราคา** ไม่ใช่แค่ชื่อรุ่น (คนอนุมัติ ฿100 ต้องไม่กลายเป็น
อนุมัติ ฿10 ให้ด้วย) กฎชนิดอื่นต้องใช้หลักเดียวกัน ไม่งั้นการอนุมัติหนึ่งครั้งกลายเป็นใบเบิกทางถาวร:

| กฎ | ตัวเลขที่ผูก | ขอใหม่เมื่อ |
| --- | --- | --- |
| `MIN_PRICE_VIOLATION` | ราคาที่อนุมัติ | ราคาต่ำลงกว่าที่อนุมัติ *(ของเดิม)* |
| `OUT_OF_STOCK` | จำนวนที่อนุมัติ | จำนวน **มากขึ้น** กว่าที่อนุมัติ (สั่งเกินของที่มีหนักขึ้น) |
| `MOQ_VIOLATION` | จำนวนที่อนุมัติ | จำนวน **น้อยลง** กว่าที่อนุมัติ — **ทิศตรงข้ามกับของหมด** |
| `BLOCKED` · `CUSTOMER_BLACKLISTED` · `CUSTOMER_CREDIT_HOLD` | ไม่มีตัวเลข — คีย์ล้วน | คีย์เปลี่ยน (คนละรุ่น/คนละลูกค้า) |

> **แก้จากร่างแรก (ตอนลงมือ 2026-09-18):** ร่างแรกเขียนสองข้อบนรวมกันว่า "ขอใหม่เมื่อจำนวน
> มากขึ้น" ซึ่งถูกกับของหมดแต่**กลับด้านกับ MOQ** — MOQ ผิดเพราะสั่ง *น้อยกว่า* ขั้นต่ำ
> การสั่งน้อยลงจึงเป็นทิศที่ผิดหนักขึ้น เกณฑ์ที่ใช้จริงคือ **"แก้ไปทางที่ผิดหนักขึ้นกว่าที่
> คนอนุมัติเห็น = ต้องขอใหม่"** ซึ่งให้ทิศตรงข้ามกันของสองข้อนี้
> · และกฎที่ไม่มีตัวเลขผูกต้องเทียบ **คีย์ที่อยู่ในคำขอจริง** ไม่ใช่แค่ชนิดกฎ ไม่งั้นอนุมัติ
> "ระงับรุ่น A" จะปลด "ระงับรุ่น B" ให้ด้วย (ด่านข้อ 11 จับได้ตอนเขียน)

### 3.7 คอลัมน์ `price_approval` **ไม่เปลี่ยนชื่อ**

ชื่อจะเพี้ยนความหมายไปนิด (มันคือ "คำขออนุมัติของใบ" ไม่ใช่เฉพาะราคาแล้ว) แต่การเปลี่ยนชื่อ
ต้องไล่แก้ guard `AND price_approval IS NULL` ที่ค้ำไม่ให้ร่างที่รออนุมัติถูกกวาดทิ้ง
(`insertDraftQuotations` · `reviseQuotation`) ซึ่งพลาดข้อเดียว = คำขอที่รออยู่หายทั้งใบเงียบ ๆ
⇒ **จ่ายด้วยคอมเมนต์หนึ่งบรรทัด ถูกกว่าจ่ายด้วยการไล่ rename** · หัวคอลัมน์ในเอกสารนี้คือที่อธิบาย

## 4. แคตตาล็อกความสามารถ (ข้อเสนอรอบแรก)

**ค่าเริ่มต้น** = พฤติกรรมวันนี้ ยกเว้นคอลัมน์ `salesperson` ซึ่งเป็นของใหม่ทั้งคอลัมน์

### ก. การทะลุกฎ — `rule.<TYPE>`

| ความสามารถ | admin | approver | subadmin | **salesperson** |
| --- | --- | --- | --- | --- |
| `rule.BLOCKED` (สินค้าระงับ) | allow | allow | allow | **approval** |
| `rule.OUT_OF_STOCK` (ของหมด) | allow | allow | allow | **approval** |
| `rule.MOQ_VIOLATION` (ต่ำกว่าขั้นต่ำสั่งซื้อ) | allow | allow | allow | **approval** |
| `rule.CUSTOMER_BLACKLISTED` | allow | allow | allow | **deny** |
| `rule.CUSTOMER_CREDIT_HOLD` | allow | allow | allow | **deny** |
| `rule.MIN_PRICE_VIOLATION` | approval | approval | approval | **approval** |
| ~~`rule.SYSTEM_ERROR`~~ | — ไม่อยู่ในเมทริกซ์ (§3.3) | | | |

ค่าเริ่มต้นสองตัวที่เสนอเป็น `deny`: blacklist กับเครดิตค้าง เป็นเรื่องของ **ตัวลูกค้า** ไม่ใช่
ของใบ — คนที่ปลดควรเป็นคนที่แก้สถานะลูกค้าได้ ไม่ใช่คนที่กดอนุมัติใบทีละใบ · **เปลี่ยนจาก
หน้าจอได้ทันทีถ้าเจ้าของเห็นต่าง**

### ข. การทำงานกับใบ — `quote.*` / `approval.*`

| ความสามารถ | admin | approver | subadmin | **salesperson** | จุดบังคับใช้ |
| --- | --- | --- | --- | --- | --- |
| `quote.create` ขอใบเสนอราคา | ✔ | ✔ | ✔ | **✔** | `POST /webquote/drafts` |

**ความสามารถที่ถูก "ถอดออกจากทุก role"** — การตั้งชื่อผู้เสนอราคาของตัวเอง
(`PUT /api/admin/webquote/me`) ไม่ใช่ความสามารถที่ปิด/เปิดได้อีกต่อไป แต่ถูกย้ายไปเป็นของผู้ดูแล
ทั้งหมด (§13.3) — ของที่ "ไม่มีใครควรทำได้" ไม่ควรมีสวิตช์ เพราะสวิตช์คือคำเชิญให้เปิด

**รอบแรกไม่เอาเมนูตั้งค่ากฎเข้าเมทริกซ์** (โปรโมชัน · กฎราคา · MOQ · บล็อกสินค้า · จัดการผู้ใช้)
— ยังเป็นของ `admin` ล้วนเหมือนเดิม เพราะมันคือ "คนที่ตั้งกฎ" ซึ่งเป็นคำถามคนละข้อกับ
"คนที่ทำงานกับใบ" และการเปิดให้ตั้งค่าได้ก่อนที่จะมีใครขอ คือพื้นที่ผิดพลาดที่ได้มาฟรี ๆ

## 5. รูปของข้อมูล

```sql
-- migrations/changes/2026-MM-DD_NN_role_permissions.sql
CREATE TABLE IF NOT EXISTS public.role_permissions (
  role        varchar(20) NOT NULL,
  capability  varchar(64) NOT NULL,
  mode        varchar(16) NOT NULL,
  updated_by  integer REFERENCES public.admin_users(id) ON DELETE SET NULL,
  updated_at  timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (role, capability),
  CONSTRAINT role_permissions_mode_check CHECK (mode IN ('deny','approval','allow'))
);

-- role ใหม่ต้องแก้ CHECK เดิมให้ตรงกับ Role ใน config/auth.ts
ALTER TABLE public.admin_users DROP CONSTRAINT IF EXISTS admin_users_role_check;
ALTER TABLE public.admin_users ADD  CONSTRAINT admin_users_role_check
  CHECK (role IN ('admin','approver','subadmin','salesperson','user'));

-- บัญชีนี้คือเซลส์รหัสไหน (§3.5) — หลายรหัสต่อบัญชีได้ · ไม่มีสิทธิ์ใดผูกกับตารางนี้
-- ไม่มี FK ไป salesperson เพราะ salesperson_id ไม่ unique ที่นั่น (5 คนมี 2 แถวต่อรหัส)
CREATE TABLE IF NOT EXISTS public.admin_user_salespersons (
  admin_user_id  integer     NOT NULL REFERENCES public.admin_users(id) ON DELETE CASCADE,
  salesperson_id varchar(50) NOT NULL,
  created_at     timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (admin_user_id, salesperson_id)
);

-- ครั้งล่าสุดแอดมินออกใบในนามรหัสไหน (§13.4) — ย้ายมาจาก localStorage
-- คนละความหมายกับตารางบน และไม่ใช่สิทธิ์ · ค่าที่อ่านมาต้องเทียบกับรายชื่อจริงก่อนใช้เสมอ
ALTER TABLE public.admin_users ADD COLUMN IF NOT EXISTS acting_salesperson_id varchar(50);

-- 1 ชื่อผู้เสนอราคา = 1 บัญชี (เจ้าของเคาะ 2026-09-18 · §13.7 ข้อ 5)
-- ต้องอยู่ไฟล์เดียวกับการเคลียร์ชื่อที่ชนกัน ไม่งั้น migration ล้มกลางคัน
CREATE UNIQUE INDEX IF NOT EXISTS admin_users_employee_quotation_id_key
  ON public.admin_users (employee_quotation_id) WHERE employee_quotation_id IS NOT NULL;
```

* **ไม่มี `COMMENT ON`** — อธิบายด้วย `--` ในไฟล์ migration (กฎเหล็ก `AGENTS.md` B4)
* **ยุบเข้า `migrations/schema.sql` ในคอมมิตเดียวกัน**
* ไม่ seed ข้อมูลตั้งต้น — ตารางว่างคือค่าเริ่มต้นที่ถูกต้องอยู่แล้ว (§3.2)

## 6. เส้นทางใหม่ทั้งเส้น (เซลส์ออกใบที่ติดกฎ)

```
เซลส์กดพรีวิว
  └─ POST /webquote/preview → validateQuotationItems()  (ด่านเดิม ไม่แตะ)
       └─ ประกอบคำตอบด้วย capsOf(req.admin.role):
            allow    → คีย์นั้นอยู่ใน override_keys  (โมดัลมีช่องให้ติ๊ก — ของเดิม)
            approval → คีย์นั้นอยู่ใน approval_keys  (โมดัลบอก "ต้องส่งขออนุมัติ")
            deny     → คีย์นั้นอยู่ใน blocked_keys   (โมดัลบอก "แก้ใบก่อน ติดต่อแอดมิน")
เซลส์กดยืนยัน
  └─ POST /webquote/drafts → createDraftFromWeb()
       ├─ deny เหลืออยู่      → 422 RULE_VIOLATION      (จบ ไม่สร้างร่าง)
       ├─ approval เหลืออยู่  → สร้างร่าง + เปิดคำขออนุมัติ (ร่างค้างใน DB จริง)
       └─ allow               → เขียน acknowledged_keys ลงใบ แล้วออกใบตามปกติ
ผู้อนุมัติกด
  └─ decideApproval() → confirmQuotationById()          (ตัวเดียวกับปุ่มยืนยันปกติ)
```

**สิ่งที่ไม่เปลี่ยนเลยแม้แต่บรรทัดเดียว:** `POST /api/quotation/:id/confirm` · `PUT /api/quotation/:id`
· `blockingViolations()` ตอนยืนยัน — เพราะคีย์ที่อยู่บนใบถูกคัดมาตั้งแต่ตอนสร้างร่างแล้ว
⇒ **ใบจาก LINE ไม่มีอะไรเปลี่ยน** (ไม่มีแถว ack ให้คัดตั้งแต่แรก)

## 8. หน้าจอ (ก่อนเขียนโค้ดต้องอ่าน `docs/design.md`)

อยู่ใต้กลุ่มเดียวกับ "จัดการผู้ใช้งานระบบ" · ตารางเดียว **แถว = ความสามารถ · คอลัมน์ = role**
จัดกลุ่มเป็น "การทะลุกฎ" กับ "การทำงานกับใบ"

* ช่องของกฎเป็นตัวเลือกสามค่า · ช่องของความสามารถเป็นสวิตช์
* คอลัมน์ `admin` เป็นสีเทาอ่านอย่างเดียว พร้อมคำอธิบายว่าทำไมแก้ไม่ได้ (§3.4)
* ช่องที่ต่างจากค่าเริ่มต้นมีจุดกำกับ + ปุ่ม "คืนค่าเริ่มต้น" ต่อแถว — คนตั้งค่าต้องมองออกว่า
  ตัวเองแก้อะไรไปแล้วบ้าง โดยไม่ต้องจำ
* **มือถือ**: ตาราง 5 คอลัมน์ที่ย่อลงเฉย ๆ อ่านไม่ออกที่ 390px ⇒ สลับเป็นการ์ดต่อความสามารถ
  (กฎ `AGENTS.md` A: responsive เป็นครึ่งหนึ่งของดีไซน์ ไม่ใช่งานเก็บท้าย)
* บันทึกแล้วต้องล้าง cache ฝั่ง server ทันที (§7) ไม่ใช่รอ TTL — คนตั้งค่าจะทดสอบทันทีที่กดเสร็จ

## 9. ด่านตรวจ (`npm run diag:role-permissions`)

1. **ตารางว่าง = พฤติกรรมวันนี้เป๊ะ** — เทียบผลของ `capsOf()` ทุก role กับตารางที่เขียนไว้ใน §4
2. **`SYSTEM_ERROR` ไม่มีสวิตช์** — assert ว่าไม่มีในแคตตาล็อก และ `blockingViolations()` ยังบล็อก
   มันทุก role ทุกโหมด
3. **ใบจาก LINE ไม่ขยับ** — สร้างใบทดสอบที่ไม่ใช่ `web:` แล้วยืนยันว่าผลของทุกด่านเท่าเดิม
4. **`deny` ไม่สร้างร่าง · `approval` สร้างร่างแล้วเข้าคิว · `allow` เขียน ack ลงใบ** — สามเส้นทางของ §6
5. **คำอนุมัติผูกกับตัวเลข** — อนุมัติ 10 ชิ้นแล้วแก้เป็น 20 ต้องกลับไปรออนุมัติใหม่
6. **`admin` แก้ไม่ได้** — ยิง API ตรง ๆ เพื่อตั้ง `admin` เป็น `deny` ต้องได้ 400
7. **ตัวกรอง "ใบของตัวเอง"** — บัญชีที่ปิด `quote.view_all` เห็นเฉพาะใบเว็บของตัวเอง + ใบ LINE
   ของเซลส์ที่ผูกไว้ · และ **ตัวกรองต้องมีผลกับ export/counts ด้วย ไม่ใช่แค่หน้าประวัติ**
8. **cache หมดอายุจริง** — แก้ค่าแล้วผลเปลี่ยนภายในคำขอถัดไป

เดิมที่ต้องยังเขียวทั้งหมด: `diag:web-quote` · `diag:price-approval` · `diag:quote-validation`
· `diag:stock-rule` · `diag:stock-rule-put` · `diag:confirm-race` · `npx tsc --noEmit`

**สถานะหลัง P2 (2026-09-18):** ด่านมี **31 ข้อผ่าน · ข้าม 1** — ข้อ 1–4 พิสูจน์ที่ระดับ
ฟังก์ชัน (ฟังก์ชันตัวเดียวกับที่ endpoint เรียกจริง ไม่ใช่สำเนา) · ข้อ 5 (คำอนุมัติผูกกับตัวเลข)
ครบทั้งสามแบบของ §3.6 · ข้อ 7 พิสูจน์ *รูปของเงื่อนไข* เพราะยังไม่มีบัญชีที่ผูกรหัสจริงสักบัญชี
(P4 คือรอบที่เปิดบัญชี) · **ข้อ 6 กับ 8 ยังข้ามอยู่** — ทั้งคู่ต้องมีตาราง `role_permissions`
ในฐานจริงก่อน (ยังไม่ได้รัน migration) และข้อ 6 ต้องมีหน้าจอของ P3 เป็นฝั่งเขียน

## 11. ต้องตัดสินใจก่อนลงมือ

1. **ค่าเริ่มต้นของ `salesperson` ใน §4ก** — ผมเสนอ blacklist/เครดิตค้าง = `deny` ที่เหลือ =
   `approval` · เจ้าของเปลี่ยนได้จากหน้าจอทีหลัง แต่ค่าที่ลงครั้งแรกคือค่าที่ใช้จริงวันแรก
2. ~~"ใบของตัวเอง" รวมใบที่ออกทาง LINE ไหม~~ — **เคาะแล้ว 2026-09-18: รวม** และนิยามด้วย
   *รหัสพนักงานขาย* ไม่ใช่ `user_id` (§3.5 · §13.7 ข้อ 7)
3. **เซลส์ที่ยังไม่มีชื่อในรายชื่อผู้จัดทำของ Odoo** (วันนี้คือ `PM00017 ดุลยภาพ ขันคำ`) —

   หรือให้แอดมินตั้งชื่อผู้จัดทำแทนได้
4. **คิวอนุมัติจะมีคนกดไหวไหม** — วันนี้ผู้อนุมัติมี 2 คน (`admin`, `THT0082`) ถ้าเซลส์ 34 คน
   เริ่มส่งคำขอพร้อมกัน ปริมาณจะไม่เท่าเดิม ⇒ อาจต้องตั้ง `approver` เพิ่มพร้อมกับงานนี้

## 13. ตัวตนบนใบที่ออกจากเว็บ — ล็อกชื่อ + ลายเซ็นขึ้นเอง (เจ้าของสั่งเพิ่ม 2026-09-18)

> **เซลส์:** ชื่อพนักงานขายขึ้นอัตโนมัติตามบัญชี พร้อมลายเซ็นที่มีอยู่แล้ว · แก้ไม่ได้ · แอบอ้าง
> เป็นคนอื่นไม่ได้ · ช่อง "ผู้เสนอราคา" เป็นชื่อของเซลส์คนนั้น **เหมือนออกผ่าน LINE**
> **แอดมิน:** ชื่อผู้เสนอราคาขึ้นอัตโนมัติตามบัญชี พร้อมลายเซ็น · แก้ไม่ได้ · แต่เลือกพนักงานขาย
> ได้อิสระ (พร้อมลายเซ็นของคนนั้น) · และ **เลือกแล้วต้องจำไว้ใน DB ไม่ใช่ localStorage**

### 13.1 วันนี้สองช่องบนกระดาษมาจากไหน (ต้องรู้ก่อน ไม่งั้นแก้ผิดฝั่ง)

| ปลายทาง | ใบจาก LINE | ใบจากเว็บวันนี้ | สวิตช์ที่ตัดสิน |
| --- | --- | --- | --- |
| PDF ช่องกลาง *(พนักงานขาย)* | ชื่อเซลส์ + ลายเซ็น `data/sale_sigs/<salesperson_id>.png` | เซลส์ที่แอดมินเลือก (ลายเซ็นเดียวกัน) | `salesperson_name` · `salesperson_employee_code` |
| PDF ช่องขวา *(ผู้เสนอราคา)* | **ซ้ำชื่อ+ลายเซ็นของเซลส์คนเดิม** | แอดมิน + `data/admin_sigs/<signature_key>` | **`issuer_name`** — `null` = เดินเส้นเดิม |
| Odoo ช่อง H *(ผู้ขาย)* | ชื่อเซลส์ | เซลส์ที่เลือก | `employee_details.saleperson` |
| Odoo ช่อง J *(ผู้จัดทำ)* | `salesperson.employee_quotation_id` ของเซลส์ | ...ของ **แถวพร็อกซี** = ชื่อแอดมิน | แถว `web:<adminId>:<spUserId>` |

### 13.2 เซลส์: ไม่ต้องสร้างเส้นใหม่ — ให้เดินเส้นของ LINE ทั้งเส้น

สองบรรทัดนี้จบโจทย์ "ผู้เสนอราคาเหมือนออกผ่าน LINE" โดย**ไม่แตะ `pdfGenerator.ts` แม้แต่บรรทัดเดียว**:

1. **`issuer_name` ของใบเซลส์เป็น `null`** ⇒ ช่องขวาเดินเส้นเดิม = ชื่อและลายเซ็นของเซลส์คนนั้น
   จาก `sale_sigs` ซึ่ง **มีอยู่แล้ว** ไม่ต้องอัปซ้ำเข้า `admin_sigs`
2. **แถวพร็อกซีเก็บ `employee_quotation_id` ของเซลส์เอง** (ไม่ใช่ของแอดมิน) ⇒ ช่อง J ในไฟล์
   Odoo ได้ชื่อเดียวกับที่ใบ LINE ของเขาได้

⚠️ **ยังต้องใช้แถวพร็อกซี ห้ามเอา `user_id` ของ LINE มาใช้ตรง ๆ** ทั้งที่รู้แล้วว่าบัญชีนี้คือใคร —
`insertDraftQuotations()` กวาดร่างเก่าของ `user_id` เดียวกันทิ้งทุกครั้ง ⇒ ร่างที่เซลส์สร้างบนเว็บ
จะลบร่างที่เขาค้างไว้ในแชท LINE ทิ้ง (และกลับกัน) โดยไม่มีอะไรเตือน

**การบังคับใช้อยู่ที่ server ไม่ใช่การซ่อน dropdown** — `createDraftFromWeb()` ต้อง **ไม่เชื่อ
`spUserId` ที่ client ส่งมา** เมื่อบัญชีนั้นไม่มี `quote.act_as_any_salesperson`: ยิงชื่อคนอื่นเข้ามา
ต้องได้ **403 พร้อมเหตุผล** ไม่ใช่เงียบ ๆ แก้ให้ (คนยิงต้องรู้ว่าทำไม่ได้ ไม่ใช่คิดว่าทำได้แล้ว)

### 13.3 แอดมิน: ชื่อผู้เสนอราคามาจาก "บัญชี" ไม่ใช่จาก "ช่องเลือก"

วันนี้แอดมินเลือกชื่อผู้จัดทำของตัวเองได้จากรายชื่อ 70 ชื่อผ่าน `PUT /api/admin/webquote/me`
— นั่นคือช่องที่ทำให้แอบอ้างชื่อคนอื่นได้ ⇒ **ย้ายสิทธิ์ ไม่ใช่ย้ายฟังก์ชัน**:

* ช่องเลือกชื่อบนหน้าขอใบเสนอราคา กลายเป็น **ข้อความอ่านอย่างเดียว** (ชื่อ + เบอร์ + ลายเซ็น)
* คนตั้งชื่อคือผู้มีสิทธิ์ `users.manage` ที่หน้า **จัดการผู้ใช้งานระบบ** ตอนสร้าง/แก้บัญชี
* **ยังเรียก `setAdminQuotationMaker()` ตัวเดิม** — เพราะกฎ "ชื่อกับเบอร์ต้องถูกเขียนพร้อมกัน
  จาก path เดียว" ยังต้องเป็นจริง (ไม่งั้นจะมีใบที่ชื่อกับเบอร์เป็นของคนละคน)
* **ลายเซ็นยังอัปเองได้** — มันคือลายเซ็นใต้ชื่อของตัวเอง ไม่ใช่การอ้างชื่อคนอื่น

### 13.4 เลือกพนักงานขายแล้วจำไว้ใน DB (ถอด localStorage)

`QuoteIssuerProfile.tsx` จำเซลส์ล่าสุดไว้ที่ `localStorage['webquote.acting_sp.<adminId>']`
⇒ เปลี่ยนเครื่อง/เปลี่ยนเบราว์เซอร์แล้วต้องเลือกใหม่ทุกครั้ง · ย้ายไป

**คนละที่กับตารางเชื่อมใน §3.5 โดยตั้งใจ** — สองคำถามคนละข้อ (ทั้งคู่ใช้ *รหัส* เป็นกุญแจ):

| ที่เก็บ | ตอบคำถาม | ใครใช้ | เปลี่ยนบ่อยไหม |
| --- | --- | --- | --- |
| `admin_user_salespersons` | *บัญชีนี้ **คือ** เซลส์รหัสไหนบ้าง* | บัญชี role `salesperson` | แทบไม่เปลี่ยน |

ที่เก็บเดียวที่แปลความหมายต่างกันตาม role คือของที่อีกหกเดือนจะมีคนอ่านผิด · ทั้งคู่
**ไม่ใช่สิทธิ์** และ **ไม่มีผลย้อนหลังกับใบที่ออกไปแล้ว** (ใบตรึง `employee_details` ไว้ตั้งแต่ยืนยัน)
· ค่าที่อ่านมาต้องเทียบกับรายชื่อเซลส์ที่โหลดได้จริงก่อนใช้เสมอ เหมือนที่ localStorage ทำอยู่วันนี้
(เซลส์อาจถูกยุบ/ปิดไปแล้ว) ไม่งั้นปุ่ม "สร้างร่าง" จะเปิดทั้งที่ช่องเลือกยังว่าง

### 13.5 ด่าน "ความพร้อมของบัญชี" ต้องแยกตาม role

วันนี้: *ไม่มี `employee_quotation_id` = บล็อกทั้งหน้า* ⇒ ต้องกลายเป็นคำถามที่ถูกต้องของแต่ละฝั่ง

| บัญชี | พร้อมออกใบเมื่อ | ยังไม่พร้อม = |
| --- | --- | --- |
| แอดมิน | `admin_users.employee_quotation_id` ไม่ว่าง | บล็อกทั้งหน้า + บอกให้ติดต่อผู้ดูแล *(ไม่ใช่ "ไปตั้งเอง" อีกต่อไป)* |
| เซลส์ | ผูกรหัสไว้อย่างน้อยหนึ่งรหัส และมีแถว `status='active'` ของรหัสนั้น | บล็อกทั้งหน้า + บอกให้ติดต่อผู้ดูแล |

เซลส์ที่แถว `salesperson` ยังไม่มี `employee_quotation_id` **ออกใบได้ตามปกติ** — ช่อง J ในไฟล์
Odoo จะว่าง ซึ่งเป็นพฤติกรรมเดียวกับใบ LINE ของเขาวันนี้เป๊ะ (ห้ามถอยไปใช้ชื่อช่อง H)

### 13.7 ข้อที่เคาะแล้ว (2026-09-18)

**5. "1 ชื่อผู้เสนอราคา = 1 บัญชี" — เจ้าของเคาะว่าใช่**
⇒ unique index แบบ partial (`WHERE employee_quotation_id IS NOT NULL`) · migration ต้อง
**เคลียร์ชื่อที่ชนก่อน แล้วค่อยสร้าง index ในไฟล์เดียวกัน** ไม่งั้น migration ล้มกลางคัน
· ของค้างวันนี้มีรายการเดียว: บัญชี `admin` (id=1) ถือชื่อ **"ยุพาทิพย์  ผลรัก"** ซึ่งเป็นชื่อของ
`THT0073` ที่กำลังจะเปิดบัญชีให้ ⇒ คืนชื่อให้เจ้าตัว · ใบเก่าไม่กระทบเพราะตรึง `employee_details`
ไว้ตั้งแต่ยืนยันแล้ว (และทั้งฐานมีใบที่ออกจากเว็บ 1 ใบ · วัด 2026-09-18)

**6. บัญชี `salesperson` ต้องผูก *รหัสพนักงานขาย* ตั้งแต่ตอนสร้าง**
`admin_users` (บัญชีล็อกอินเว็บ) กับ `salesperson` (แถวของเซลส์ที่ผูกกับ LINE) เป็นคนละตาราง
บัญชีที่ไม่ได้ผูกจึงไม่มีทางรู้ว่า "ฉันคือเซลส์คนไหน" ⇒ ชื่อไม่ขึ้น ลายเซ็นไม่ขึ้น ตัวกรองใบของตัวเอง
ตอบไม่ได้ · API ปฏิเสธถ้า `role='salesperson'` แล้วไม่ส่งรหัสมาอย่างน้อยหนึ่งรหัส + `diag`
ไล่หาบัญชีที่หลุด · **ไม่ใส่เป็น CHECK ใน DB** เพราะการเปลี่ยน role ไป-กลับจะติดล็อกโดยไม่จำเป็น

**ผูกด้วยรหัส แปลว่าปัญหา "แถวซ้ำ" หายไปเอง** — ไม่ต้องเลือกว่าจะผูกแถวไหนใน 2 แถวของคนที่มี
บัญชี LINE ซ้ำ เพราะทั้งสองแถวถือรหัสเดียวกันอยู่แล้ว · สิ่งที่ยังต้องเลือกคือ **แถวตัวแทน**
ตอนออกใบ (ใช้ทำ `user_id` พร็อกซี และเป็นชื่อที่ลงช่อง H) ซึ่ง `salespersonPicker` เลือกให้
อยู่แล้วด้วยเกณฑ์ "ใช้งานล่าสุด" — ของเดิม ไม่ต้องเขียนใหม่

**7. "ใบของตัวเอง" นิยามด้วยรหัสพนักงานขาย ไม่ใช่ `user_id`**
คนหนึ่งคนมีได้หลาย `user_id` และมันเกิดขึ้นแล้วจริง (วัด 2026-09-18):

| รหัสเซลส์ | ใบทั้งหมด | จำนวน `user_id` ที่ใบกระจายอยู่ |

| 422 (`คุณจิรายุ`) | 126 | 2 |
| 608 (`คุณอุดมพร`) | 109 | 2 |

(เซลส์ 37 แถว · 5 คนมีบัญชี LINE สองใบ · `salesperson_id` ไม่เป็น NULL เลยสักแถว)

⇒ ถ้ากรองด้วย `user_id` ที่ผูกไว้แถวเดียว **คุณนฤเบศร์จะมองไม่เห็นใบของตัวเองเกือบทั้งหมด**
