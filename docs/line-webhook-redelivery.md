# LINE ส่ง webhook ซ้ำ (Webhook redelivery) — ข้อเท็จจริงที่วัดได้

เอกสารนี้เก็บ **สิ่งที่วัดจริงพร้อมวันที่** ของเรื่อง redelivery ทั้งก้อน เพราะข้อสรุปชุดแรก
(2026-09-22) **ผิดบางส่วน** แล้วถูกใช้ตัดสินใจเขียนโค้ดไปแล้ว — ใครอ่านเจอข้อความเก่าที่ไหน
ให้ยึดไฟล์นี้

---

## 1. มันเป็นสวิตช์ที่ต้องเปิดเอง ไม่ใช่พฤติกรรมตั้งต้น

เอกสาร LINE ระบุว่า webhook redelivery **ปิดอยู่เป็นค่าเริ่มต้น** ต้องเข้าไปเปิดที่
LINE Developers Console → Messaging API → Webhook settings และเมื่อเปิดแล้ว LINE จะส่ง
event เดิมซ้ำ **ทุกครั้งที่เราไม่ตอบ 2xx** · จำนวนครั้งและระยะห่างของการส่งซ้ำ
**LINE ไม่เปิดเผยและเปลี่ยนได้โดยไม่แจ้ง**

### เปิดเมื่อไหร่ — วัดจากฐานข้อมูล (2026-09-23)

`messages.reply_token` เก็บ token ของทุก event ที่ประมวลผล และ event ที่ถูกส่งซ้ำจะพก
token **ตัวเดิม** มาด้วย ⇒ token ที่ซ้ำโดยห่างกันเกิน 20 วินาที = การส่งซ้ำ

ช่วงข้อมูล: **2026-06-17 → 2026-09-23 · 7,598 แถว**

| ช่วง | ครั้งที่ LINE ส่งซ้ำ |
| --- | --- |
| 2026-06-17 → 2026-09-15 (3 เดือน) | **0** |
| 2026-09-16 16:30:50 | 1 ← ครั้งแรกในประวัติ (ห่าง 104 วิ) |
| 2026-09-17 15:47:15 | 1 (57 วิ) |
| 2026-09-18 → 09-20 | 0 |
| 2026-09-21 | **8** — รวมตัวที่ถูกส่งซ้ำ 5 รอบ (ยาว 244 วิ) และ 4 รอบ (187 วิ) |
| 2026-09-22 09:54:52 | 1 (59 วิ) |

⇒ สวิตช์ถูกเปิดราว **2026-09-16** · เงียบสนิทมาก่อนหน้านั้นสามเดือน
(หลัง 2026-09-22 14:34 ไม่มีแถวใหม่ เพราะโค้ดข้ามก่อนถึงจุดบันทึก — ดูข้อ 5)

**การส่งซ้ำไม่ใช่สาเหตุที่เซลส์ไม่ได้คำตอบ มันคืออาการ** ที่บอกว่ารอบแรกมีปัญหา
ปิดสวิตช์แล้วปัญหาไม่หาย — หายแค่ร่องรอย

## 2. อายุของ `replyToken` — ทดลองจริง 2026-09-23

**ความเชื่อเดิมที่ใช้ออกแบบทั้งระบบ: token ตายที่ 60 วินาที — ผิด**

### วิธีทดลอง

ต้องใช้ token ที่ **ยังไม่ถูกใช้** ซึ่งหาได้จาก event `follow` (กดเลิกบล็อกบอท):
ทั้งระบบไม่มีโค้ดจัดการ `follow`/`unfollow` เลย บัญชีที่ลงทะเบียน active แล้วจะหลุดไปถึง
`return null` ใน `lineHandler.ts` ⇒ token ไม่ถูกแตะ · จากนั้นยิง
`POST https://api.line.me/v2/bot/message/reply` ด้วย token นั้นเมื่อครบเวลาที่กำหนด

### ผล

| อายุ token ตอนยิง | ผลลัพธ์ |
| --- | --- |
| 10 วินาที | HTTP 200 |
| 65 วินาที | HTTP 200 |
| **120 วินาที** | **HTTP 200** |

⇒ **token ที่ยังไม่ถูกใช้ อยู่ได้อย่างน้อย 120 วินาที** (ยังไม่ได้หาเพดานจริง)

เทียบกับของจริง: event ที่ถูกส่งซ้ำมาถึงที่อายุ **53–104 วินาที** ⇒ 120 วินาทีครอบคลุม
ทุกเคสที่เคยเกิดในรอบ 3 เดือน

### ⚠️ ห้ามเอาผลนี้ไปขยาย `BUDGET_MS`

`REPLY_TOKEN_TTL_MS = 60_000` ใน `services/webhookQueue.ts` เป็น **งบที่เลือกให้ปลอดภัยไว้ก่อน**
ไม่ใช่ตัวเลขที่เพิ่งพิสูจน์ว่าผิด — LINE ระบุเองว่าเวลานี้เปลี่ยนได้โดยไม่แจ้งล่วงหน้า
การยืดงบเพราะ "วัดได้ 120 วิ" คือเอาความเร็วไปแลกกับความเสี่ยงที่ทั้งระบบตอบไม่ทันพร้อมกัน

## 3. ทำไม 400 `Invalid reply token` ถึงเกิด — สาเหตุจริง

**ไม่ใช่เพราะ token หมดอายุ** (ข้อ 2 พิสูจน์แล้ว) แต่เพราะ **token ถูกใช้ไปแล้ว**
reply token ใช้ได้ครั้งเดียว ⇒ event ที่เราตอบไปแล้วรอบแรก พอถูกส่งซ้ำมาก็ตอบด้วย token
เดิมไม่ได้อีก

ที่ขึ้นเป็น **"คู่"** ในหน้าบันทึกระบบ เพราะ fallback ในตัว catch-all ใช้ token ตัวเดิมยิงซ้ำ:
```
เกิดข้อผิดพลาดในการประมวลผลระบบ: HTTPFetchError: 400 - Bad Request
ไม่สามารถส่งข้อความแจ้งข้อผิดพลาดกลับไปยังผู้ใช้ได้: 400 - Bad Request
```

## 4. event ที่ถูกส่งซ้ำมี **สองกลุ่มที่คนละเรื่อง** — ข้อสรุปเดิมครอบไม่ครบ

ข้อความเดิมเขียนว่า redelivery คือ *"event เดิมที่เราตอบไปเรียบร้อยแล้ว"* ทุกกรณี
วัดจริง 2026-09-23 (หน้าต่าง 21 ชม. · 168 event · ส่งซ้ำ 7 ครั้ง) พบว่า **จริงแค่ 5 ใน 7**

| กลุ่ม | จำนวน | รอบแรกมาถึงไหม | เซลส์ได้คำตอบไหม | ข้ามแล้วเสียอะไร |
| --- | --- | --- | --- | --- |
| A — ของซ้ำจริง | 5 | ถึงแล้ว ตอบแล้ว | ได้ | ไม่เสีย |
| B — รอบแรกหาย | **2** | **ไม่เคยถึง** | **ไม่ได้** | **งานไม่ถูกทำเลย** |

### หลักฐานว่ากลุ่ม B "ไม่เคยมาถึง" จริง

- `webhookEventId` ของทั้งสองตัวปรากฏใน log **ครั้งเดียว** (ของกลุ่ม A ปรากฏสองครั้ง ห่างกัน ~60 วิ)
- ทุกแถว `POST /callback` ใน `api_logs` ตอบ **200 หมด** และจำนวนแถว POST เท่ากับจำนวน event
  ที่ประมวลผลเป๊ะทุกวัน (2026-09-23: 111 = 108 + 3) ⇒ ไม่มี request ที่มาถึงแล้วถูกปัดทิ้ง
- log ช่วงนั้นมี event อื่นเข้ามาปกติ ⇒ แอปไม่ได้เงียบ
- ULID ของตัวที่หาย (`01M3682X…`) เรียงต่อจากตัวที่มาถึงก่อนหน้า 8 วินาที (`01M3682N…`)

### เคสจริงของกลุ่ม B (2026-09-23)

ใบ `4ae3ef39` — เซลส์สร้างร่าง 11:23:46 แล้วกดยืนยัน 11:23:52
(`action=confirm&id=4ae3ef39…`) · รอบแรกไม่เคยมาถึง · ตัวส่งซ้ำมา 11:24:55 แล้ว**ถูกข้าม**
⇒ ใบค้างเป็น `draft` ไม่มีเลขที่ · เซลส์สังเกตเองแล้วกดใหม่ตอน 11:33 จึงได้ `QT-260905364`

อีกตัว (10:27:23) เป็นข้อความ "บันทึกร่างแล้ว" ของใบ `3201d7ee` ที่หายไปเหมือนกัน
แต่ใบรอดเพราะเซลส์ไปยืนยันจาก LIFF แทน (`QP-260905802`)

## 5. พฤติกรรมของโค้ด

### 5.0 ของเดิม (2026-09-22 → 2026-09-23) — ข้ามทุกตัว

`07ee4af` ข้าม event ที่ `isRedelivery === true` **ทุกตัว** แล้วบันทึกเป็น `outcome: 'dropped'` (= 499)
ซึ่งแก้อาการ 400 ได้จริง — `/callback` ใน `api_logs`:

| วัน | 500 (พังจริง) | 499 (ตั้งใจทิ้ง) |
| --- | --- | --- |
| 2026-09-21 | 11 | 0 |
| 2026-09-22 | 4 (ทั้งหมดก่อน 14:34) | 4 (ทั้งหมดหลัง 14:34) |
| 2026-09-23 | 0 | 3 |

**แต่มันทิ้งกลุ่ม B ไปด้วย** ⇒ คำสั่งของเซลส์หายเงียบโดยไม่มีใครรู้

### 5.1 ของปัจจุบัน — ถามก่อนทิ้ง

ตัดสินจาก **สถานะจริงในตาราง `webhook_events`** ไม่ใช่จากธง `isRedelivery` เพียว ๆ:

| สถานะของ event นั้น | ทำอะไร | บันทึกเป็น |
| --- | --- | --- |
| เคยรับ และจบแบบ `replied` | ทิ้งเงียบ (กลุ่ม A) | `skipped_duplicate` |
| **ไม่เคยรับเลย** | ไม่ทำงานให้ · แจ้งเซลส์ให้สั่งใหม่ | `warned` |
| เคยรับ แต่จบแบบ timeout/failed/dropped หรือยังไม่จบ | เหมือนบรรทัดบน | `warned` |
| แจ้งไม่สำเร็จ (token ใช้ไม่ได้แล้ว) | เข้าหน้า "บันทึกระบบ" ให้แอดมินตามต่อ | `warn_failed` |
| ถามฐานไม่ได้ (DB ล่ม / ยังไม่ได้รัน migration) | ทิ้งไว้ก่อน = พฤติกรรมเดิมเป๊ะ | — |

**⚠️ ไม่มีทางไหนที่ระบบจะทำงานให้เอง** — เจ้าของสั่ง 2026-09-23: *"ไม่อยากให้ใบได้เลขเงียบ เพราะ
เซลส์จะไม่รู้เลยว่าร่างถูกยืนยันไปแล้วจริง"* ⇒ `services/redeliveryPolicy.ts` มีทางออกแค่
`skip` กับ `warn` และด่านข้อ 2 ไล่ทุกชุดค่าที่เป็นไปได้เพื่อพิสูจน์ว่าไม่มีทางที่สาม

ทำไมถึงตอบกลับได้ทั้งที่ event มาช้า: token ที่ **ยังไม่ถูกใช้** อยู่ได้ ≥120 วินาที (ข้อ 2)
ส่วนที่ตอบไม่ได้คือ token ที่เราใช้ไปแล้ว ซึ่งตรงกับกลุ่ม A พอดี — และกลุ่ม A ไม่ต้องตอบอยู่แล้ว

ตรรกะอยู่ที่ **`services/redeliveryPolicy.ts`** (ฟังก์ชันบริสุทธิ์ ไม่แตะ DB/เครือข่าย) ·
ใบรับอยู่ที่ **`db/webhookEventsRepo.ts`** · จุดต่อสายอยู่ที่ `handleRedelivery()` ใน `index.ts`
· gate: **`npm run diag:redelivery`** (ไม่เขียนฐาน รันบน prod ได้)

### 5.2 ตาราง `webhook_events` — เก็บอะไรและทำไม

1 แถว = 1 `webhookEventId` (ตัวส่งซ้ำใช้ค่าเดิม ⇒ เป็น UPDATE ไม่ใช่แถวใหม่) **เก็บถาวร ไม่ลบทิ้ง**
(เจ้าของสั่ง 2026-09-23) — ~170 แถว/วัน ≈ 10 MB/ปี

| คอลัมน์ | ตอบคำถามอะไรตอนสอบกลับ |
| --- | --- |
| `delivery_count` | LINE ยิงมากี่รอบ (วัดได้สูงสุด 5 รอบ / 244 วินาที) |
| `postback_data` | ปุ่มที่หายไปสั่งอะไรกับใบไหน — `action=confirm&id=<uuid>` |
| `first_delay_ms` / `last_delay_ms` | อายุ replyToken ณ ตอนที่มาถึง = ยังตอบทันไหม |
| `outcome` | รอบแรกจบยังไง (`replied` = เซลส์ได้คำตอบแล้ว) |
| `redelivery_action` + `note` | เราทำอะไรกับตัวส่งซ้ำ และถ้าแจ้งไม่สำเร็จเพราะอะไร |
| `request_id` | กระโดดไป `api_logs` ดู duration / llm_ms ของ event นั้น |

**ทำไมไม่เก็บใน `messages`:** `messages` คือความจำการสนทนาที่ `quoteExtraction` อ่าน **10 แถว
ล่าสุด** ยัดเข้า prompt ของ LLM — เพิ่มแถวต่อทุก postback จะเบียดบทสนทนาจริงออกจากหน้าต่างนั้น
(เซลส์กดปุ่ม 5 ครั้ง = กินไป 5 ใน 10 ช่อง) และมีสคริปต์วัดผล 8 ตัวที่ขุดตารางนั้นไปทำชุดข้อสอบ

## 5.3 ทำไมรอบแรกถึงไม่ได้ 2xx — กลไกฝั่งขาออก (วัด 2026-09-22)

log ของ cloudflared ย้อนหลัง 20 วัน (2026-09-02 → 2026-09-22) มี request ตก **133 ครั้ง
แยกเป็นสองกลุ่มที่คนละสาเหตุ**:

| สาเหตุ | ครั้ง | แปลว่า |
| --- | --- | --- |
| `Error shutting down control stream: context canceled` | **122 (92%)** | Cloudflare edge ตัด connection ทิ้งขณะ request ยังวิ่งอยู่ (`Lost connection with the edge` 106 ครั้ง ≈ 5 ครั้ง/วัน ทีละ 4 connection ภายใน 2 วินาที) |
| `connection refused` | 11 (8%) | ช่วงที่ app ไม่อยู่ตอน deploy |

⇒ กลุ่มนี้คือ **เราตอบสำเร็จแล้วแต่คำตอบไปไม่ถึง LINE** = กลุ่ม A ในข้อ 4

**การมี connector หลายตัวไม่ได้แก้ 122 ครั้งนี้** — request ที่วิ่งบน connection ที่กำลังตาย
ยังไงก็ตาย

⚠️ กลไกนี้ **อธิบายกลุ่ม A ได้ แต่อธิบายกลุ่ม B ไม่ได้** เพราะกลุ่ม B คือขา**เข้า**ที่ไม่เคย
มาถึงแอป และ tunnel ตัวใหม่ (cloudflared 2026.9.1) มี error 0 ครั้งตั้งแต่ 2026-09-22 17:00

## 6. สิ่งที่ยังไม่รู้ — อย่าเขียนเกินนี้

- **ยังไม่เคยทดสอบ token ที่มาจาก event ที่ LINE ส่งซ้ำจริง ๆ** ข้อ 2 ทดสอบกับ token ปกติ
  ที่ไม่ถูกใช้ · เอกสาร LINE เขียนว่า token ของ event ที่ส่งซ้ำ *"ใช้ได้ ยกเว้นบางกรณี"*
  และแนะนำให้กันซ้ำด้วย `webhookEventId` ไม่ใช่ทิ้งทั้งหมด · จำลองของจริงไม่ได้โดยไม่ทำให้
  webhook ล้มทั้งระบบ ⇒ จะรู้ตอนเจอเคสจริงครั้งแรกเท่านั้น
- **เพดานอายุ token จริง** — รู้แค่ว่า ≥ 120 วินาที
- **ทำไมรอบแรกของกลุ่ม B ถึงไม่มาถึง** — tunnel ตัวใหม่ (cloudflared 2026.9.1) มี error
  **0 ครั้ง** ตั้งแต่ 2026-09-22 17:00 ⇒ ของที่หายตายก่อนถึง connector คนละกลไกกับ
  `Error shutting down control stream` 122 ครั้งที่บันทึกไว้ 2026-09-22

## 7. ข้อเท็จจริงของ LINE API ที่วัดเองแล้ว (2026-09-23)

**LINE ตรวจ `messages` ก่อน `replyToken` เสมอ** ⇒ ถาม LINE ว่า token ยังดีไหมโดยไม่ส่ง
ข้อความจริง **ทำไม่ได้**

| ยิงอะไร | ได้อะไรกลับมา |
| --- | --- |
| token ปลอม + `messages: []` | `The request body has 1 error(s)` — ไม่บอกเรื่อง token |
| token ปลอม + messages ถูกต้อง | `Invalid reply token` |
| token มั่ว + `messages: []` | `The request body has 1 error(s)` — เหมือนอันแรก |
