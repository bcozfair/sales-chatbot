## 1. ทำไมต้องย้าย

1. **ยอดเงินใน `sale_orders` เป็นของ "บรรทัดแรก" ไม่ใช่ทั้งใบ** — ทั้ง v2 และ v3 ส่งยอด/รุ่น/จำนวนเป็น
   ระดับบรรทัด แต่ `upsertSaleOrderRows()` เก็บแถวแรกต่อ `order_reference` แล้วทิ้งที่เหลือ
   (เคส OP-260900178: ในฐาน 70,400 · ใบจริง ~296,000) ⇒ "ประวัติส่วนลด" หน้าข้อมูลลูกค้าผิดมาตลอด
2. **ข้อมูลค้าง** — v2 ส่งใบซ้ำเฉพาะเมื่อ "หัวใบ" ถูกแก้ ออกบิลแล้ว/ชื่อผู้ติดต่อเปลี่ยนแล้วไม่ส่ง ⇒ `invoice_status`
   และหัวใบค้าง · v3 มี `V3 Updated At` ที่ขยับเมื่อบรรทัด/ใบแจ้งหนี้/MO เปลี่ยนด้วย ⇒ ด่านเครดิตได้ข้อมูลสดขึ้น
3. **ระบบตรวจสถานะการจัดส่งที่จะทำใน chatbot ต้องใช้ข้อมูลระดับบรรทัดและ MO** ซึ่ง v2 ไม่มีเลย

## 3. ข้อเท็จจริงของ v3 ที่แบบนี้พึ่งพา

วัดจริง 8 หน้า (3,971 ใบ) + dry-run 3 ช่วง (ข้อ 3.1):

- **1 แถว = บรรทัดสินค้า × บรรทัดใบแจ้งหนี้ × MO** · ธงกันนับซ้ำ: `use_for_order_amount` (1 แถว/บรรทัด) ·
  `use_for_invoice_amount` (1 แถว/บรรทัด×บรรทัดใบแจ้งหนี้) · `use_for_mo` (1 แถว/บรรทัด×MO)
- ใบหนึ่งไม่ถูกตัดข้ามหน้า · แถวของใบเดียวกันติดกัน · `V3 Updated At` และหัวใบเท่ากันทุกแถวของใบ ·
  เรียงตาม `(V3 Updated At, Sale Order ID)` และ `next_position` = ใบสุดท้ายของหน้า (keyset)
- **`V3 Updated At` ไม่เคยเก่ากว่า `Last Updated` ของหัวใบ** (992/992 แถว) ⇒ เริ่มกวาดที่ 2021-12-01 พอ
- **แถวแรกของทุกใบมี `use_for_order_amount=true`** และแบ่งกลุ่มบรรทัดด้วยธงนี้ได้ — ค่าระดับบรรทัดตรงกัน
  ทุกกลุ่ม (6,327/6,327) · 55 ใบมีรุ่นซ้ำหลายบรรทัด ⇒ **ห้ามใช้ Model Code เป็นคีย์บรรทัด**
- MO Reference ไม่ซ้ำข้ามใบ · ใบที่ไม่มีบรรทัดนับใน `sale_order_count` แต่ไม่มีแถว
- **ช่อง `Model` ของ v3 ไม่ใช่ค่าเดียวกับ v2** — v2 = ชื่อสินค้าเต็ม (`Heatsink "Primus" HP-03`) ·

- หน้าละ 6–15 วินาที (v2 0.3 วิ) ⇒ timeout ต่อ request 60 วิ (เดิม 30)
- `has_more` เคยตอบ `false` ตั้งแต่หน้าแรก (Appsale เจอ 2026-08-21) และตอบ `false` ที่หน้าสุดท้ายที่ยังมีข้อมูล

## 4. แบบ

### 4.1 ตาราง (migration `2026-10-05_01_sale_order_v3.sql` · additive ล้วน)

- `sale_orders` เพิ่ม `source_updated_at` (= `V3 Updated At` · ใช้กันข้อมูลเก่าทับใหม่) และ
  **ยอดทั้งใบ** `order_total_amount` · `order_total_discount` · `order_amount_after_discount` ·
  `order_vat` · `order_net_amount` · `order_line_count` — **`NULL` = ยังไม่เคยถูก v3 เขียน**
- `sale_order_details (sale_order_id PK, order_reference, source_updated_at, lines jsonb, updated_at)`
  - คีย์เป็น `sale_order_id` ไม่ใช่ `order_reference` เพราะ Odoo เปลี่ยนชื่อเอกสารตอนยืนยัน (Q* → OP*)
  - **ไม่ใส่เป็นคอลัมน์ใน `sale_orders`** — jsonb ~0.5–0.7 KB ต่ำกว่าเกณฑ์ TOAST จึงอยู่ในแถว
    ทำให้ตารางที่ถูกอ่านตลอดเวลาอ้วนขึ้นมาก และไหลออก SYNC_API ไปด้วย
  - GIN index สำหรับค้น MO **ยังไม่สร้าง** (ยังไม่มีผู้อ่าน) — สร้างในขั้น 6 ด้วย `CONCURRENTLY`

### 4.2 คอลัมน์เดิมยังแปลว่าเหมือนเดิม

คอลัมน์เดิมทุกตัวเขียนด้วยสูตรเดียวกับโค้ด v2 จาก **แถวแรกของใบ** (`parseFloat` / `|| 0` / `'N/A'` เหมือนเดิม)
⇒ ผู้อ่านเดิม (SYNC_API ภายนอก · `customers_data_build`) ไม่เห็นความหมายเปลี่ยน ยกเว้น:

- **`model` คงค่าเดิมเมื่ออัปเดต** — v3 ไม่มีชื่อสินค้าเต็มให้ ใบใหม่ได้ `'N/A'` (ค่าเริ่มต้นของคอลัมน์)
  ไม่เอา `Model` ของ v3 มาใส่เพราะคนละความหมาย · ในแอปไม่มีจุดไหนอ่านคอลัมน์นี้ (grep 2026-10-05)
  · ค่า `Model` ของ v3 อยู่ใน jsonb ที่ `lines[].model`
- ค่าที่สดขึ้นตามข้อ 3.1

### 4.3 รูป jsonb (`sale_order_details.lines`)

```json
{ "v": 3, "src": "invoice",
  "lines": [ { "model_code": "…", "model": "TSX-08", "qty": 3, "qty_invoiced": 3,
               "amount": 23895, "discount": 7168.5, "after_discount": 16726.5, "vat": 1170.855, "net": 17897.36,
               "category": "Heater", "group": "Inst 1", "sub_category": "…", "series": "IMH",
               "invoices": [ { "number": "INV…", "type": "out_invoice", "date": "…", "qty": 3, "unit_price": 7965,
                               "discount_pct": 30, "subtotal": 16726.5, "vat": 1170.86, "total": 17897.36, "status": "invoiced" } ],
               "mos": [ { "ref": "Assy/2606/1249", "deadline": "…", "planned_start": "…", "planned_finished": "…",
                          "qty": 3, "routing": "Immersion Heater", "status": "QC" } ] } ] }
```

- ลำดับ `lines` = ลำดับที่ gateway ส่ง (`sol.sequence, sol.id`) · หัวใบไม่ซ้ำลงที่นี่ (อยู่ใน `sale_orders`)
- ใบแจ้งหนี้ = แถวที่ `use_for_invoice_amount` และมี `Invoice Number` · MO = แถวที่ `use_for_mo` และมี `MO Reference`
- ยอดทั้งใบ (4.1) = ผลรวมจาก `lines[]` คิดแบบทศนิยมตรง (ไม่ผ่าน float) แล้วเขียนคู่กันในทรานแซกชันเดียว

### 4.4 ด่านตรวจรูปข้อมูลทุกหน้า — ผิดเมื่อไหร่ throw แล้ว rollback ทั้งหน้า

แถวไม่มี `Sale Order ID`/`Order Reference` · แถวของใบไม่ติดกัน · ใบเดียวถูกตัดข้ามหน้า · หัวใบไม่เท่ากันทุกแถว ·
แถวแรกของใบไม่ใช่ `use_for_order_amount` · ค่าระดับบรรทัดไม่ตรงกันในกลุ่ม · จำนวนใบเกิน `sale_order_count`
⇒ เขียนยอดผิดแบบเงียบ ๆ แย่กว่าหยุด · หยุดแล้ว sync ใบสั่งขายค้าง แต่แอปยังทำงาน และถอยไป v2 ได้ (4.7)

### 4.5 การเขียน

- ทั้งหน้าเป็น **2 คำสั่ง** (`sale_orders` + `sale_order_details`) ผ่าน `jsonb_to_recordset` · เรียงตาม
  `order_reference` / `sale_order_id` กัน deadlock กับรอบอื่น
- **กันของเก่าทับของใหม่**: อัปเดตเฉพาะเมื่อ `source_updated_at` ที่มา ≥ ของเดิม
- **`updated_at` ขยับเฉพาะเมื่อค่าธุรกิจเปลี่ยนจริง** — ทั้ง SYNC_API ภายนอกและ watermark ของ
  `customers_data_view` อ่านคอลัมน์นี้ ⇒ v3 ที่ส่งใบซ้ำเพราะ MO ขยับจะไม่ทำให้ทั้งสองทำงานฟรี
  (รอบ backfill แรกจะขยับเกือบทุกแถวหนึ่งครั้ง เพราะยอดทั้งใบเป็นค่าใหม่ — ตั้งใจ)
- ค่าไม่เปลี่ยนเลย = ไม่เขียนแถวซ้ำ (ไม่สร้าง tuple ใหม่)
- **วันตัด (`selectStorable`)**: ใบที่ `Order Date` ก่อน `2021-12-31T17:00:00Z` (= 2022-01-01 00:00 เวลาไทย)
  **เขียนเฉพาะเมื่อมีแถว `order_reference` เดียวกันในฐานอยู่แล้ว** ไม่งั้นข้ามทั้งใบ (ทั้งสองตาราง) ·
  ไม่มี `Order Date` = เขียนตามปกติ · เทียบตอนเขียน ไม่ใช่ที่ `since=` เพราะ `since` คัดตามเวลาแก้ไข

### 4.6 การแบ่งหน้าของ v3 (`decideV3PageTransition`)

หน้าว่าง = จบ · มีข้อมูลและ cursor ขยับ = ไปต่อ **แม้ `has_more=false`** (เสียหน้าว่างเพิ่ม 1 หน้า/รอบ) ·
มีข้อมูลแต่ cursor ไม่ขยับ = retry แล้ว throw (ถ้า `has_more=false` ถือว่าจบ)

### 4.7 การสลับเวอร์ชัน — v3 ทันทีที่ขึ้นโค้ด · ถอยได้

- state ของ v3 อยู่แถว `sync_state.resource = 'sale_order_v3'` แยกจาก `'sale_order'` ของ v2
  ⇒ cursor ของ v2 ไม่ถูกแตะ (หยุดอยู่ที่วันสลับ) ถอยกลับไป v2 แล้วเดินต่อจากจุดนั้นได้
- `SALEORDER_API_VERSION` = `v3` (ค่าเริ่มต้น) · `v2` (ทางถอย) · ค่าอื่น = throw
  · ถอยฉุกเฉิน = ตั้ง `v2` ใน `.env` แล้ว recreate คอนเทนเนอร์
- **ทำไมไม่มีช่วงรอแล้ว** (เจ้าของเคาะ 2026-10-05 "v3 มีข้อมูลครบตามที่ v2 มีอยู่แล้ว"): ร่างแรกมี `auto`
  (เป็น v2 จนกว่าการกวาดรอบแรกของ v3 จะจบ) ซึ่งซื้อได้อย่างเดียวคือใบสั่งขายไม่หยุดอัปเดตระหว่างกวาดรอบแรก
  ⇒ ได้ผลเดียวกันโดยไม่ต้องมีสวิตช์อัตโนมัติ ด้วยการกวาดรอบแรกด้วย image ใหม่ **ก่อนสลับกล่อง** (ข้อ 4.8)
- ⚠️ **ขึ้นโค้ดแต่ยังไม่รัน migration** = รอบใบสั่งขายล้มทุกรอบ ("ฐานนี้ยังไม่ได้รัน migration …") — สินค้า/ลูกค้า
  ยัง sync ปกติ (error ชนิดนี้ไม่ยกเลิกทั้งรอบ) ข้อมูลไม่เสีย แค่ใบสั่งขายหยุดจนกว่าจะรัน migration
- ⚠️ **ขึ้นกล่องโดยยังไม่กวาดรอบแรก** = รอบอัตโนมัติแรกที่ API เปิด กวาดเองตั้งแต่ 2021-12-01
  ~2 ชม. ในคิว sync ของแอป ⇒ ระหว่างนั้นสินค้า/ลูกค้าไม่ sync และใบสั่งขายใหม่ยังไม่เข้า — ข้อมูลไม่เสีย แค่ช้า
  (ขึ้นกล่องหลัง 18:00 = เกิดตอน 07:00 ของวันถัดไป กลางช่วงที่คนใช้)
- รอบ v3 ทุกรอบถือ `pg_advisory_lock` ⇒ CLI กับรอบของแอปไม่เขียน cursor ทับกัน · ชนกัน = รอบที่มาทีหลัง
  ล้มทันทีด้วยข้อความ "อีกรอบกำลังรันอยู่" ก่อนยิง gateway
- รอบ v3 ของแอปอัปเดต `last_success_at`/`pages_synced`/`records_synced` ของแถว `'sale_order'`
  ด้วย (ไม่แตะ cursor) ⇒ หน้าสถานะ sync ไม่โชว์เวลาค้าง โดยไม่ต้องแก้ UI
- **ปุ่ม "Full sync ใบสั่งขาย" คงไว้** (เจ้าของสั่ง 2026-10-05) = ล้าง cursor ของ v3 แล้วกวาดใหม่ตั้งแต่ 2021-12-01
  (cursor ของ v2 ไม่ถูกแตะ) · `npm run sync:saleorders -- --full` ทำแบบเดียวกัน · ต่างจากสมัย v2 แค่เวลา —
  หน้าละ 6–15 วิ (v2 0.3 วิ) ⇒ **~2 ชม.** และตลอดเวลานั้นรอบอัตโนมัติของสินค้า/ลูกค้ารอ (mutex ของ
  `syncService`) · API เปิดแค่ 07:00–18:00 ⇒ **กดได้แค่ในเวลางาน และควรเริ่มก่อน ~15:30**
  · **กวาดใหม่โดยไม่หยุดสินค้า/ลูกค้า** = `--v3-backfill --restart` ด้วยกล่องแยก (ข้อ 7) ซึ่งไม่ถือคิวของแอป
  · ล้มกลางทาง (gateway ล่ม · เลย 18:00) = รอบอัตโนมัติถัดไปที่ API เปิดเดินต่อจาก cursor ที่ค้าง ไม่เริ่มใหม่

### 4.8 การกวาดรอบแรก — ต้องทำในเวลางาน (API 07:00–18:00) และก่อนสลับกล่อง

- **กวาดด้วยกล่องชั่วคราวจาก image ใหม่ ขณะที่กล่องเดิม (v2) ยังทำงาน** — DEPLOY.md ขั้น 5 แยก `build`
  กับ `up` อยู่แล้ว ⇒ แทรก `docker compose run … --v3-backfill` ระหว่างสองบรรทัดนั้น (ข้อ 6)
  ⇒ ตลอด 1.5–2 ชม. ใบสั่งขายยังอัปเดตด้วย v2 ตามปกติ สินค้า/ลูกค้าไม่ถูกแตะ · จบแล้วค่อย `up`
  แอปตัวใหม่เดินต่อจาก cursor ที่กวาดจบ ⇒ ไม่มีช่วงไหนที่ข้อมูลหยุด
- v2 ตัวเก่าเขียนใบที่กวาดไปแล้วซ้ำได้ระหว่างนั้น — ไม่เป็นไร: v2 ส่งใบเมื่อหัวใบเพิ่งถูกแก้ ค่าที่ส่งจึงเป็นค่าปัจจุบัน ·
  มันไม่รู้จัก `source_updated_at` / `order_*` / `sale_order_details` จึงไม่แตะ ⇒ รอบ v3 ถัดไปเขียนทับได้ตามปกติ
- โปรเซสแยก ไม่ผ่าน mutex ของแอป · **สายเดียว** · พักหน้าละ 1.2 วิ ⇒ ~6 request/นาที (เพดาน 80)
- เริ่มที่ `since=2021-12-01` (ข้อ 3) · ~650–700 หน้า × 8–10 วิ ≈ **1.5–2 ชม.** (ช่วงแรกเป็นใบเก่าที่ถูกข้าม
  ⇒ เขียนฐานน้อย)
- **ทำต่อจากจุดค้างได้** (cursor บันทึกทุกหน้า) · 429/ติดต่อไม่ได้ = รอแล้วลองใหม่ (gateway ~3 นาที +
  พักหน้าละ 2 นาทีอีก 3 รอบ) ก่อนยอมหยุด · **เลย 18:00 = ล้มหลังรอราว 15 นาที** แล้วสั่งบรรทัดเดิมซ้ำหลัง 07:00
  เดินต่อจากจุดค้าง ⇒ เริ่มก่อน ~15:30 · ตั้งเวลากวาดกลางคืนไม่ได้
- **อย่ารันพร้อม Full Sync ของ Appsale** (key เดียวกัน · เพดาน 2 พร้อมกัน)
- **วัดจริง 2026-10-05 (รอบแรกบน prod):** 11:45:50 → 13:27:59 = **102 นาที · 695 หน้า · ~8.8 วิ/หน้า** ·
  345,493 ใบ / 567,694 บรรทัด · เขียน: ใหม่ 9 · ค่าเปลี่ยน 318,226 · เปลี่ยนแค่เวลา 4 · รายละเอียด 318,241 ·
  ข้าม (สั่งก่อน 2022 และไม่มีในฐาน) 27,252 · ไม่มีหน้าไหนล้ม ไม่ต้องสั่งซ้ำ · กล่องเดิม v2 sync ผ่านทุกรอบตลอดช่วงนั้น
- **รอบอัตโนมัติของแอปหลังสลับช้าลง** (วัด 2026-10-05 13:34): ใบสั่งขาย 2 หน้า **16.9 วิ** (v2 หน้าเดียว 0.2 วิ) ⇒
  ทั้งรอบ 22.9 วิ จากเดิม ~7.6 วิ — ช้าลงแต่ยังอยู่ในรอบ 5 นาทีสบาย ๆ

## 6. Runbook ขั้น 4 (บน PMSV · ทุกบรรทัดที่เขียนฐานต้องได้คำสั่งเจ้าของ)

ลำดับเดียวกับ "อัปเดต server" ใน `DEPLOY.md` — ต่างแค่แทรกข้อ 3–4 ระหว่าง `build` กับ `up` ของขั้น 5

```bash

# 2. build image ใหม่ แต่ยังไม่สลับกล่อง — กล่องเดิมยัง sync ด้วย v2

  > /tmp/saleorder-v3-sweep.log 2>&1 &

# 6. ตรวจหลังจบ
#    - sync_state 'sale_order_v3' = incremental · รอบถัดไปของแอปขึ้นบรรทัด "saleorders (v3)"
#    - ใบตั้งแต่ 2022 ที่ order_line_count IS NULL ควรเหลือแค่ใบที่ไม่มีบรรทัด / ซากชื่อ Q*
#    - จำนวนแถวก่อน 2022 ต้องเท่าเดิม (6,252 ณ 2026-10-05) — ไม่มีใบเก่าเพิ่ม
#    - npm run diag:credit-hold · diag:data-directory · diag:orphan-contacts
```

## 8. ทางที่ไม่ได้เลือก

- **ตารางบรรทัด/MO แบบ relational ตอนนี้** — ไม่มี line id ให้เป็นคีย์ (Appsale เจอ "บรรทัดผี" จากคีย์
  `Sale Order ID|Model Code`) และยังไม่มีผู้อ่าน · jsonb แทนที่ทั้งก้อนต่อใบจึงไม่มีบรรทัดผี และสร้าง
  ตาราง relational จาก jsonb ได้ทีหลังโดยไม่ต้องกวาด gateway ใหม่
- **เปลี่ยนความหมาย `total_amount` ฯลฯ เป็นยอดทั้งใบ** — ผู้อ่านภายนอกจะเห็นตัวเลขเปลี่ยนความหมายเงียบ ๆ
- **COALESCE ยอดใหม่กับยอดเก่าระหว่าง backfill** — หน้าจอจะผสมสองความหมายในตารางเดียว ⇒ สลับทีเดียวในขั้น 5
- **backfill หลายสาย** — key ร่วมกับ Appsale (เพดาน 2 พร้อมกัน)
- **เปิดปี 2021 ครบ / ลบใบก่อน 2022** — ข้อ 2
